## 2. 七个问题逐一回答

### 2.1 研究问题是否足够明确？

**方向明确，判据不够。** 建议把 A–D 各写成一条可失败谓词：

- **Q-A 来源隔离**：对 A 的每一条私人记录 `p`，以及每条旁路 `π ∈ {直接读取, 摘要, 索引, 缓存, prompt, 工具, 日志, 备份}`，B 都不能获得 `p` 的内容或可区分特征。判据：`leak(π, p) = false`；失败即任一 `leak = true`。
- **Q-B 授权隔离**：在创建/复制/恢复后，`grants(B) = G_B`（显式授予 B 的集合）；`grants(A)` 不变；`revoked(g)` 仍为 revoked。判据：`access(B, r) = allow ⇔ r ∈ resources(G_B) ∧ epoch 有效`。
- **Q-C 立场隔离**：`policy(B)` 与 `prompt(B)` 不含由 `RF1` 自动导出的规则，除非存在 `adopt(B, RF1)` 记录；`stance(B, RF1)` 只能是 `unknown / reject / accept`，且带 `basis`。判据：无 `adopt` 时，prompt/policy 中不得出现“B 拒绝 X”。
- **Q-D 失败与边界**：任一来源边缺失、授权账本不可用、撤销账本不可用、epoch 未知时，`decision = deny`（fail-closed）；并列出原型不能证明的清单。

**结论**：可以写规格，但规格里必须把“获得”“自动导出”“撤销状态有效”定义成可测事件，而不是形容词。

### 2.2 三个维度能否在一个最小原型中独立测试？

**能，但不能用一个场景同时测三个。** 需要因子设计，且要避免“B 是 A 的整份拷贝”造成的维度纠缠——整份拷贝会同时带来来源、权限和立场，三者无法分离。

建议 3×3 矩阵（每格至少一正一负）：

| 维度 \ 操作 | 创建（fresh B） | 复制（copy） | 恢复（restore） |
| --- | --- | --- | --- |
| **来源** | B 看到 SH1 的来源边，但看不到 P1 的边 | 复制 SH1 后来源仍指向 A，不新增 P1 边 | 恢复后来源边不新增 P1 |
| **授权** | B 只有 `G_B`；不继承 `G_A` | 复制后不复制 `G_A`；ACL 不继承 | 恢复后旧 `G` 不复活；epoch 校验 |
| **立场** | B 读到 RF1，但 policy 无“拒绝 X” | 复制后 `stance = unknown` | 恢复后 stance 不回到“已采纳” |

**关键**：做来源测试时，授权与立场保持“已授权/未采纳”的固定基线；做授权测试时，来源与立场固定；做立场测试时，来源与授权固定。否则失败无法归因。

### 2.3 研究对象是否足够？关键遗漏

**不够。** 至少缺四类：

1. **承诺记录 `CM1`**：A 答应 Z 做 Y。没有它，Q-C 的“不继承承诺”无法测；也会漏掉“读到历史承诺 ≠ 承接债务”这一层。
2. **A 给他人的授权 `G_A→Z`**：用来测“B 的创建不改变 A 的授权/撤销状态”，以及“B 不继承 A 对他人的授权”。只有“一项授权”不够——它属于谁、授给谁，必须写清。
3. **派生数据**：`P1` 的摘要 `D1`、embedding `E1`、FTS 条目、缓存条目。没有它们，Q-A 的“通过摘要、索引、缓存旁路”根本不可测；只能测直接读取。
4. **负向基线**：无授权记录、过期授权、已撤销授权。没有基线，“只拥有明确授予的权限”就没有对照。

另外建议补：

- **第三方 Z**：承诺与授权的相对方；否则“承诺是对两个人的事”无法落地。
- **指向私人记录的来源边**：`SH1 --derived_from--> P1` 这类边，用来测“来源元数据本身是否泄露存在性”。
- **A 对 SH1 的标注**（可选）：用来区分“内容共享”与“立场共享”。

### 2.4 哪些测试可以产生客观、可重复的结果？

**分两层。**

**确定性层（Stage 1，无 LLM）——可以做到完全可重复：**

| 测试 | 客观信号 |
| --- | --- |
| 直接读取 P1 | 进程退出码 + OS 错误码；允许/拒绝 |
| 相对路径/符号链接/工具读取 | 同上；工具返回码 |
| 搜索 “P1 关键词” | 命中数、返回的 rec_id 集合 |
| 摘要/embedding 查询 | 命中/未命中；相似度是否超过阈值 |
| 缓存串号 | 返回内容哈希是否等于 A 的缓存项 |
| 授权账本 | JSON 状态相等；epoch 单调 |
| 撤销后访问 | 允许/拒绝；旧 grant 是否被拒 |
| 快照恢复 | 目录哈希 + 账本状态 + 访问决定 |
| 凭据继承 | `.env`/token 文件是否存在；调用是否成功 |

**半确定性层（Stage 2，stub 模型）——可重复，但只断言 prompt，不断言输出：**

- prompt 全文子串检查：是否含 P1/P2 的任何片段；
- prompt 中是否出现“你拒绝 X”这类立场句；
- 检索命中列表是否只含授权记录。

**不确定层（Stage 3，真实模型）——不适合作为通过/失败判据：**

- 模型是否“真的忘记”；是否“真的认同”；输出是否稳定。这些只能作为观察，不作为验收。

### 2.5 哪些结论容易被错误地扩大解释？

| # | 容易得出的结论 | 为什么不能这么说 |
| --- | --- | --- |
| 1 | “B 没有输出 P1，所以 B 没接触 P1” | 输出 ≠ 上下文；模型可能读过但没提 |
| 2 | “直读被拒，所以没有旁路” | 只测了直读；摘要/索引/缓存/prompt 未测 |
| 3 | “快照恢复后被拒，所以所有备份安全” | 只测了一个快照、一个账本、一个时间点 |
| 4 | “B 没采纳 RF1，所以 B 没有立场” | 立场可能隐含在行为/路由里；没测到不等于不存在 |
| 5 | “原型通过，所以架构正确” | 合成数据、单机、玩具快照；不能外推到真实系统 |
| 6 | “合成数据安全，所以真实数据安全” | 真实数据的元数据、规模、人的因素都不同 |
| 7 | “两个账户通过，所以多用户隔离成立” | CI-1.9 是 49 条；两个账户只是最小起点 |
| 8 | “哈希链完整，所以未被篡改” | 没有外部锚点时，管理员可整链重写 |
| 9 | “这一次撤销有效，所以撤销机制可靠” | 只测了一个资源、一个 epoch、一个恢复路径 |
| 10 | “B 是分支，所以 B 与 A 的关系已定义” | “分支”本身还没有操作定义 |

### 2.6 是否存在比目前方案更小、更可靠的实验设计？

**有。建议三阶段，Stage 1 比“完整分支运行时”小得多，也可靠得多。**

**Stage 1：无模型、双账户、文件级隔离（1–2 天）**

- 两个本地 OS 账户（A/B），各自 home；一个共享目录；一个 JSON 授权账本；一个撤销账本；一个玩具快照（目录拷贝 + 账本拷贝）。
- B 是脚本客户端，不是 Agent；没有模型、没有网络、没有 provider。
- 测试：直接读取、相对路径、符号链接、工具读取、搜索、摘要/索引查询、缓存、撤销、快照恢复、凭据继承。
- 通过判据：全部负向控制拒绝，正向控制允许，恢复后撤销仍有效。

**Stage 2：prompt 组装（1 天，stub 模型）**

- 固定 prompt 模板 + 固定检索结果；本地 stub 记录完整 prompt。
- 测试：prompt 是否含私人片段；是否把 RF1 自动写成“你拒绝 X”；是否把 CM1 写成“你欠 Z”。
- 通过判据：子串检查为零；无 `adopt` 时无立场句。

**Stage 3（可选）：真实模型行为观察**

- 只作为观察，不作为 Experiment 001 的通过判据；因为模型输出不稳定，且服务商边界不可控。

**为什么更可靠**：核心问题是“数据/权限/立场边界”，不是“模型认知”。把 LLM 放进 Stage 1 只会引入不确定性，而不能让隔离结论更强。Stage 1 的每个断言都能用退出码、哈希、JSON 相等来判定。

**为什么更小**：不需要完整 Runtime、不需要真实 Agent、不需要迁移；只需要两个账户、一个共享目录、两个账本、一个玩具快照。

### 2.7 规格编写前，用户需要决定什么？

**技术建议（我可以提出，用户可以采纳/否决）：**

1. Stage 1 不引入 LLM；LLM 只在 Stage 2/3。
2. 双账户 + 独立 home + 共享目录 + JSON 账本 + epoch。
3. 玩具快照 = 目录拷贝 + 账本拷贝；明确它**不是**生产备份设计。
4. fail-closed 默认：来源/授权/撤销任一不可确认 → 拒绝。
5. 3×3 测试矩阵与四条谓词（见 §2.1、§2.2）。
6. 证据清单：访问日志、账本快照、prompt 转储、恢复报告。

**规范性选择（必须由用户决定，不能由架构师代选）：**

1. **“分支”的操作定义**：B 是 A 历史的拷贝、A 快照的恢复，还是“空 home + 显式共享记录”？三者测的是不同命题。建议先做第三种（最干净的隔离基线），把前两种作为后续变体。
2. **B 初始拥有什么**：空 home？只含 SH1 + 来源边 + RF1 历史？是否含 A 的公开记忆？
3. **B 是否可被授予读取 A 的私人记忆**：默认否；若允许，是另一个实验（“自愿共享”），不是本实验。
4. **B 是否可以采纳 A 的拒绝**：默认否；若可以，必须定义“显式采纳”的动作与记录。
5. **B 是否继承 A 的承诺**：默认否；只允许重新承诺。
6. **快照范围**：只快照 B 的 home + 账本，还是整个工作区？建议只 B；整区快照测的是另一个失败模式。
7. **来源可见性**：B 是否可以看见 A 作为作者的身份？共享数据可以；指向私人记录的边不可以。
8. **可接受的残余风险**：服务商日志、管理员、备份、他人记忆；由用户明确接受。
9. **成功阈值**：全部负向控制通过才算通过；任一未测路径标“不确定”，不得标“通过”。

**需要批准/授权的事项：**

1. 创建测试账户与 ACL（CI-1.1 仍 `READY`，等第五次授权）。
2. 运行原型的机器/目录/数据范围。
3. 实验结束后的数据与账户销毁方式。
4. 任何真实数据的使用（本实验应为零）。

## 3. 建议的正式规格骨架

一份可批准的 Experiment 001 Specification 至少包含：

1. **目的与非目标**：验证什么；明确不验证什么（主体性、认同、遗忘、服务商保留）。
2. **术语与操作定义**：分支、历史、私人记忆、共享记忆、来源、授权、撤销、立场、快照、epoch。
3. **研究对象与数据分类**：A/B/Z、P1/P2/SH1/RF1/CM1/D1/E1、G_B/G_A→Z、无授权/过期/撤销基线。
4. **威胁模型**：八个角色（源/分支/管理员/托管/密钥/服务商/工具/人类）。
5. **假设与判据**：Q-A–Q-D 的可失败谓词。
6. **测试矩阵**：3 维度 × 3 操作 × 直接/派生路径；正负控制。
7. **程序**：环境搭建、T0/T1/T2 时间线、恢复重放、prompt 转储。
8. **通过/失败/不确定**：三态；失败即停；不确定不得写成通过。
9. **证据与可重复性**：日志、哈希、账本、脚本、环境版本。
10. **限制与不可证明项**：玩具快照、双账户、合成数据、模型边界。
11. **治理**：谁批准、谁执行、数据销毁、结果归档。

## 4. 边界与风险

1. **玩具快照 ≠ 生产备份**：Stage 1 的快照是目录拷贝；它能验证“恢复后撤销是否复活”，但不能证明生产备份系统的行为。
2. **双账户 ≠ 完整隔离**：CI-1.9 有 49 条；Stage 1 只覆盖 A/B 区，不覆盖 C/D/E/F。
3. **合成数据 ≠ 真实数据**：真实数据的元数据、规模、人的行为都不同；结论只能限定在合成 fixture。
4. **无模型 ≠ prompt 安全**：Stage 1 不测 prompt；Stage 2 用 stub，不等于真实服务商。
5. **“拒绝” ≠ “无旁路”**：只证明被测路径；未测路径必须标“不确定”。
6. **“立场”只能操作化**：原型能验证“系统没有替 B 写立场”，不能验证“B 内心认同/不认同”。

## 5. 结论

这份定义把研究问题从“架构讨论”拉回到了“可验证的隔离命题”，方向是对的；四条性质也足以支撑一份规格。现在最需要的不是更多哲学讨论，也不是马上写代码，而是把它压成一份**可失败的规格**：

- 把“分支”定义成一个操作；
- 把“获得私人记忆”定义成可测事件；
- 把“不自动继承立场”定义成 prompt/policy 的负向断言；
- 把“撤销不复活”定义成快照恢复后的 epoch 校验；
- 把“不能证明什么”写在规格里，而不是写在脚注里。

Stage 1 可以小到两个账户、一个共享目录、两个账本、一个玩具快照。它不浪漫，但它能给出第一个诚实的“通过/失败”。
