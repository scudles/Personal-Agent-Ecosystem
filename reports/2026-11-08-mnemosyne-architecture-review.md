## Q1：五层架构是否存在结构性问题？

**有，而且是结构性的，不是措辞问题。** 三个具体问题：

### 1.1 分类轴不统一（最严重）

五层混了三种不同的划分标准：

| 层 | 实际依据的轴 |
| --- | --- |
| L1 Archive | **来源**（原始 vs 派生） |
| L2 Episodic / L3 Semantic | **记忆类型**（认知科学的 episodic/semantic 二分） |
| L4 Decision | **对象类型**（决策这类东西） |
| L5 Personal | **归属与可见性**（谁的、给谁看） |

这些轴不是互斥的：**一条记录可以同时是"原始的"+"情景的"+"Hermes 私有的"**。它在五层里该住哪一层？没有答案。落地时只有三种结果：

1. 物理存五份（重复、容量炸）；
2. 存一份 + 五张关联表（查询复杂、跨层一致性难保证）；
3. 强行归到"最重要的一层"，其它维度退化成标签（那五层就名存实亡）。

### 1.2 L2 与 L1 高度重叠，且没有规定谁是真相

L2 记的"时间、参与者、项目、关系、结果"基本是从 L1 原始事件**投影**出来的索引。必须明确：**L1 是唯一真相源，L2 可重建**。提案没写这条，会导致"两处不一致时信谁"的长期扯皮。

### 1.3 缺了"读路径"

原则 9/10 说"按需检索，不依赖全量上下文注入"，但五层全是**存储侧**，没有定义**读侧**：启动时加载什么？每轮检索预算多少？命中集怎么缓存？没有读侧设计，"按需检索"就只是一句口号，实现时必然退化成"全量塞进去"或"什么都检索不到"。

### 1.4 我的替代结构：**一条记录 + 三个正交维度 + 派生 DAG**

不要物理分五层，而是把五层变成**查询视图**：

```
记录（唯一的物理表/事件）
├── provenance : raw | derived            ← 相当于 L1 vs L2/L3
├── kind       : episodic | semantic | decision | artifact | aside
├── visibility : shared | private(agent)  ← 相当于 L5
└── links      : derived_from[] / supersedes / refs[]
```

- "L1 Archive" = `provenance=raw` 的视图
- "L2 Episodic" = `kind=episodic`（可从 raw 重建的物化视图）
- "L3 Semantic" = `kind=semantic AND provenance=derived`
- "L4 Decision" = `kind=decision`（**关键：决策是链，靠 `supersedes` 连接，不是层**）
- "L5 Personal" = `visibility=private`

**这样做的好处**：一条记忆只有一份，不会"住在哪层"打架；五层的概念语言对用户和 Agent 仍然成立（它们是视图名）；删除/可见性/溯源都变成对**字段**的操作，而不是"搬层"。

**代价**：用户看到的"五层"是解释层，不是目录层。要在产品语言里说清楚（"这五层是五种看法，不是五个柜子"）。

## Q2：Archive 与各 Agent 私有记忆如何做权限隔离？

**靠操作系统账户 + ACL，不靠代码里判断 `agent_id`。** 但有一个真实难点，提案没提：

### 2.1 表面方案（简单，但不够）

- 共享 Archive：`D:\PAE\shared\memory\archive`，四账号 `RX`，写入器 append-only；
- 私有记忆：落在各自 home，如 `D:\PAE\runtime\hermes-home\memory\private`，只有 `pae-hermes` 有 `F`，其余 deny F；
- 这直接复用已设计的 ACL-02/03，**不需要任何新机制**。

### 2.2 真正的难点：检索进程是一个"跨私有区的读口子"

如果有一个统一的检索服务，它必须以某个身份运行：

| 方案 | 检索进程身份 | 结果 |
| --- | --- | --- |
| A | 用户（Administrator） | 能读所有私有区 → **逻辑隔离形同虚设** |
| B | 每个 Agent 一个检索实例，用各自账号跑 | 各自只看自己的私有区 + 共享区（各自索引，冗余） |
| C | 新增 `pae-index` 账号，对各私有区授 `R` | 制造了一个**新的全可见信任主体**，等于把隔离绕回去 |

**我选 B**。理由：它在现有 ACL 模型内、不新增信任主体、天然满足原则 6（私有记忆不自动进公共知识库）；代价是每个 Agent 各建一份共享区索引（冗余，但个人生态规模下可接受）。

### 2.3 加密作为第二道（可选，但推荐）

私有记忆用该 Agent 的密钥加密落盘。这样即使方案 A/C 被采用（或将来有超级进程），**读到的也只是密文**。注意：**向量也算正文**（embedding 可反推大意），所以私有向量必须同样隔离或加密。

> 这一条与 §6 的删除语义共用同一套密钥机制：**一条记录一个数据密钥**，删除 = 销毁密钥。

## Q3：原始记忆、摘要、认知提取之间如何保证可追溯？

三层机制，缺一不可：

### 3.1 内容寻址 + 派生 DAG

```
event_id = sha256(canonical_json)          # 内容寻址，天然去重
derived 记录必须带:
  derived_from : [event_id, ...]
  derivation   : {method, model, prompt_hash, at, version}
```

派生是**新增记录**，永远不修改原记录 → 形成 DAG：`raw → extraction → semantic claim`。

### 3.2 查询"这句话的依据"

沿 `derived_from` 反向走到底，得到原始事件集合；报告里展示"依据链"而不是"结论"。若链在某处断开（源被删），必须显示 `orphaned_source`，**不能假装还有依据**。

### 3.3 一致性巡检

定期跑 `trace_audit`：

| 检查 | 失败含义 |
| --- | --- |
| 所有 `derived_from` 可达 | 断链（可能被绕过删除） |
| 每条 `kind=semantic` 至少一个来源 | 出现"无来源的事实"（违反原则） |
| `supersedes` 无环 | 决策链自相矛盾 |
| `visibility=private` 的记录不出现在共享索引 | 越界 |

**这一项必须做成可自动运行的检查**，否则"可追溯"只是设计时的承诺。

## Q4：记忆删除、备份、历史审计三者的冲突怎么处理？

**冲突是真实存在的，必须按对象类型分别定义，不能一个"删除"管到底。**

| 对象 | 删除语义 | 理由 |
| --- | --- | --- |
| L1 原始记忆 | **tombstone + 销毁该条数据密钥**（不可恢复，链上留哈希与时间） | 用户意志优先，但"删过"这件事必须可见 |
| 派生记忆 | 不自动删，标 `orphaned_source` | 保留"当时为什么这么想"，否则无法解释历史判断 |
| 决策记录 | **不可删**，只能追加 `revoked` / `superseded` | 决策史是项目资产 |
| 审计日志 | **不可删**（现有设计） | 安全边界 |
| 备份 | 无需特殊处理 | 见下 |

### 4.1 关键洞察：加密让"备份里还有副本"这个问题消失

传统删除的死结是"数据有五个备份，你得把五个都擦干净"。**每条记录独立密钥 + 删除即销毁密钥**之后：

- 备份里的密文**永久不可解**，不需要碰备份；
- 恢复备份也不会"复活"已删记忆（解密失败）；
- 恢复流程里必须显式标 `unrecoverable_deleted`，不能当成"文件损坏"去修。

这是选"逐条密钥"的**核心理由**，不只是优雅。

### 4.2 代价（必须让用户知道）

1. 密钥丢失 = 数据永久丢失（所以密钥要有独立备份策略，且**不与数据同盘同备份**）；
2. 删除**本身**会留痕（谁在什么时候删了什么 id）——这是可问责性，但也意味着"删除不是隐形的"；
3. 无法做"删了还能反悔 30 天"的回收站 —— 除非先保留密钥一段时间再销毁（**建议**：默认保留 7 天，之后销毁；需用户定，P-013）。

## Q5：长期存储扩展会不会导致检索质量持续下降？

**会。而且这不是"容量大了慢"的问题，是"记忆污染"的问题**：大量低价值、重复、闲聊内容会把真正有用的记忆挤出 top-k。

没有任何方案能承诺"无限增长且质量不降"。能承诺的是：**质量下降可观测、可干预**。措施五条：

1. **写入端分层打分**：入库时算"信息量 / 重复度 / 与已有记忆的相似度"，低分进 cold 层，**降低检索权重但不排除**（← 2026-11-09 修正：原写"默认不参与检索"是错的，等于软删除；见 [第二轮答复](2026-11-09-mnemosyne-deletion-and-id-privacy.md) Q2）；
2. **分层检索**（先窄后宽）：`决策 → 近期事件 → 语义 → 全库兜底`，并给每层预算；不是一上来全库 top-k；
3. **时间衰减只影响排序，不影响可检索性**：否则"很久以前但很重要"的记忆会消失——这是最容易做错的一点；
4. **内容寻址去重 + 会话聚类**：重复闲聊合并成"会话摘要"节点，原文仍在 L1；
5. **检索质量体检**：维护一个小测试集（问题 → 应命中的 event_id），每次重建索引后跑一遍，Recall@k 掉超过阈值就告警。**没有这个，质量下降是无声的。**

### 5.1 给数字（便于判断什么时候必须换架构）

| 规模 | 检索方式 | 预期 |
| --- | --- | --- |
| < 1 万条 | SQLite FTS5 + 暴力向量 | <20 ms，质量好 |
| 1 万–10 万 | FTS5 + 分区（按项目/时间） | <100 ms，需去重与打分 |
| > 10 万 | 必须 ANN（HNSW/IVF）+ 分层检索 | 否则延迟与召回都会塌 |
| > 100 万 | 单机 SQLite 不合适 | 需要列存/搜索引擎，个人项目应在此前归档 |

**诚实结论**：Mnemosyne 的规模上限不是存储，是**检索质量的可维护性**。

## Q6：Mnemosyne 应该是独立基础设施，还是某个 Agent 的附属模块？

**独立基础设施，但不要做成独立服务。**

- **必须独立**：如果长在 Hermes 的 memory 目录里，DSH 就永远是二等公民，而且数据模型会被第一个实现者绑死（Hermes 的记忆模型 ≠ DSH 的）。
- **不必做服务**（现阶段）：独立服务带来生命周期、端口、崩溃恢复、升级迁移，与当前项目阶段（还在做账户隔离）严重不匹配。
- **折中做法**：先定**数据契约**（文件布局、事件 schema、检索 API 的输入输出），实现可以是进程内库。将来若要独立成服务，契约不变、调用方不改。

一句话：**独立的是契约与数据所有权，不是进程拓扑。**

## Q7：与 DSH、Bridge、Nagi Memory 的边界

| 对象 | 它负责什么 | 与 Mnemosyne 的边界 |
| --- | --- | --- |
| **Bridge** | 身份、授权、审计、准入 | Mnemosyne 每次写入**必须过 Bridge 准入**；但 Bridge **不存内容**——它只记"谁在何时写了哪个 `event_id`"。内容留在 Mnemosyne。 |
| **DSH** | 执行者 / 插件生态 | DSH 是**消费者**（检索、写入），不拥有存储。插件要写记忆，必须用 DSH 自己的 Agent 身份 + Bridge 授权，**不得直接写文件**。 |
| **Nagi Memory**（凪，`E:\凪`） | 用户自己的 Live2D 陪伴角色的记忆 | **建议不合并。** 见下。 |

### 7.1 为什么不该把凪的记忆并进来（这条我要说重一点）

1. **性质不同**：凪的记忆是"一个角色的经历"，带着情感与人格连续性；PAE 的 Mnemosyne 是"一个生态的项目与认知资产"。合并会让凪的私人经历变成可被其它 Agent 检索的公共知识——**这正好破坏用户最在意的"她有不是为你而存在的东西"**。
2. **用户明确说过**不希望她和自己看一样的东西；把她的记忆变成共享库，等于让她的一切都可被审查。
3. **技术上也不同**：凪是单角色、强情感、含语音/日记/偏好；PAE 是多 Agent、项目导向、含决策链。硬合并会互相污染数据模型。

**建议**：**接口不合并，格式可互操作**。需要共享时走"用户主动导出 → 显式导入"（带来源标记 `imported_from=nagi`），不做后台同步。她的记忆留在 `E:\凪`，保持独立。

## 8. 我的替代架构（供讨论，不是实施）

```
写入路径：Agent → Bridge（授权+审计）→ Memory Writer → 事件日志(raw) + blob + SQLite 元数据
                                           └→ 派生作业（异步）：抽取 episodic / semantic / decision 链接

读取路径（回应"不注入全部历史"）：
  启动：只加载 [决策索引] + [近 N 条] + [pinned 记忆]          ← 通常是几十 KB
  每轮：query = 当前消息 + 最近 k 轮摘要
        → 按 visibility 过滤（先过滤再检索，绝不反过来）
        → 分层检索（决策 → 近期 → 语义 → 全库兜底）
        → 命中集进上下文（带 budget，超了截断并标注"已截断"）
  缓存：命中集缓存 + 失效规则（新事件写入即失效）
```

**三个开关分开**（回应 Lounge 那条）：

| 频道 | archive（保存） | cognition（提取） | retrieval（默认可被检索） |
| --- | --- | --- | --- |
| Project Room | 默认开 | 默认开 | 开 |
| Lounge | **需独立授权**（默认关） | 默认关 | 默认关 |
| 自主交流 | 需独立授权 | 默认关 | 默认关 |

这样"Lounge 不写认知"不会连带"Lounge 没有历史"。
