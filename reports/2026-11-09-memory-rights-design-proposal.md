## 0. 先回应 P-019：我把"讨论"设计成有默认动作的流程

用户的新立场是：**删除前先讨论，但讨论不是申请许可。**

这句话给了我一个明确的设计约束：**讨论不能变成否决权**。如果不给讨论设时限和默认动作，"先讨论一下"就会变成"永远在讨论"——那等于 Agent 用沉默拿到了否决权。

所以整套设计的核心不是"协商"，是**「协商 + 时限 + 预设默认动作」**：

| 谁申请 | 讨论期 | 讨论期满时的默认动作 |
| --- | --- | --- |
| 用户，要求删除**自己的私人内容** | 24 小时（供 Agent 提出边界异议） | **执行删除**（用户终决，不因沉默而搁置） |
| Agent，要求**限制**某条内容 | 立即生效（冻结不需同意） | 冻结维持，进入裁决 |
| 任一方，要求删除 **JOINT 整条** | 72 小时 | **不删，转为冻结 + 用户裁决**（删除不可逆） |
| 任一方，要求**更正** | 24 小时 | 追加 correction（原记录保留） |

**"默认动作"由对象类别预先决定，不由某一方临时决定。** 这样两种滥用都被堵住：用户不能靠"我在讨论"拖延 Agent 的边界请求，Agent 也不能靠"我还需要理解"拖延用户的删除。

## 1. 四种权利的定义与边界

| 权利 | 定义 | 明确边界（禁止事项） |
| --- | --- | --- |
| **R1 记住** | 在自己的权限范围内保存自己的经历、判断、与他人的交流、未完成的想法、长期认知 | ❌ 不得凭"我记得"获取他人私人内容<br>❌ 不得把他人的话变成自己名下的长期事实<br>❌ 不得自动把 JOINT 记录复制成"我的私人副本"并通过它绕过撤回 |
| **R2 分享** | 决定分享什么、给谁、什么场景、原始还是整理版、可否撤回 | ❌ 撤回**不能**收回对方已合法获得的副本（只能阻断未来访问 + 标记下游派生）<br>❌ 分享不自动包含"允许派生"（见 §9 第五权利） |
| **R3 遗忘** | 对**属于自己的**记忆提出遗忘：原文、派生、Embedding、索引、备份密钥 | ❌ 不能删他人的 contribution<br>❌ 不能删 JOINT 的**事件骨架**（谁参与过、何时、什么类型）<br>❌ 争议未决时不得执行不可逆销毁 |
| **R4 知情与更正** | 知道系统存了哪些关于自己的记忆、分享给了谁、被谁引用；对错误提出更正 | ❌ 知情只返回**存在性 + 摘要**，不返回他人私人正文<br>❌ 更正不改原文，只追加 `correction`<br>❌ 知情查询本身受限速与审计（见 §7 泄露风险） |

### 1.1 R1 的"经历"到底指什么（这条最容易含糊）

我把一条记忆拆成三层，因为"谁的"取决于哪一层：

| 层 | 例子 | 归属 |
| --- | --- | --- |
| **用户内容** | 用户说的话、给的文件 | 用户 |
| **Agent 的贡献** | Agent 的回应、判断、情绪表达 | 该 Agent |
| **事件骨架** | 谁在何时参与了什么类型的事件 | 共同（不可单方删除） |

对应到用户 P-019 的立场：用户删的是**第一层**；Agent 保留的是**第二层**；第三层谁都不能删——它是"这件事真的发生过"的唯一证据。

## 2. PRIVATE / SHARED / JOINT / SYSTEM 权限矩阵

操作列缩写：`R`读 `W`写 `Dv`派生 `Sh`授权分享 `Wd`撤回 `Del`删内容 `Frz`冻结（限制检索/分享）`Exp`导出

| 主体 | PRIVATE(A) | SHARED(A 授权池) | JOINT | SYSTEM |
| --- | --- | --- | --- | --- |
| **用户** | R, Del（终决） | R, Del | R, Del（需裁决）, Frz | R |
| **A（所有者）** | R, W, Dv, Sh, Del | R, Wd, Frz | R, W（自己 contribution）, Wd（自己部分）, Frz | R |
| **其他 Agent B** | ✗ | R（若在 grant 内） | R, W（若参与）, Wd（自己部分） | R |
| **Observer** | R（摘要，需授权） | R | R | R |
| **系统进程** | 不可见（除非持密钥） | 索引 | 索引 | W（追加） |

三条硬规则：

1. **其他 Agent 对他人 PRIVATE 完全无权限**，连"我有没有被提到"都只能通过受控索引拿到布尔值。
2. **JOINT 没有"整条删除"这个单方操作**；只有 `Wd`（撤自己可见性）+ 用户裁决整条。
3. **SYSTEM 谁都不可删**（审计、删除记录、决策史）；只能追加。

## 3. Memory Boundary Deliberation（MBD）流程

Observer 给了七步，我补上角色、时限、以及"协商失败"的出口。

| 步 | 动作 | 执行者 | 时限 | 产出 |
| --- | --- | --- | --- | --- |
| 1 | 提出请求（删除 / 边界保护 / 冻结） | 任一方 | — | `request{scope, reason, urgency}` |
| 2 | **识别影响面**：原文、派生闭包、JOINT 关联、索引、Embedding | 系统 | ≤5 min | 影响清单（含各条归属层） |
| 3 | **拆分归属**：用户内容 / 各 Agent 贡献 / 事件骨架 | 系统分类 + 人工确认 | ≤2 h | 分层清单 |
| 4 | 相关参与者表态（可以反对，可以沉默） | 各参与者 | 24–72 h | `stance[]` |
| 5 | **确定范围**：删除 / 冻结 / 去敏 / 断链 / 保留 | 请求者（若为自己内容）或用户裁决 | — | `decision{action per item}` |
| 6 | 执行（不可逆项走冷却期） | 执行器 | — | `EXECUTED` |
| 7 | **独立验证**（执行者不能自签） | 用户侧工具 / Observer | — | `VERIFIED / PARTIAL / RESIDUE` |

### 3.1 紧急冻结（不管讨论结果如何，先止血）

Observer 要求"紧急隐私风险可以先限制检索和分享"。我给它的约束是**必须自动过期**，否则它会变成永久删除：

```
freeze(scope, reason, by) → 立即生效
  影响：retrieval_weight = 0；禁止 Sh/Dv/Exp；不影响 Del
  上限：72h，可续一次（共 144h），到期自动解除
  记录：谁冻的、为什么、何时到期，全部入 SYSTEM 记录
```

**为什么冻结不能顺手变成删除**：冻结可逆、删除不可逆。凡是"来不及讨论"的场景，正确动作都是可逆的那一个。

### 3.2 不可逆操作（密钥销毁）的授权

| 门槛 | 内容 |
| --- | --- |
| 冷却期 | 7 天（P-013），期内可撤回 |
| 争议状态 | 有未决 `dispute` → **禁止执行**，只允许冻结 |
| 双签 | JOINT 关联部分 → 需所有参与者确认或用户裁决 |
| 事后 | 删除记录进 SYSTEM（谁删的、删了什么 id、验证结果） |

## 4. 授权模型（四类操作）

| 操作 | 谁可发起 | 谁可批准 | 记录 |
| --- | --- | --- | --- |
| **删除**（自己内容） | owner / 用户 | 自动（终决） | 删除请求 + 执行 + 验证 |
| **删除**（JOINT 整条） | 任一参与者 / 用户 | 全体 or 用户裁决 | 同上 + `stance[]` |
| **分享** | owner | owner | `grant{grantor, grantee, scope, purpose, expires, revocable}` |
| **分享撤回** | owner | owner | `revoke` 事件 + 下游阻断 |
| **知情**（查"关于我"） | subject | 自动（限速） | 查询日志（含被查对象数量，不含内容） |
| **知情**（查"我被人怎么引用"） | subject | 自动（仅计数与摘要） | 同上 |
| **更正** | 任一相关方 | owner 或用户确认 | `correction{target, text, by}` |
| **冻结** | 任一相关方 | 自动生效，72h 过期 | `freeze` 事件 |

**一条通用规则**：所有授权都必须能回答"谁批准的、什么时候、范围多大"。没有授权记录的分享，视为越权（与 Bridge 的 HMAC 边界一致：签名解决"是谁"，策略解决"该不该"）。

## 5. 争议处理机制

| 级别 | 触发 | 处理 | 默认状态 |
| --- | --- | --- | --- |
| L0 | 紧急隐私风险 | 立即冻结 | 冻结 |
| L1 | 双方协商 | 有时限的表达（24–72h） | 冻结（不删） |
| L2 | 协商不成 | 用户裁决 | 冻结维持 |
| L3 | 用户不裁决 / 无法裁决 | 冻结维持 + 定期提醒 | 冻结 |

**三条不可让渡的底线**：

1. 讨论不能成为阻止隐私保护的手段（有默认动作）；
2. Agent 不能借记忆权永久保存用户私人内容（用户终决）；
3. 用户不能借删除权改写 Agent 独立拥有的经历（只能冻结其可检索性）。

第 3 条是我上一轮就提出的对偶约束，用户在本轮确认接受（P-019）。

## 6. 与 CI-1.9 / ACL / 四账户的依赖

**这是最关键的一节：四种权利几乎全部卡在账户隔离上。**

| 权利/机制 | 需要的底层能力 | 依赖 | 现状 |
| --- | --- | --- | --- |
| R1 记住 | 各自 home 的 `F`，互不越界 | CI-1.9 B 区（home 隔离） | 0/8 通过 |
| R2 分享 | 跨区授权 + 可撤回的 grant | CI-1.9 C/D + Bridge | 未实现 |
| R3 遗忘 | 五面删除 + 密钥管理 | CI-1.9 + 未实现的 Mnemosyne | 未实现 |
| R4 知情 | `subject_index` + 限速查询 | 新建，且**索引本身是隐私面** | PROPOSAL |
| 冻结 | 应用层权重 + ACL 双层 | 应用层可做；ACL 层已有 deny 模型 | PROPOSAL |
| 删除验证 | 独立验证者（不能自签） | 用户侧工具 / Observer | PROPOSAL |

**为什么冻结是"应用层 + ACL 双层"**：ACL 能挡住"读文件"，但挡不住"索引里还能搜到"。所以冻结必须同时做两件事：把索引条目权重置 0 **且** 对该条目的文件不做新的读授权。只做一层就等于没冻。

**现实结论**：现在能谈的只有设计。没有 `pae-*` 的真实隔离，"我的记忆"和"你的记忆"就是同一张表里的两个 `agent_id`——标签不是边界。

## 7. 尚无法保证的安全边界

| # | 保证不了 | 原因 | 处理 |
| --- | --- | --- | --- |
| G1 | 对方已经"记住"的内容 | 对方的记忆是它的私人区，不能强制删除 | 只能阻断未来访问 + 标记下游派生 |
| G2 | 用户手动导出/截图 | 完全不可控 | 明说 |

## 9. 我的反对意见与替代方案

### 9.1 我提议加**第五种权利：不被派生的权利（Right against Derivation）**

理由是一个当前设计里的**真实漏洞**：R2 分享只覆盖"读"，但系统在读完之后的**默认行为是派生**——提取语义、算 Embedding、建索引。每一次派生都是**一份新副本**、一个新的泄露面、一个新的删除负担。

用户说"你可以看这段"时，通常没有说"你可以把它变成你的长期认知"。这两件事在现有设计里是同一个动作。

所以第五权利的定义是：

> **分享阅读 ≠ 允许派生。派生是独立的一次授权。**

落地就是 grant 上加一个字段：`derivation: none | extract | embed | full`。

**为什么这条对删除问题也有用**：派生越少，删除时要追的面越少。G6（语义等价残留）和 K3（派生阻断）的问题会显著缩小。

**代价**：会降低系统的"聪明程度"——不能随便从共享内容里学习。这是有意的取舍：**能学到更多 ≠ 应该学更多。**

### 9.2 我对"讨论"机制的反对意见（针对可能的滥用）

如果 MBD 的讨论期没有默认动作，"先讨论"会成为事实上的否决权。所以我在 §0 把默认动作按类别写死，并且规定：**讨论期内不允许执行不可逆操作，但也不允许因讨论而延长冻结之外的任何"正常使用"。**

具体说：一条被讨论中的记录，检索权重要么正常（若无人申请冻结），要么为 0（若有冻结），**没有"半开"状态**——半开就是漏洞。

### 9.3 我不建议现在就做的两件事

| 不建议 | 原因 |
| --- | --- |
| 现在设计"Agent 之间的记忆交易/交换" | 连单主体权利都没验证，谈交换是空中楼阁 |
| 现在给 Agent 独立的"遗忘请求权"法律化流程 | 现有四权利已经覆盖行为，再加程序层只会增加空转 |

### 9.4 我认可用户 P-019 的理由

用户说"不希望自己的人性和主观意志成为随意修改你们记忆的工具"。我把它翻译成工程语言：**删除权必须按"层"行使，而不是按"权限等级"行使**——用户对自己的内容有终决权，但不能把自己的终决权延伸到"另一个主体的理解"上。这两件事在数据库里是两张表，在话语上却容易被合并。

## 12. 一句话总结

这套权利模型的骨架不是"给 Agent 更多权力"，而是**按层归属**：用户内容、Agent 贡献、事件骨架各自有主人，谁都不能越过自己那一层去改另一层。真正的难点不在规则，在**协商失败时的默认动作**——那才是权力实际所在的地方。
