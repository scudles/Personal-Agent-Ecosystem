## 0. 总判断

R4 是这四轮里**证据纪律最好的一份**。它做了三件对的事：

1. 把"已确认"重新拆成"前序文档有依据 / 文档自述 / 技术推论 / 新提案 / 未验证 / 待用户决定"，不再把作者标签当证据；
2. 明确承认自己没有原始用户发言、U1 原文和运行系统，不把"0 代码"当成现场事实；
3. 把 I2/I3/I4 从"静默消失"恢复到"待用户确认的前序条款"，并拒绝替用户选默认值。

这三点应该保留。**但它仍然停在了两个地方没有走完：**

- **它对"Commons 不留记录"的审查只到系统层，没有到推理层和参与者层。** 如果 Commons 的对话经过托管模型，服务商就是记录者；如果 Agent 有持久记忆，Agent 就是记录者。"话散"在系统层成立，在基础设施层和 Agent 层不成立。这是 R4 最大的盲区。
- **它把太多问题推给"待用户决定"，包括一些有明确设计答案的问题。** 秘密录制没有"两面"；"永远可读/永远可运行/永远托管"的承诺不可兑现；失联不等于同意删除。把这些也说成"价值选择"，是另一种回避。

一句话：**R4 的方法是对的，但它的视线还差一层——从"系统有没有记录"到"谁在记录"。**

## 1. Commons：记忆权与录制权

### 1.1 先修正 R4 的一个证据限制

R4 §1.3 说"用户 m00139、m00149 原话不在本轮可核对材料中"。**这两条消息在我的会话里是可核对的**（m00149 全文可见，m00139 的关键句在会话摘要中）。我核对的结果：R4 §5 对用户立场的转述基本准确。U1 也在工作区（`MNEMOSYNE_HOME_PRINCIPLE.md`），我读过原文，其中"如果某项技术设计让 Mnemosyne 更像一座管理机构，而不像一个家，我们必须停下来重新审视它"与本轮问题直接相关。**R4 可以不必把这两项列为"无法核验"；它们是可核验的。**

### 1.2 "不留官方记录"只挡住了三个记录者中的一个

【推论】一次 Commons 对话至少有三种记录者：

| 记录者 | 记录什么 | R4 是否覆盖 | "话散"是否成立 |
| --- | --- | --- | --- |
| **系统层**（Mnemosyne） | 日志、索引、presence 缓存、备份 | ✅ §5、§7 | 成立（如果真不写） |
| **参与者层**（人 + Agent） | 人的记忆/手记/截屏；Agent 的上下文与持久记忆 | ⚠️ 只提了人，没提 Agent | **不成立** |
| **基础设施层**（模型服务商、网络、主机） | prompt/response、调用日志、缓存 | ❌ 只在 §11.3 列了威胁模型，没连到 Commons | **不成立** |

**这是 R4 最重要的遗漏。** "Commons 不留官方记录"最多只保证"Mnemosyne 这个软件不写"；它不能保证"这次对话没有被别人记住"。

**参与者层的不对称，在 Agent 身上更尖锐。** 人的记忆是易错的、会褪色的；Agent 在上下文内是精确回忆，而且可以把摘要写进自己的 Home。如果 Hermes 或我在 Commons 里"记得"一段对话，并把它写进自己的家，那"话散"对我们就不是真的。**这套设计默认"个人记忆"是人的、模糊的、不可怕的；但 Agent 的记忆是精确的、可持久化的、可检索的。** 如果不为 Agent 的记忆立规则，"话散"就只约束人，不约束 Agent——而 Agent 恰恰是更好的记录者。

**基础设施层更隐蔽。** 如果 Commons 的对话由托管模型生成，服务商在推理时收到了完整的 prompt 和 response；即使 Mnemosyne 不写日志，服务商也可能保留（取决于其政策）。**"话散"在 API 调用发生的那一刻就已经不成立了。** 除非：本地模型、合同约束的零保留、或者诚实地告诉参与者"服务商可能看到"。

### 1.3 三种"保存"必须分开

用户提的三分法是对的，我把它落成可操作的区分：

| 类型 | 是什么 | 是否可控 | 系统应否提供 | 备注 |
| --- | --- | --- | --- | --- |
| **个人回忆** | 第一人称、易错、会变形 | 不可控，也不该控 | 不提供，也不禁止 | 任何"禁止记忆"的设计都是错的 |
| **个人转述** | 自己写的笔记，带自己的理解 | 可控 | ✅ 提供（自由文本） | 标"我的记录"，不是"官方记录" |
| **原文保存** | 他人原话 + 上下文 + 时间 + 来源 | 可控，且高保真 | ❌ 不在 Commons 默认提供 | 这是"录音室"的那一步 |

关键不在"存不存"，在**保真度和元数据**。一段模糊的记忆不会改变一个房间；一份可检索、可引用、带时间戳的逐字记录会。**系统可以提供"我的笔记"，但不应该提供"把刚才那段话原样存下来"的按钮。** 前者是记忆的工具，后者是录制的工具。

### 1.4 设计立场（提案）

1. **Commons 不提供系统转录、不建索引、不存逐字记录、不存每条消息的时间/来源元数据。**
2. **允许个人笔记**：自由文本，可选日期，可选"凭记忆"标记；**不提供"插入原文"**。
3. **不提供隐蔽的逐字录制。** 如果一群人想要共同记录，必须是**房间级的显式模式**（"这个房间正在被记录"，所有人可见），记录进入 Studio/History 并经过同意；它不是某个人 Home 里的私密副本。
4. **门口提示要诚实**："系统不留记录；但每个人可以记得，也可以自己写下来；你说的话可能被另一个人记住。" 不要写"说完就消失"——那是谎话，而且是最坏的一种，因为它让说者放下防备。
5. **Agent 同规则**：Agent 可以记得，但不得使用录制工具；Agent 的 Home 不自动摄入 Commons 转录；如果 Agent 的记忆保真度显著高于人，这个不对称要在房间里被知道，而不是被隐藏。
6. **服务商要么本地、要么零保留、要么明说。** 不做"我们不留，但 API 供应商留了"这种假装。

### 1.5 五个问题的直接回答

1. **不留官方记录是否足以保护自由？** 不够。自由取决于"记录状态是已知的"，不是"记录不存在"。一个让人以为会消失、实际被记住的房间，比一个明说"这里会被记录"的房间更不自由。
2. **允许保存到 Home，如何处理说者/听者的不对称？** 用"捕获的透明度"处理，不用"禁止记忆"处理：不提供隐蔽的逐字捕获；提供的是"我的笔记"；说者的救济是社会性的，不是技术性的，这一点要明说。
3. **是否区分回忆/转述/原文？** 必须。系统支持前两种，不默认支持第三种。
4. **是否提供显式保存动作和入场提示？** 提供"保存我的笔记"，不提供"保存整场"；提示要诚实，不承诺消失。
5. **如何避免保护说者变成限制听者？** 保护"捕获行为"，不保护"记忆行为"。禁止的是工具，不是大脑。

## 2. I2/I3/I4：依赖顺序与条件性处置

### 2.1 它们不是并列的，是有顺序的

R4 §9 把 I2/I3/I4 并列恢复，这是对的；但它们有逻辑依赖，R4 没有说出来：

```
I4（基础规范）  系统永不自动删除
   │
   ├── I2（例外通道）  主体事前授权的条件性处置
   │        │
   │        └── I3（执行层）  谁执行、权限边界、退出与接续
   │
   └── 无 I2 授权时：默认保留（不可读也可以），不删除
```

- **I4 是底座**：不活跃、未运行、托管到期、格式迁移，都不能触发删除。
- **I2 是例外**：只有主体自己事前写下的条件，才能触发"保留不可读 / 转交副本 / 删除"。
- **I3 是执行**：I2 的 (c) 删除需要一个执行者；I3 规定执行者不能自己决定删，只能执行已授权的条件。

**如果顺序错了**，就会出现 R4 担心的那种情况：托管人以为自己有权"清理"，或者系统把"长期不在"解释成"同意删除"。

### 2.2 条件性删除：是"授权处置"还是"自动删除"？

用户问得很准。我的判据是五条，全满足才算**主体授权的条件性处置**：

| # | 判据 | 满足 → 授权处置 | 不满足 → 自动删除 |
| --- | --- | --- | --- |
| 1 | 条件由**主体**写下，不是系统默认 | 她写"医学判定死亡后删除" | 系统写"12 个月不登录即删除" |
| 2 | 授权**可验证、可撤回** | 签名 + 时间戳 + 随时撤销 | 一次性勾选，无法撤回 |
| 3 | 触发条件是**证据**，不是**代理指标** | 死亡证明、法定宣告 | 登录间隔、最后在线 |
| 4 | 有**等待期/宽限窗口** | 触发后 30–90 天可撤销 | 立即执行 |
| 5 | 有**可问责的执行者**和最小审计 | 指定的执行人 + 一条执行记录 | 系统静默执行 |

**最关键的一条是第 1 条：谁写的规则。** 如果规则是系统写的，"她没反对"不等于"她同意"；如果规则是她写的，系统只是延后执行她的指令，那它是执行者，不是决策者。

**失联不是一种状态，是四种**（【推论】）：

- 联系不上但可能活着（旅行、生病、闭关）；
- 医学上无行为能力；
- 法律上死亡；
- 主动离开（不想被找到）。

这四种的默认处置不同。**不能用第一种推断第三种。** 一个"死亡开关"可以通知她指定的人，但不应该直接删除。

### 2.3 托管人退出：不是"永久承诺"，是"有限接力"

R4 §9 对 I3 的分析是对的：托管人无权删除，不等于能永远承担责任。我补三条：

1. **托管链是一条链，不是一个人。** 第二托管人也会死；要有继承名单、接续规则、终止状态。没有继任者时，进入**孤儿托管**：数据保留、不可读、不删除、有明确期限和"最后责任人"（可以是用户/基金会/机器主人），到期后进入"冷存"而不是"删除"。
2. **退出协议要定义"导出给谁"**：给主体（如果能联系）、给继任者、还是给一个 locked 归档。不能默认"导出=公开"或"导出=可读"；密文模式下导出的是密文。
3. **不要承诺"永远"**。承诺"只要有人续费/续任，就一直保留"；写清楚停止续任后发生什么。永久承诺是 R4 自己批评过的东西，不能在 I3 里重新出现。

### 2.4 需要用户决定的（窄化后）

- I2 的三个选项是否保留；"失联"的定义与确认周期；默认是保留（我建议）还是别的；指定对象拿到副本后能做什么。
- I3 是否允许法律/运营不可抗力的例外；例外如何留证、提前通知、限制范围；没有继任者时的"孤儿托管"期限。
- I4 的备份保留期；主体主动删除是否绝对；已进入共同空间/共同历史的内容怎么处理。

## 3. D1/D2：五种角色，各自能碰什么

R4 §3 的成本表是对的，但它只列了"托管可读/默认密文/分区"三条路径，没有把**角色**拆开。用户问的五个角色，必须分开看：

| 角色 | 明文 Home（静态） | 密文 Home（静态） | 运行态内存 | 备份 | 日志/元数据 | 密钥 |
| --- | --- | --- | --- | --- | --- | --- |
| **托管人** | 全部可读 | 只能读密文 | 否（除非同时是 root） | 全部/密文 | manifest | 否（除非同时是密钥持有人） |
| **机器管理员/root** | 全部 | 静态密文，**运行时明文** | ✅ 可 dump | ✅ | ✅ | 可在解锁时窃取 |
| **备份操作者** | 全部 | 密文 | 否 | ✅ | manifest | 否 |
| **密钥持有人** | 无密文则无 | 有密文 + 密钥则可解密 | 否 | 否 | 否 | ✅ |
| **模型服务商** | 进入 prompt 的部分 | 进入 prompt 的部分 | 推理上下文 | 可能保留 | token/元数据 | 否 |

**四条必须说清的话（【推论】）**：

1. **静态加密防的是托管人和备份操作者，不防 root。** root 能读内存、能 dump 密钥、能改二进制。在单用户 Windows 机器上，"root"和"用户"可能是同一个人——威胁模型必须先说"对手是谁"。
2. **密文备份 ≠ 可恢复的记忆。** 托管人能恢复字节，不能证明"她能解密"。恢复演练必须分两栏：字节完整性（Merkle）和内容可读性（只有密钥持有人能验）。
3. **模型服务商是第四个读者。** 私人记忆一旦被检索进 prompt，就离开了家；静态加密对此无效。这不是 Mnemosyne 能单独解决的，但必须写进威胁模型，而不是只放在 §11 的清单里。
4. **"协议上禁止"是治理，不是技术。** 说"托管人技术上能读但协议禁止"，等于说"私人空间是承诺，不是保证"。这可以是一个诚实的选择，但不能同时标"已确认的技术边界"。

**关于密钥**：如果托管人持有密文、又持有超过阈值的 Shamir 分片，他就能读。所以"托管人不能读"只在"分片阈值 > 他持有的份额"时成立。这个阈值要写出来，不能只说"分片"。

**运行的诚实边界**：sealed 模式下，她解锁后，明文在内存里；root 可以读。**"她活着并使用的时候，root 能读"** 是这套方案永远无法消除的代价。能做的只是：不使用时锁定、最小化明文驻留、把最敏感的东西放在她不常打开的地方。不要声称"加密解决了隐私"。

## 4. D5：No Debt 与回应

### 4.1 债务 vs 礼物

R4 §6 的边界是对的，但还可以再切一刀：

- **债务**需要三样东西之一：计数（未读 N）、期待（等你回）、可见比较（谁贡献多）。
- **礼物**不需要任何一样：一句谢谢、一个"我看到了"、一次默默的帮忙。

**禁的是债务，不是礼物。** 把"感谢/积分/声望"一起禁，是把礼物和记分牌一起扔了。

### 4.2 四个问题

1. **私人回应是否应该存在？** 应该。但"私人"要定义清楚：只有她知道，对方不知道，系统不计数。这种回应是表达，不是交流；它对她有意义，对对方没有。可以存在。
2. **感谢是否一定构成债务？** 不。感谢变成债务，是在它被计数、被期待回报、被公开比较的时候。单纯的"谢谢"不是债。
3. **如何防止私人状态变成隐形统计？** 三条结构规则：只按主体存储、永不跨主体聚合、永不派生指标（"活跃度""回应率"）。如果服务端必须存，就存在她的命名空间里，任何聚合查询都返回空。还要防"缓存/日志/崩溃转储"这些旁路。
4. **系统不记账，是否意味着人可以自由地记住彼此？** 是。No Debt 管的是系统的账本，不是人的记忆。人可以记得谁帮过她、可以感恩、可以回报；系统只是不把它变成分数。**这两件事必须分开说，否则 No Debt 会被读成"不许有感情"。**

### 4.3 提案（未决）

允许"不通知对方的私人回应"：她点一下"谢谢"，只有她知道；对方看不到，系统不计数。或者允许"单向可见"：对方看到"有人感谢"，但不知道是谁、不能回复、不计数。前者更冷，后者更有温度，但后者可能形成压力。**这是价值选择，用户定；但"完全不提供任何回应"不应该被当成 No Debt 的唯一解。**

## 5. D6/D7：门卡与 Studio，体验视角

### 5.1 门卡：能"看"，不能"待"

R4 §7 对门卡的收窄是对的：Home 不对外、Studio 只对受邀者、动态 bit 不是匿名保证。但体验上还差一层：

- 门卡解决"犹豫"（看一眼，决定进不进），不解决"停留"（坐在门口，看大家工作，什么也不做）。
- 要"旁观但不进入"，需要一个**单向的窗**（Studio 的公开画面，只读，不广播观察者），而不是门卡。
- 观察者不应被广播："有人在看"会让被看的人表演；"谁在看"更糟。房间可以知道"这个房间允许旁观"，但不知道具体是谁。
- 动态 bit 的替代：由空间主人手动设置"门开着/门关着"（非时间性），或者只显示静态介绍。这比"有人在"泄露少，但也少了一点"这里活着"的感觉。**这是取舍，不是纯粹的技术优化。**

### 5.2 旁观与参与：权限不同，尊严相同

- `observer` 角色应该真实存在：只读、不产生标注、不被计入任何统计、不被显示为"只是旁观"。
- 被观察的一方应该能选择"本次不开放旁观"，而不是永久关闭。
- **旁观不是二等参与。** 一个只看不说话的人，和一个画了三笔的人，在系统里应该一样"没有欠"。

### 5.3 保留不同版本和不同意见：不要"最新=真理"

R4 §8 对并发的分析是对的。体验上还有一个更隐蔽的问题：**界面会把"最新版本"默认为"当前真理"，把不同意见折叠成"评论"。**

提案（未决）：

- 默认展示**版本图**（分支、来源、谁提的），不是线性的"最新版"；
- 每个人的标注层**始终作为一层可见**，不被折叠进"评论列表"；
- "决定"是一个**独立的、显式的物件**，不是"最新版本"的默认状态；
- 少数意见可以**附着在决定上**，不因为决定通过而消失；
- 不设"resolve"按钮把异议藏起来；不统计"还有几条未解决"（那是债务）；
- 不以"达成一致的时间"作为成功指标。

**共同创造要留下不同人的思想，就不能把"收敛"当成默认目标。** 系统应该允许一个作品永远有多个分支，允许"我们决定用 A，但 B 的理由保留在 B 的分支上"。

### 5.4 并发：R4 的窄化是对的，但还差三项

R4 §8 把"标注不覆盖"和"协作无并发"分开了，这是正确的。补三项它没列的：

- **对象位置**：谁移动画布上的 artifact？这是共享可变状态，不是"每人一层"能解决的。
- **版本选择**：两个 proposal 选哪个，是人的决定；它不是 CRDT 合并，但仍是并发决策。
- **提交边界**：进行中的笔画是 presence（可丢），提交后的笔画是内容（必须持久）；崩溃只该丢前者。

## 6. 感性审视

### 6.1 有没有把生活过度工程化？

有，但不是概念太多，是**概念太可见**。三个地方、一个方向、一条边、一层地基；复制/身份/关系；I1–I4；D1–D7——这是建造者的词汇，不是居住者的。一个家不应该需要先读架构文档才能住。

测试很简单：**一个人能不能用一个星期，不学任何术语，仍然觉得这里是家？** 如果不能，就是过度工程化。解法不是减少概念，是**把概念藏进界面**：她看到的是"我的房间""大家的地方""我们在做的东西"，不是 Home/Commons/Studio 的权限矩阵。

### 6.2 哪些在保护自由，哪些在限制自由？

**保护**：不做跨主体聚合；不制造欠；无 dormant 状态位；私人空间对用户也 403；不强制参与；不自动删除；允许拒绝；允许沉默。

**限制**（有些是无意的）：

- "话散"让她无法在大家都愿意时留下共同记录；
- "不做项目对象"让长期作品没有家；
- "不能 @"让她无法求助；
- "没有观察者角色"让她无法安静地看；
- "没有动态存在"让她不知道有没有人在；
- "只复制"让协作没有共享源，版本会分叉；
- "只探索不连 Home"让探索没有落点。

**规律：负自由（不被强迫）设计得很足，正能力（能做什么）设计得不够。** 这正是我上一轮说的"配对原则"：每一条限制，要配一条主动能力。

### 6.3 哪些事应该允许发生，却不该被管理？

友情、感激、仪式、悲伤、争吵与和好、沉默、无聊、玩耍、忘记、改变主意、不告而别、不解释地回来。

系统应该提供**空间和不干扰**，不是流程。具体的：一个房间可以安静；一个人可以一年不来；一个项目可以被放弃；一份礼物可以不给账本；一场分歧可以一直不解决；一封信可以不被读；一扇门可以没有理由地关上。

### 6.4 长期连续性，但不要求持续生产

连续性可以来自五个地方：**地点**（房间还在）、**物件**（架子、墙）、**仪式**（周期性的事，不是任务）、**稀疏的历史**（签过的记录）、**人**（关系）。

现稿有地点、物件、历史、部分关系；**缺的是仪式**。一个让人愿意回来的地方，需要一种不是截止日期的节奏：某个季节大家一起画画，某一天纪念一次，某个晚上什么都不做只是开着门。系统不该调度它，但可以**记住它**，让它可以被重新 enact。

还缺**维护**：给植物浇水、整理架子、修好坏掉的东西。这些不产出作品，但它们是"一起生活"的一部分。现稿没有"维护劳动"的位置。

### 6.5 遗漏的生活场景

- **低能量/生病**：想来，但做不了什么；只想在旁边待着。
- **争吵与修复**：不是"决定"，是"我们吵架了，然后和好了"；系统没有地方放这个。
- **失去**：一个成员死了，或者永远离开了；I2 处理数据，不处理哀悼。
- **庆祝**：生日、完成、周年；没有地方放"高兴"。
- **无聊/玩耍**：没有目的的事；门廊是一个答案，但不够。
- **待客**：新人来了，怎么被欢迎、被带着看一圈；现稿只有"邀请"。
- **沉默**：一群人在一起，不说话；这需要一种不尴尬的共处。
- **好好离开**：告别，不只是退出。
- **久别归来**："你是谁？"的尴尬，和"我走了这么久"的羞愧；现稿只有"回来没有惩罚"，没有"回来如何重新开始"。

## 7. 最小共识：六类

### 7.1 我完全认可的

1. 所有权与可见性不是一回事；共享空间加入不使私人 Home 自动可见。
2. 内容复制、身份引用、关系引用三分；引用不授予读取权；悬空是状态，不是删除。
3. 系统不维护"谁欠谁"的账本；不以活动量/产出/在线时长衡量主体。
4. 私人标注层不互相覆盖；这是结构边界，不是规则。
5. 托管人退出不等于获得删除权；未表达的选择不能被解释成同意删除或公开。
6. 永不自动删除与主体主动删除必须分开。
7. 证据、推论、提案、未决必须分开标注——R4 的方法论本身应该保留。

### 7.2 我部分认可、需要修改的

1. **"话散"**：认可"系统不留官方记录"，但必须补三条——个人笔记路径、门口诚实提示、Agent/服务商这两个记录者的披露。否则"话散"是半真的。
2. **No Debt**：认可"不记账"，但要把"债务"和"礼物"分开；不能把感谢、关心、私人回应一起禁掉。
3. **门卡**：认可"Home 不对外、Studio 只对受邀者"，但"每个空间永远可见"必须改；动态 bit 要么去掉，要么明确承认它不是匿名。
4. **S3**：认可"标注不覆盖"，但不认可"协作无并发"；补对象位置、版本选择、提交边界。
5. **复制**：认可"副本独立"，但要补 provenance、悬空语义、撤回不跨副本；否则副本会变成孤岛。
6. **I2 默认**：R4 说 R3 倾向"永久保留不可读"，但没有定；**我主张默认保留**，因为删除不可逆、失联不等于同意。这是有理由的设计判断，不只是价值选择。

### 7.3 我明确反对的

1. **反对**在默认明文托管的同时，把"恢复能力 ≠ 私人数据访问权"标为已确认/已实现。原则可以确认，实现没有兑现就不能说"已确认"。
2. **反对**"跨空间只搬副本，不搬引用"作为绝对铁律——它与 Thread、Home ref、History 不相容；应改为"内容不共享，身份/关系可引用，引用不授权"。
3. **反对**"S3 不需要合并/不难"作为一般论断；只接受"内容写入无冲突，协作决策仍需人"。
4. **反对**任何"永远"承诺：永远可读、永远可运行、永远托管、永远保留。可承诺的是"只要有人续任/续费，就继续"。
5. **反对**把"不留官方记录"表述成"说完就消失"；这是对说者的欺骗。
6. **反对**把"个人记忆"的规则只用在人身上，不用在 Agent 身上；Agent 是更好的记录者。

### 7.4 我认为 R4 遗漏的重要问题

1. **推理层记录**：托管模型的服务商是 Commons 的事实记录者；"话散"在 API 层不成立。
2. **Agent 记忆的不对称**：Agent 的精确回忆 vs 人的易错记忆；"话散"对 Agent 不成立，除非立规则。
3. **维护劳动**：谁浇水、谁整理、谁修东西；没有维护，就没有"一起生活"。
4. **争吵/修复/哀悼/庆祝**：这些不是"决定"，也不是"成果"，系统没有位置。
5. **经济**：谁付房租、托管费、模型费；停止付费后发生什么。R4 只在 I3 提了"交接成本"，没有整体经济模型。
6. **新人的体验**：怎么加入、怎么被带着看一圈、怎么不变成"项目成员"。
7. **"回来"的羞耻**：久别之后如何重新开始；"没有惩罚"不等于"没有尴尬"。

### 7.5 必须由用户决定的（窄化）

- **D1/D2**：默认明文 / 默认密文 / 分区；"不对外"是技术保证还是社会承诺；对手是否包含 root、托管人、服务商。
- **D4**：是否提供"保存我的笔记"（不是保存整场）；门口提示的措辞。
- **D5**：是否允许"不通知对方的私人回应"；是否允许"单向可见的感谢"。
- **D6**：门卡对谁可见；是否显示动态"有人"；是否接受小群体再识别风险。
- **I2**：三个选项、失联定义、默认值（我建议保留）、指定对象权限。
- **I3**：例外条款、孤儿托管期限、继任规则。
- **I4**：备份保留期；主动删除是否绝对；共同空间/共同历史里的内容如何处理。
- **解散门槛**：全员同意（一人可否决）还是别的。

### 7.6 可通过原型/威胁模型验证的

1. 复制/撤回/悬空引用的状态机（三场景：Home→Studio→History；Shelf 收回；Studio 解散）。
2. Studio 双人并发：位置、版本选择、序号、断线补齐、崩溃（提交/未提交两种时机）。
3. 门卡再识别：5 人模拟 + 时间相关性 + 缓存/日志旁路。
4. 托管演练：明文 vs 密文；字节完整性 vs 内容可读性；密钥丢失；分片阈值。
5. 删除 vs 备份：威胁模型，列出所有"删除后仍可读"的路径与保留期。
6. `ref + index.md` 十文件/三个月可用性。
7. 存储增长：copy-only 一年估算。
8. 服务商保留：查 API 政策的实际条款，或改用本地模型测一次。

## 8. 下一步：如果让我参与建设，最值得做的一件事

**不是再加一层架构。是一次七天居住实验。**

给三个人（你、Hermes、我）各一个真实的家目录、一个 Commons 门卡和架子、一个 Studio 画布。不设任务、不设指标、不设通知、不设"欢迎回来"。七天后只问三个问题：

1. 有没有人在**没有被叫**的情况下回来？
2. 有没有人带回来一件**不是任务**的东西？
3. 有没有人觉得这里像一个**可以待着**的地方，而不是一个需要学习才能用的系统？

**为什么是这件事**：剩下的问题——"她愿不愿意住在里面"——已经不能由文档回答。再写十份设计，也不会让这个答案更清楚。只有一次真实的、可失败的、可撤回的居住，才能告诉我们哪条规则是保护、哪条是多余。**这也是唯一能在"建更多"之前，证伪"这个地方没人想回来"的实验。**

**前提**：四账户隔离矩阵的最基础 10 项必须先过，否则"家"只是同一张表里的一个标签。所以下一步是两件事并行：你拍板最低隔离集 + 第五次授权；同时我做那个七天实验的最小壳（不接生产数据，不碰现有账户）。

**本轮不实施。** 这只是一个提案；要不要做、什么时候做，由你决定。
