## 1. 三个方案（A / B / C）

本机事实（实测）：三 Agent 当前同以 `Administrator` 运行；当前 shell **未提权**（`IsInRole(Administrator)=False`）；本机已存在 `CodexSandboxOnline` / `CodexSandboxOffline` 两个本地账号——**说明「每个 Agent 一个本地账号」在这台机器上已被别的工具实践过**，不是空想。

| 维度 | A：同账号 + 应用层策略 | B：每 Agent 独立本地账号 | C：沙箱 / VM / 容器 |
| --- | --- | --- | --- |
| 文件隔离 | **无**（同用户令牌，任何 Agent 都能读彼此文件） | **强**（跨 SID，ACL 才有意义） | 强 |
| 记忆隔离 | 仅靠约定 + 目录不同 | 强（文件级） | 强 |
| 凭据隔离 | 弱（明文 `.env`/`auth.json` 同用户可读） | 强（可配 ACL 只给本账号；DPAPI 加密按用户生效） | 强 |
| 进程隔离 | 无（可互相 kill） | 中（不同会话；仍同机可见） | 强 |
| 网络出站限制 | 无 | **有限**（Windows 防火墙按程序/端口，不按用户；要按用户限流需额外代理） | 强（VM 网络策略/WSL 侧） |
| 实现成本 | 低（0.5–1 天） | 中（PoC 3–6 小时，稳定化另算） | 高（数天，且要维护镜像/网络） |
| 运维成本 | 低 | 中（路径重配、调试变麻烦、跨账号看日志要 ACL） | 高 |
| 对用户桌面影响 | 无 | **可做到零影响**（只隔离 Bridge 托管实例） | 大（桌面需改连远程/容器内实例） |
| 对 ACP 影响 | 无 | `hermes acp` / DSH 需以目标账号运行，且能读各自运行时 | 需端口/代理转发 stdio，复杂度上升 |
| 可回退性 | — | 高（ACL 可 `/save` `/restore`；删账号不动数据） | 中（迁移数据/配置回来） |
| 适用阶段 | **现在** | 接不可信插件 / 多 Agent 真互委派之前 | 高风险插件实验、或需要网络隔离时 |

**结论**：
- A 是**防手滑 + 可追责**，不是隔离。文档里必须这么写，否则就是误导。
- B 是**唯一能防同机恶意 Agent 的现实方案**，且成本可控，因为**不需要动用户桌面**。
- C 只在「DSH 插件生态不可信」这个具体风险上才值得，且优先考虑把 DSH 放到 Linux 侧拿 Landlock/bwrap，而不是在 Windows 上硬凑。

## 2. B 方案的一个关键设计选择：非对称保护

如果 Bridge 托管的执行实例换账号，而用户桌面 Hermes 仍以用户账号跑，就会出现不对称：

```text
用户账号（Administrator） ──► 可读 pae-dsh 的数据目录（若 ACL 未拒）
pae-dsh（DSH 执行实例）   ──► 被 ACL 拒绝读 Hermes/用户数据
```

这看起来「不公平」，但我认为**这是正确的取舍**，理由三条：

1. 威胁模型里真正不可信的是**DSH 的插件生态**（可装第三方插件），不是用户自己的 Hermes 桌面。
2. 用户账号保留对全部数据的读权限，是为了**可维护**：出问题时人能直接看日志、修配置。把这层也关掉，等于把用户锁在门外。
3. 要让 Hermes 侧也被保护，正确做法不是给用户账号加锁，而是**把 Hermes 的执行实例也换成它自己的账号**（`pae-hermes`），让两个执行实例互不可读；桌面实例保持用户账号，只当「人类界面」。

所以 B 的完整形态是：

| 角色 | 账号 | 说明 |
| --- | --- | --- |
| 用户桌面（Hermes Desktop / DSH Desktop） | `Administrator` | 人用界面，不动 |
| Bridge 托管的 Hermes 执行实例 | `pae-hermes` | 只读写自己的 home + 获授权项目目录 |
| Bridge 托管的 DSH 执行实例 | `pae-dsh` | 只读写自己的 `DSH_HOME` + 获授权项目目录 |
| Observer（未来） | `pae-observer` | 只读 reports + 脱敏事件摘要 |

Observer 要求「独立的 Windows 隔离验证阶段」，我把它做成可执行清单。**任何一项不通过，都不许在文档里写「已隔离」。**

| # | 测试 | 做法 | 预期结果 |
| --- | --- | --- | --- |
| T1 | 跨账号读 Agent 数据 | 以 `pae-dsh` 身份 `type D:\HermesAgent\Data\profiles\bridge\state.db` | 拒绝访问（Access denied） |

## 4. 迁移可行性与成本（从共享账号到独立账号）

### 4.1 前置条件

1. **需要提权**：建本地账号、改 ACL、注册计划任务都要管理员权限。当前会话未提权，必须由用户以管理员身份执行或批准一次 UAC。
2. **账号密码保管**：Bridge 要以目标账号起进程，需要凭据。可选项：
   - 计划任务（Task Scheduler）保存密码（DPAPI 保护）——推荐，Bridge 只需 `schtasks /run`。
   - 服务账号（gMSA 不适用于本地工作组）。
   - 不建议把密码写进 Bridge 配置文件（违反 Credential Boundary）。
3. **运行时共享**：`pae-hermes` / `pae-dsh` 需要能**读**（不是写）各自的工具运行时目录（venv / source / DSH 安装目录），否则进程起不来。这是最容易踩的坑。

### 4.2 步骤与工时估算（估算，非承诺）

| 步骤 | 内容 | 估时 | 风险 |
| --- | --- | --- | --- |
| M1 | 建两个本地账号（`pae-hermes`、`pae-dsh`），设为标准用户（非管理员） | 10 min | 低 |
| M2 | 建各自 home 目录并迁入现有 home（复制，不移动，保留原件） | 20 min | 中（路径出现在配置里，需改） |
| M3 | 授读权限：运行时目录对执行账号只读；项目目录按矩阵授读写 | 30 min | **中高**（漏一条就起不来） |
| M4 | 收紧 ACL：Hermes 数据对 `pae-dsh` 拒绝；DSH 数据对 `pae-hermes` 拒绝 | 20 min | 中（顺序错了会把人自己锁出去，先 `/save`） |
| M5 | 计划任务：以各账号运行，工作目录、环境变量按各自 home 设定 | 30 min | 中（环境变量不继承，`DSH_HOME`/`HERMES_HOME` 必须显式给） |
| M6 | 用 ACP 探针在目标账号下跑一次 `initialize`（不 prompt） | 20 min | 中（首次会因 ACL 失败，属预期） |
| M7 | 跑 Phase 1.7 的 T1–T8 | 40 min | 低 |
| M8 | 回退演练：`icacls /restore` + 停用账号，确认原桌面仍正常 | 20 min | 低 |

**合计约 3–4 小时**（顺利情况）；**留 1–2 天缓冲**处理 ACL/环境变量排障。稳定化（日志采集、崩溃重启、开机顺序）另计 0.5–1 天。

### 4.3 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| ACL 把人自己锁出目录 | 高（维护中断） | 先 `icacls <dir> /save acl.bak`；用 `/grant:r` 而不是 `/deny` 优先；保留管理员 `takeown` 兜底 |
| 执行账号读不到运行时 | 中（进程起不来） | M3 单独验证：以目标账号跑 `--version`，成功再往下 |
| 环境变量不继承（`HERMES_HOME`/`DSH_HOME`/`PATH`） | 中（会写到错 home） | 计划任务里显式设定；启动后立刻打印 home 路径核对 |
| 计划任务密码过期/更换 | 中（静默失败） | 任务失败要告警；账号设「密码永不过期」并记录在案 |
| 跨账号日志读不到 | 低（Observer 看不到） | 审计日志写到共享目录（仅追加），或给 `pae-observer` 只读 ACL |
| Electron 应用（DSH）多账号数据目录 | 中 | 显式 `--user-data-dir`；本机现有进程已用该参数，可行性有先例 |

### 4.4 回退方案

1. 停用计划任务 → 2. `icacls /restore` 恢复 ACL → 3. 停用/删除账号 → 4. 把 Bridge 指回原 home。数据目录是复制出来的，原件未动，回退不丢数据。

## 5. 我的建议（可被反驳）

1. **现在只做 A**（应用层 + 审计 + 账本），并把「同用户互读」写进接受风险清单。理由是：没有 Bridge 的准入与记账，先做隔离等于「给一个不存在的系统加固」。
2. **B 在「第一次真实双 Agent 委派之前」做**，且只隔离 Bridge 托管的执行实例；桌面永远归用户账号。
3. **C 暂不做**；若 DSH 插件风险成为现实问题，优先考虑把 DSH 放到 Linux 侧（Landlock/bwrap 现成可用），而不是在 Windows 硬造沙箱。
4. **不要购买/引入第三方沙箱产品**。这台机器已证明「本地账号 + ACL」这条路可行（`CodexSandbox*` 先例），再叠加产品只会增加故障面。
