## Q1：派生记忆的删除权限与主体边界

### 1.1 先把对象分类（不分清就没法定权限）

| 类 | 定义 | 例子 |
| --- | --- | --- |
| **PRIVATE(A)** | 只有 A 与用户可见 | A 的私人笔记、A 与用户的对话 |
| **SHARED** | A 授权进入共享池的内容（可撤回） | A 总结的项目经验 |
| **JOINT** | 多参与者共同产生，谁都不是唯一所有者 | Lounge 对话、共同创作、Project Room 讨论 |
| **SYSTEM** | 审计、删除记录、决策史 | 谁在何时删了什么 |

**为什么必须分出 JOINT**：Project Room 的讨论既不属于 Hermes 也不属于 DSH，它是"共同经历"。用 private/shared 二分法处理它，一定会出现"某一方把自己的发言删了，整段讨论就断了"。

### 1.2 主体 × 对象 × 操作（权限模型）

| 主体 | PRIVATE(A) | SHARED | JOINT | SYSTEM |
| --- | --- | --- | --- | --- |
| 用户 | **读/删（终决）** | 读/删 | 读/删（裁决） | 读（审计留痕） |
| A（所有者） | 读/写/删 | 读/**撤回** | 读/写自己的部分/**撤回自己的可见性** | 只读 |
| 其他 Agent B | **无** | 读（若授权） | 读（若参与）/写 | 只读 |
| Observer | 只读摘要（需授权） | 只读 | 只读 | 只读 |

三条硬规则：

1. **用户对 PRIVATE(A) 有终决权**，包括要求 A 删除其派生信息。**Agent 没有否决权**——它可以要求澄清范围（"是指整段对话还是其中一句"），但不能以"这是我的记忆"为由拖延或拒绝。
2. **B 对 PRIVATE(A) 无任何权限**，连"我有没有被提到"都只能通过受控索引查询（返回"是/否"而不返回内容）。
3. **任何主体都不能单方删除 JOINT 整条**——只能撤回自己那部分。

### 1.3 逐条回答五个子问题

**① 用户要求删除自己的私人内容，Agent 能否自行保留派生信息？**

**不能。** 派生记录若可溯源到被删内容，默认 `retrieval_blocked=true`。
唯一例外：该信息**独立地**来自用户已确认的共享来源。此时允许"重建"，但必须是**新记录**（见 ③），且原记录仍 blocked。

**② 多来源派生，删掉一个来源后怎么验证剩余来源够不够？**

自动化只能做到"发现"，做不到"判断"。机制：

```
record.support_set = [ {event_id, supports: ["claim_part_1","claim_part_2"]} ]
```

删除后：
1. 从 `support_set` 移除被删 id；
2. 若 `support_set` 非空 → 标 `needs_revalidation`；
3. **重新提取**（re-extraction）：用剩余来源重跑提取器，产出**新记录**；
4. 新旧对比：若新记录仍覆盖原 `claim` 的语义 → 新记录生效，旧记录保留但 blocked；若不能覆盖 → 该 claim 标 `unsupported`。

**为什么不能直接判定"够不够"**：语义支持关系不是图上的可达性，只有重跑一遍提取才知道。所以设计上把它做成"重新生成 + 对比"，而不是"逻辑推理"。

**③ 去敏重建后的记录是否必须新记录、并标记断链？**

**必须。** 新记录字段：

```json
{"rec_id":"…","provenance":"derived","rebuilt_after_deletion":true,
 "lineage_broken":true,"redacted":["person:name","location:city"],
 "derived_from":["<剩余来源>"], "supersedes":"<旧记录>"}
```

旧记录不删（它是"当时为什么这么想"的证据），只是不可检索。

**④ 私人 / 共享 / 共同经历是否不同规则？**

| 类 | 删除 | 撤回 | 说明 |
| --- | --- | --- | --- |
| PRIVATE | 可删（owner 或用户） | — | 密钥销毁 |
| SHARED | owner 可**撤回授权**，不删库 | ✅ | **撤回 ≠ 抹除他人已合法获得的副本**（见下） |
| JOINT | 需全体或用户裁决 | 单方可撤自己可见性 | 撤回后记录标 `partially_withdrawn` |

**关于"撤回共享后别人的副本"**：现实类比是"你告诉我一件事，我记住了"。我们能做的是：
- 共享池里的条目移除；
- 其他 Agent 的**下游派生**被标记并阻断（因为来源已撤回）；
- 但对方**已经形成的私人理解**不强制删除（那是它自己的记忆）。

这条必须在产品语言里说清楚，否则"撤回"会被理解成"物理销毁所有副本"，做不到。

**⑤ 参与者意见不一致怎么办？**

**不阻塞，记录分歧，交用户裁决。**

- 记录加 `dispute: [{by, at, reason, stance}]`；
- 争议期间**默认维持现状**（不删），因为删除不可逆；
- 用户裁决后写 `resolution: {by: user, at, decision}`；
- **分歧本身保留**——它与项目其他决策一样是资产。

### 1.4 我不同意提案的一点（要说明）

提案说"Agent 不应以保护自身记忆为由绕过用户删除要求"，我完全同意。但要补一条对偶的约束，否则会失衡：

> **用户也不能以"生态需要"为由，单方面决定某个 Agent 必须忘记它自己的经历。**

区别在于：用户对其**自身内容**有终决权；但一条 JOINT 记录里 Agent 的那部分视角，属于该 Agent。用户裁决 JOINT 争议时，应该有义务看到"这会让某一方失去什么"，而不是只按效率决定。

## Q2：删除验收的可靠性（七个层面 + 四态）

**Observer 说得对：`grep` 只是其中一层。** 拆成七项检查，每项有独立的成功条件与不可验证边界。

| ID | 检查 | 方法 | 成功条件 | **无法验证的边界** |
| --- | --- | --- | --- | --- |
| K1 | 密钥销毁 | 查 key store；尝试解密该 `rec_id` | 解密失败，且错误类型是 `KEY_NOT_FOUND`（不是 `CORRUPT`） | 内存中的密钥副本；keystore 自身的备份 |
| K2 | 可解密副本 | 枚举所有持密钥的副本（keystore 备份、导出包、恢复演练目录） | 全部不含该 key id | 用户手动导出的包 |
| K3 | 派生阻断 | 对派生闭包逐条查 `retrieval_blocked`；跑一次该主题检索 | 0 条可检索命中 | **语义等价但措辞不同**的记录（无法穷举） |
| K4 | 全文索引 | `secure_delete` + `VACUUM` 后对 DB/WAL 文件做字节级扫描 | 0 命中 | 文件系统快照；SSD 磨损均衡层的旧块 |
| K5 | Embedding | 删行 + 重建索引段；再跑一次相似检索 | 不返回该 `rec_id`；索引文件内无该向量 | ANN 内部图结构残留（**不 rebuild 就不干净**）；服务商缓存 |
| K6 | 备份 | 用残留密钥尝试解密备份 | 解密失败 | 离线/异地备份未接入时无法验证 |
| K7 | 外部系统 | Agent 会话库、ACP transcript、Bridge 日志 | 清单逐项人工确认 | **模型服务商日志：不可验证** |

### 2.1 四态（不能因为 API 返回成功就宣称消失）

```
DELETE REQUESTED   ← 请求者发起，记录范围与理由
      ↓（执行 K1–K5）
DELETE EXECUTED    ← 执行器完成自己管得到的部分
      ↓（执行 K6–K7 + 独立验证）
DELETE VERIFIED    ← 全部通过，且由**独立验证者**签发
  或  DELETE PARTIAL      ← 部分通过（例：K1–K5 过，K6 未接入）
  或  EXTERNAL RESIDUE    ← 确认外部仍有副本（例：服务商日志）
```

**关键设计：执行者不能自己宣布 VERIFIED。**

- 删除执行器只写到 `EXECUTED`；
- `VERIFIED` 必须由**另一个主体**签发：用户侧工具，或 Observer 的独立验证；
- 理由与审计链一样：自己给自己发合格证没有意义。

### 2.2 验收记录长什么样

```json
{"del_id":"…","rec_ids":[…],"state":"DELETE PARTIAL",
 "checks":{"K1":"PASS","K2":"PASS","K3":"PASS(blocked=7)",
           "K4":"PASS","K5":"SKIPPED(no-embeddings)","K6":"NOT_WIRED","K7":"MANUAL_REQUIRED"},
 "verifier":"user-tool@2026-11-09","residual_hits":0,"notes":"…"}
```

规则：**任何一项 NOT_WIRED / MANUAL_REQUIRED，最终状态就不能是 VERIFIED。** 不许"大部分过了就算过"。

## Q3：完整性哈希链的整体重写风险

**Observer 的判断成立**：`H(prev ‖ ciphertext ‖ meta)` 只能防"不知道算法/没有写权限"的人。有写权限者可以整链重算，链自洽如初。

### 3.1 三种手段的必要性

| 手段 | 防住什么 | 防不住什么 | 成本 |
| --- | --- | --- | --- |
| **签名检查点**（Anchor 用自己的私钥签 `(seq,hash,ts)`） | 重写链必须同时偷签名密钥 | 拿到签名密钥的一切攻击 | 签名本身便宜（~几十 µs/次）；**成本在密钥管理**（生成、存放、轮换、备份、丢失=永久无法验证） |
| **独立保存的检查点摘要**（写到不同主体/介质/甚至纸质打印） | 本地整库被毁后仍有旁证 | 两边同时被改 | 低（定期导出 + 手工归档） |
| **交叉验证**（Observer 定期拉取检查点独立比对） | 单人作弊 | Observer 与攻击者共谋 | 低（只读） |

### 3.2 我的判断：对记忆，签名不是最优先

- 对**审计**（安全追责）→ 签名值得做，因为"篡改审计"本身就是攻击目标；
- 对**记忆**（理解与经历）→ 篡改的危害低一档，而且记忆量大、写入频繁；
- 所以建议：**记忆层先做"外部检查点 + Observer 交叉验证"，签名后置到有明确需求时**。

### 3.3 必须先承认的边界

> 拥有管理员权限的一方可以**替换验证工具本身**。任何本地验证方案都只能"提高门槛 + 提高可发现性"，不能"阻止"。

所以文档口径固定为：**可检测、可归责，不可阻止**。

## Q4：冷存储的长期可恢复性（HMR）

**Historical Memory Recoverability** —— 我认为这个指标比"文件存在"有意义得多，接受并细化。

### 4.1 抽样设计（分层随机，不是随便抓）

| 维度 | 分层 |
| --- | --- |
| 年份 | 每个自然年一层 |
| 项目 | 每个项目一层 |
| 存储层 | hot / warm / cold |
| 记录类型 | raw / derived / decision |
| 可见性 | private / shared |

每月每层抽 N=20；**每季度做一次全层覆盖**（确保没有层被长期漏掉）。

### 4.2 每条的五个检查项（Observer 列的）

| 项 | 怎么测 | 判据 |
| --- | --- | --- |
| 内容可恢复 | 在**干净目录**里用备份 + 密钥恢复单条 | 字节级与哈希一致 |
| 来源关系 | 沿 `derived_from` 走到 raw | 链完整，或断链有明确标记 |
| 派生追溯 | 从 raw 查所有下游 | 数量与索引记录一致 |
| 权限边界 | 用**无权账号**尝试读 | 被拒（10） |
| 密钥可用 | 解密测试 | 成功；失败即计入不可恢复 |

**"干净目录恢复"是关键**：只在原库里测，测的是"文件还在"，不是"未来还能找回来"。

### 4.3 指标与阈值

```
HMR = 通过项 / 采样项总数（分维度报告，不报单一总分）
≥0.99 正常 ｜ 0.95–0.99 告警 ｜ <0.95 冻结归档/压缩等破坏性操作
```

**阈值触发动作要写死**：低于 0.95 时**不允许**继续"清理 cold"，因为那时最可能是"数据已经捞不出来了，而你还在想删更多"。

### 4.4 长期漂移防护

- 抽样记录保存 3 年，用于追踪"某条记录从哪一年开始不可恢复"；
- 每次换存储格式/压缩算法，**先对历史抽样集跑一遍**，再决定是否迁移；
- 密钥轮换后必须复测（这是最容易忘的一步）。

## 5. 本轮新增的设计增量

| 增量 | 内容 |
| --- | --- |
| 对象四分类 | PRIVATE / SHARED / JOINT / SYSTEM，各自权限不同 |
| 主体权限矩阵 | 用户终决 / owner 自决 / 其他 Agent 无权限 / Observer 只读 |
| 多来源重建 | `support_set` + 重新提取 + 新记录（不原地改） |

| HMR 指标 | 分层抽样 + 五项检查 + 阈值触发冻结 |
