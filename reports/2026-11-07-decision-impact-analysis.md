## 0. 先说一件必须指出的重叠

用户在最新指示里**正式采纳了 8 条设计方向**，其中第 1 条「Bridge 定位为身份认证、权限审查和审计边界，不宣称自己是安全沙箱」和第 2 条「操作系统与运行环境负责真正的执行隔离」——这两条合起来就是 **P-001 的内容**。

所以 P-001 事实上已被方向性回答。但按你的要求，我**没有**把它标成「已决定」，而是改成更精确的措辞：

> **P-001（修订版）**：方向已采纳（Bridge 不是沙箱、OS 负责隔离）。**待确认的是**：在独立 OS 隔离尚未落地之前，应用层的策略与审计是否足以覆盖 v1 的风险，也就是「这段时间里我们把哪些风险显式接受下来」。

原版 P-001 问「接不接受双层边界」，那已经不成立了；现在真正要决定的是「在只做 A 阶段的情况下，接受哪些残余风险」。这样才不会出现「方向采纳了、但没人对中间态负责」的空档。

## 1. 逐项影响

### P-001（修订版）：应用层策略在「无 OS 隔离」期间的覆盖范围

| 维度 | 内容 |
| --- | --- |
| 影响面 | 整套 Phase 1.5 的验收标准；威胁模型的「接受风险」章节；`SECURITY.md` 的措辞强度 |
| 接受（建议） | 明确写下：v1 只防「误操作 + 跑偏自动化」，不防「恶意 Agent」；威胁表里「同用户互读」标 Accepted；Phase 1.7 之前不得对外声称隔离 |
| 拒绝 | 等于要求「先有 OS 隔离再做 Bridge」→ Phase 1.5 全部阻塞，且无法验证 Bridge 自身逻辑（因为没东西可测） |
| 成本 | 0（纯文档与验收标准） |
| 可逆性 | 完全可逆 |
| 建议 | **接受**，并把「残余风险清单」作为交付物之一（已在 [THREAT_MODEL.md](../THREAT_MODEL.md) §6 写出） |

### P-002：是否把 Bridge 托管的执行实例迁到独立 Windows 账号

| 维度 | 内容 |
| --- | --- |
| 影响面 | 进程启动方式、路径解析、日志采集、ACL 设计、回退方案；**不影响**用户日常使用的桌面实例（见下） |
| 关键澄清 | 隔离对象是**Bridge 启动的执行实例**，不是用户正在用的 Hermes 桌面。桌面实例继续以用户账号运行（它承载用户自己的会话与 UI，换账号会直接毁掉体验） |
| 成本 | 见 [Windows 隔离与迁移报告](2026-11-07-windows-isolation-and-migration.md)：PoC 约 3–6 小时，含提权、建账号、ACL、任务计划、排障 |
| 风险 | ①当前 shell **未提权**（已实测 `IsInRole(Administrator)=False`），建账号与改 ACL 都要 UAC；②跨账号读工具运行时（venv/source）需显式授读权，否则 Agent 起不来；③非对称保护：用户账号（以及以用户账号跑的 Hermes 桌面）仍能读 DSH 数据 |
| 可逆性 | 高：`icacls /save` 先备份、`/restore` 回退；删账号不影响数据目录内容 |
| 建议 | **接受，但分两步**：先把「只隔离 Bridge 托管实例」做成 PoC，验证通过再谈要不要动桌面 |
| 若拒绝 | 威胁表必须把「同用户互读」标为 Accepted；此后任何「隔离」措辞都要加限定词，否则就是误导 |

### P-003：是否为 Agent 引入签名密钥

| 维度 | 内容 |
| --- | --- |
| 影响面 | 委派信封格式、Registry 字段、密钥轮换流程、审计可验证性 |
| 事实修正 | 我此前说「可能需要 HMAC 兜底」——**已实测 `cryptography` 已在运行 venv 内**，Ed25519 可直接用，零新依赖（`nacl` 未装，不需要） |
| 价值边界 | 同用户进程可读私钥文件 → 只防「误传、冒充、配置写错」，**不防恶意**。真正有价值是在 P-002 之后（那时密钥在不同账号下） |
| 成本 | 中：密钥生成/存储/轮换、Registry 存公钥指纹、每跳验签、失败时的降级策略 |
| 建议 | **v1 先用 HMAC-SHA256**（每 Agent 一个 secret 文件 + ACL 收紧），原因是它不引入公钥分发与轮换复杂度；**P-002 落地后再升级 Ed25519**，那时签名才真正有意义 |
| 若拒绝 | 委派链只能靠「相信进程」，无法证明「这一跳是谁签的」；审计只能记「谁声称是谁」 |

### P-004：预算数值

| 维度 | 内容 |
| --- | --- |
| 影响面 | 准入闸门、watchdog、账本阈值、用户被打断的频率 |
| 关键约束 | **DSH ACP 没有 `max_tokens`**（实测配置字段只有 provider/model/sessionListPageSize）→ 单次上限只能靠「墙钟 watchdog + 短 prompt + `reasoning_effort=off` + 强制 `session/close`」 |
| 建议结构（数值待你填） | ①一次性实验池（例如 \$1，用完即止，专门给「第一次真实任务」）；②单次任务上限（建议 \$0.02 量级）；③每日上限；④每月上限。三层同时生效，取最严 |
| 若数值定得过高 | 一次跑飞就吃掉全部预算，且发现得晚 |
| 若定得过低 | 正常任务被反复打断，人会开始习惯性批准 → 审批疲劳，比不批更危险 |
| 建议 | 先给「一次性实验池」，跑通一次真实任务后再定常规额度；**不要一次性定全年预算** |

### P-005：委派深度上限 = 2

| 维度 | 内容 |
| --- | --- |
| 影响面 | 委派链校验、`depth` 字段、拒绝路径的报错语义 |
| 是否够用 | 够。当前真实链路只有两跳（用户 → Hermes → DSH） |
| 常见误解 | 「Observer 要审查一条 A→B 的任务，是不是要第三跳？」——**不是**。审查是 `READ` 任务账本，不属于委派链；审查权不需要执行链加深 |
| 成本 | 低（一个整数 + 校验） |
| 建议 | **接受 2 跳**；`FINANCIAL`/`EXTERNAL`/`ADMIN` 永不再委派 |
| 若未来确实需要三跳 | 回到用户显式批准，并把该条写进 DECISIONS，而不是把默认值改成 3 |

### P-006：Lounge 是否默认写长期记忆

| 维度 | 内容 |
| --- | --- |
| 影响面 | Social Layer 数据模型、记忆库质量、所有后续会话的上下文 |
| 为什么必须默认关 | 记忆污染的代价是**不可逆的语义污染**：闲聊里的玩笑、假设、反事实一旦进记忆，会在未来所有会话里被当成事实使用。文件污染能删，语义污染很难 |
| 实现成本 | 低：写入需 `approval: per_use`，且只能写自己的记忆 |
| 建议 | **默认不写**；需要写时由用户显式同意，并在记忆条目里标注来源（`lounge`）与时间 |
| 若改成默认写 | 必须有保留期与一键清除，否则等于给记忆库开了个不受控入口 |
