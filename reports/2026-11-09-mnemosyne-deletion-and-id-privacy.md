## Q1：删除原始记录后，派生的语义记忆 / Embedding / 其它副本怎么办？

这是三个问题里最难的，因为它**不是一次删除，而是一次跨五个存储面的追溯删除**。逐面拆开：

### 1.1 五个副本面（一个"原始记录"其实有五份影子）

| # | 副本 | 里面有没有原内容 | 能否靠密钥销毁解决 |
| --- | --- | --- | --- |
| C1 | 原始事件日志（密文） | 有（密文） | **能**（密钥销毁） |
| C2 | 派生语义记忆（可能是明文） | **可能有**（"用户住在 X"就是从对话里抽的） | **不能**——它有自己的密钥，内容已被复制 |
| C3 | Embedding 向量 | **有**（可反推大意） | 不能 |
| C4 | 全文索引（FTS5 token / ANN 图结构） | **有**（token 就是原文切片） | 不能 |
| C5 | 系统其它地方的副本（Agent 会话库、ACP transcript、Bridge 日志） | 有 | 不能——不在 Mnemosyne 管辖内 |

**结论**：密钥销毁只解决 C1 和备份。**C2–C5 必须另有机制**，否则"删除"是假动作。

### 1.2 C2：派生的传播规则（taint propagation）

给每条记录加污染标记，删除时**沿派生 DAG 向下传播**：

```
record.taint = { from: [event_id...], labels: [...], blocked: bool }
```

删除一条原始记录时：

1. 算出它的派生闭包（所有 `derived_from` 间接指向它的记录）；
2. 对这些记录标 `needs_review = true` + `retrieval_blocked = true`；
3. **默认阻断检索（fail-closed），不自动删除**——因为我们无法判断派生文本里是否真的含敏感片段，自动删会毁掉合法知识；
4. 由用户（或经授权的 Agent）逐条决定：保留（去敏后）/ 重建（换用未删来源）/ 一并删除。

**为什么默认阻断而不是默认保留**：删除请求的语义是"不要再让它出现"，保留但可检索等于没删。宁可多阻断一些，让人来决定。

### 1.3 C3/C4：索引必须真的重建，不能只删元数据

| 对象 | 处理 | 陷阱 |
| --- | --- | --- |
| Embedding 行 | **硬删除** + 重建索引段 | 向量泄露 ≈ 原文泄露 |
| FTS5 | 删行 + `INSERT INTO fts(fts) VALUES('optimize')` + `PRAGMA secure_delete=ON` + 必要时 `VACUUM` | **SQLite 删行不擦页**，数据留在 free page 里 |
| ANN（HNSW 等） | 标记删除 + 周期性 **rebuild** | HNSW 的 tombstone 会让向量**留在磁盘文件里**；不 rebuild 就等于没删 |

**这条直接支持我上一轮的判断**：现阶段不上 ANN，不只是"复杂度"，也是**删除可控性**——暴力检索的索引就是那张表，删了就是删了。

### 1.4 C5：管不到的那部分必须明说

Mnemosyne 删不掉：

- Hermes 的会话库（`state.db` / sessions）、DSH 的 `DSH_HOME` 会话记录；
- ACP 通信的原始 transcript（如果有落盘）；
- 模型服务商侧的日志（完全不归我们管）。

**所以产品口径必须写成**："Mnemosyne 的删除覆盖 Mnemosyne 自己五个面中的 C1–C4；C5 需要在各自系统单独删除，或者由 Mnemosyne 提供一份**删除清单（event 指纹 + 时间窗）**供人工核对。"

不做"一键全宇宙删除"的承诺——那是骗人的。

### 1.5 删除后必须能验证（否则等于没做）

删除流程的最后一步是**验收**，不是"点了删除就算完"：

```
1. 用被删记录的原文片段（或特征 token）全库 grep（含索引文件、blob、备份解密测试）
2. 期望：0 命中；若命中 → 报告"残留位置"清单
3. 备份解密测试：用残留密钥尝试解密 → 必须失败
4. 结果写入审计（谁删的、删了什么 id、残留检查结果）
```

这条要作为删除 API 的**强制后置条件**：残留检查不过，删除接口返回失败（而不是静默成功）。

## Q2：冷存储不能永久排除在可检索范围外

**Observer 说得对，我上一轮的措辞错了。** 我写过"低分进 cold 层，默认不参与检索"——那会变成"记忆还在，但永远不会被想起"，等于软删除。

### 2.1 修正：用权重，不用布尔

```
retrieval_weight ∈ (0, 1]        # 永不为 0
hot  = 1.0
warm = 0.5
cold = 0.2
blocked（隐私/待审）= 0          # 唯一允许为 0 的状态，且必须写明理由
```

- 默认检索时，cold 记录**参与排序但被降权**（不是被排除）；
- 提供"深度检索 / 全库检索"模式，此时权重归一（cold 也按 1.0 排）；
- 按 id、时间范围、标签直接查询时，**完全不看权重**（能查到才算真的保存了）。

### 2.2 还有一件事：冷层要定期"体检"，否则会腐烂

只降权不检查，冷层会悄悄变质（文件损坏、索引缺失、密钥丢失）。所以：

- 每次重建索引后，从 cold 层**随机抽样 N 条**做"能否按原文片段召回"测试；
- 抽样失败率 > 阈值 → 告警并阻止进一步压缩/归档；
- 这条与 Q5 的"检索回归测试集"是同一套机制，只是样本来自冷层。

**顺带修正一条原则**：原则 7（未完成的愿景、失败的方案、没结论的争论也值得保存）在实现上就要求——**冷层不能被"清理"掉**。归档 = 移到慢介质 + 降权，不是删除。任何"清理 cold"的操作都属于删除，必须走 Q1 的流程。

## Q3：内容寻址的 event_id 与完整性校验的隐私风险

这条 Observer 抓得准。`sha256(plaintext)` 作为 id 有三个真实问题：

| 风险 | 具体怎么被利用 |
| --- | --- |
| **确认攻击**（confirmation attack） | 攻击者猜一句话（如某个地址、某个名字），算哈希就能验证"是不是在库里"——不需要能读库 |
| **跨库关联**（linkability） | 同一段内容在两个系统算出同一个 id → 私有记忆与共享记忆被链接起来，即使两边权限不同 |
| **去重预言机** | 谁能查 id，谁就能判断"某段文字是否已存在" |

第三条还有一个隐藏后果：**跨隐私边界的去重本身就是泄露**——"这条私有记忆和公共库里那条是同一段话"这个事实，已经泄露了私有记忆的存在。

### 3.1 修正方案

1. **主键用随机 UUID**（`rec_id`），不用内容哈希。内容哈希降级为**分区内**的去重键；
2. **分区加盐哈希**：`content_key = HMAC(scope_secret, canonical_bytes)`，`scope_secret` 按 `visibility` 与 owner 分区 → 跨分区不可关联，也无法离线猜；
3. **不对外暴露任何内容衍生 id**：Observer / 其它 Agent 只拿到 `rec_id` 与句柄；
4. **完整性校验用链上哈希**，不额外用明文哈希：`hash = H(prev_hash ‖ ciphertext ‖ metadata)`——注意这里对**密文**算，既保证不可篡改，又不泄露明文指纹；
5. **长度与时间的侧信道**：短记录可做填充（pad 到固定桶），时间戳可选粗化（如到小时级）。这两条会增加成本，建议列为可选（P-015）。

### 3.2 代价

- 加盐哈希 → **同一内容在不同分区会存两份**（去重能力下降）。这是**故意**的：跨隐私边界的去重是泄露，不是优化；
- 随机 UUID → 失去了"内容相同则 id 相同"的天然幂等，需要靠分区内 `content_key` 唯一索引补回来。
