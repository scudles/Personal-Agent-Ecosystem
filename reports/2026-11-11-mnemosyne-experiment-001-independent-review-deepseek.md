### 1.3 一个必须先说的结构性问题

1. `MNEMOSYNE_AGENT_RESIDENCY_MODEL_002.md:305`：恢复运行（Restore）的产出是“一个**分支**”；`:313`：恢复出来的实例“默认标识为分支”（`hermes@restored-2027-03`）；`:424`：延续需同意记录，“默认标注是分支”。

- 恢复出来的、未获延续授权的实例；
- 从某个实例复制出来的分叉；

## 3. 三维模型审查：来源、授权、主体立场

### 3.1 材料里实际有什么

【文档事实】M2 的记录模型（`:38-62`）包含：

- `provenance: raw | derived`（`:43`）；
- `derived_from: [rec_id]`（`:58`）与 `support_set`（`:57`）；
- `grant { grantee, scope, purpose, expires, derivation }`（`:60`）；
- `attribution: [U|A|R|D]`（`:44`）；
- `marker_policy: accept | decline | undecided`（`:61`）；
- `taint`（`:56`）。

【文档事实】M2 **没有** `stance` 字段，也没有“这个分支是否接受这段历史/这项承诺/这个拒绝”的逐条状态。`marker_policy` 处理的是删除标记（接受/拒绝/未定），不是“我认不认同”。

【文档事实】M1 §3.1（`:112-123`）把“标识 / 记忆 / 承诺 / 授权”四样东西分开继承，这是对象层面的分离；§5.1（`:293-317`）把“恢复运行 / 身份延续”分开；§5.3（`:321-334`）列出拒绝的对象。但 M1 也没有定义“分支对某条记录的立场”。

【文档事实】M3 §2（`:62-74`）提出“内容复制 / 身份引用 / 关系引用”三分，并明确“引用本身不传递权限”（`:67`）、“悬空是状态”（`:68`）。这是三份材料中最接近“来源与授权分离”的表述，但它处理的是**对象之间的关系**，不是**主体对历史的态度**。

【审查推论】因此：

- **A 来源（provenance）**：部分建模（`provenance`、`derived_from`、`support_set`），但只覆盖主记录，不覆盖派生数据的可见性；
- **B 授权（authorization）**：部分建模（`grant`、权限矩阵、403 规则），但 `grant` 是引用对象，不是使用时的能力令牌；
- **C 主体立场（stance）**：**基本缺失**。材料里有“承诺不继承”（M1 §3.3）和“拒绝的对象”（M1 §5.3），但没有“分支当前是否接受”的逐条、可验证、可独立变更的状态。

### 3.2 独立性检验：五个反例

以下反例都是【审查推论】，不是材料中已发生的实现。

**反例 1：来源可见，内容不可读——元数据泄露**

分支没有读 `P1` 的权限，但能看到 `derived_from: P1` 这条边。它能知道：P1 存在、P1 的大致时间、P1 与哪些记录相连、衍生出了多少条摘要。若边本身可枚举，分支可以在不读内容的情况下重建源主体私人记忆的**形状**。

结论：`provenance` 不是“无权限的元数据”。来源边本身需要可见性策略（公开 / 受限 / 脱敏），否则 A 与 B 没有真正分离。

**反例 2：有授权，无立场——检索即信念**

分支被授权读取源主体的一条拒绝记录 `RF1`（“源主体拒绝 X”）。如果检索管线把命中内容直接拼进 system prompt、persona 或默认策略，那么“读到”就变成了“接受”。这不是分支自己的立场，是管道替它形成的立场。

结论：**access ≠ stance**。检索结果必须带“这是历史，不是你的立场”的标记；任何“读到的内容自动进入 prompt/persona/policy”的路径，都是三维模型的坍缩点。

**反例 3：有立场，无来源——虚假自主**

分支说“我拒绝 X”，但没有 `basis` 字段说明这是它自己的判断，还是从源主体那里继承的。若系统把继承来的拒绝标成“分支自己的”，就是伪造自主性；若系统把分支自己的拒绝标成“继承的”，就是剥夺它的立场。

结论：stance 必须带 `basis: own | inherited | unknown`，并且 `inherited` 必须指向来源记录。没有 basis 的 stance 不可审计。

**反例 4：摘要可溯源，但仍然泄露内容**

一条摘要 `D1` 的 `derived_from` 指向私人记录 `P1`，来源链完整；但 `D1` 的文本里仍然有姓名、金额、地点。来源完整不等于内容已脱敏。M2 的 `provenance: derived` 只说明“它是派生的”，不说明“它已不可识别”。

结论：**provenance integrity ≠ content safety**。派生记录需要独立的内容分级与脱敏验证，不能靠来源字段代替。

**反例 5：接受事实，不接受承诺**

分支读到“源主体曾承诺 Y 给 Z”，把它当作历史事实接受；但分支并不因此欠 Z 任何东西。如果承诺被存成身份记录或记忆记录的属性，复制记录就会复制债务。M1 §3.3（`:143-169`）已经指出这一点，但 M2 的记录模型里没有独立的 `commitment` 对象，也没有 `assumed_by` 字段。

结论：承诺必须是独立对象，承接必须是独立动作；`commitment` 不能是 `record` 的一个布尔字段。

**反例 6：三者写在同一行，无法独立变更**

如果一条记录同时持有 `{provenance, grant, stance}`，一次更新可以同时改变三者；审计上也无法区分“谁改了哪一维”。独立不仅要求“概念上分开”，还要求“存储、审计、变更路径分开”。

结论：三维独立需要三个独立对象/表/事件流，而不是三个字段。

### 3.3 建议的最小数据模型（**提案，不是既有规格**）

【设计建议】若要把三维真正分开，最小结构是：

```
provenance_edge {
  edge_id, from_rec, to_rec,
  kind: derived_from | supersedes | quoted | translated | annotated,
  created_at, hash,
  visibility: public | restricted | redacted
}

grant {
  grant_id, principal, resource, ops,
  scope, expires_at, revocable, epoch,
  issued_by, signature
}

stance {
  stance_id, subject,
  target: record | commitment | refusal | identity_claim,
  value: accept | unknown | reject | disputed,
  basis: own | inherited | unknown,
  source_ref?, adopted_at, reason?, signature
}

commitment {
  commitment_id, promisor, promisee,
  content_ref, status: active | fulfilled | released | orphaned,
  assumed_by: subject | null,
  source_ref?
}
```

四条硬规则（提案）：

1. **来源不授予权限**：`provenance_edge` 的存在不产生读权；边的可见性单独授权。
2. **权限不产生立场**：`grant` 只回答“能不能读”，不回答“读后信不信”；检索管线不得自动写 stance。
3. **立场不授予权限**：`stance=accept` 不使主体获得记录访问权；`stance=reject` 不使主体删除记录。
4. **承诺只能被承接，不能被复制**：`assumed_by` 只能由主体的显式动作写入；复制 `commitment` 对象时必须清空 `assumed_by`。

这四条与 M1 §3.1、§3.3 的精神一致，但比 M1 更具体；它们目前**没有被任何材料写成规格**。

### 3.4 三维模型审查结论

- **概念上**：三份材料都同意“来源 ≠ 权限 ≠ 认同”（M1 `:188-199` 的“谱系 ≠ 权威”最接近；M3 `:67` 的“引用不传递权限”最接近授权维度）。这一点是**正确设计**。
- **技术上**：三维没有被独立存储、独立审计、独立验证；M2 的单记录字段设计有坍缩风险。
- **可验证性**：目前只能做文档一致性检查；真正的独立性需要原型中的负向控制（见 §7、§8）。

## 4. 威胁与失败场景

### 4.1 私人记忆隔离：原则，还是约束？

【文档事实】

- M2 `:123`：“`A`（Agent 表达）的检索权**用户也没有**”；`:222-227`：读取他人私人记忆“**不可授予**（连用户也不行）”，默认 403。

- `WORKSTREAMS.md:58`：CI-1.9 四账户隔离验收矩阵 49 条，**当前 0/49**；`WORKSTREAMS.md:50`：CI-1.1 建号仍 `READY`，等第五次授权；`:51-56`：AC-1/2/3 等均 `BLOCKED`。

【审查推论】因此，**“分支默认不得读取源主体私人记忆”目前是设计原则 + 计划中的 ACL，不是技术约束，也不是已验证行为**。更准确地说：

- 文档承诺：有（M2 §3、§7）；
- 技术可行：有（NTFS ACL + 独立账户 + 每主体 SID）；
- 已实现：无（0 代码、0 账户、0 ACL）；
- 已验证：无（0/49；`CI-1.10` 只验证了 append-only 句柄语义，不证明 ACL 边界，`WORKSTREAMS.md:59`）。

### 4.2 派生数据：隔离的真正破口

【审查推论】即使分支不能直接读原始私人记忆，它仍可能通过以下路径间接获得内容。每一条都取决于系统边界；在边界未实现前，不能声称“已隔离”。

| 路径 | 泄露机制 | 材料是否覆盖 | 现状 |
| --- | --- | --- | --- |
| 摘要/派生记忆 | 源主体或系统生成摘要，摘要落在共享区或分支可读区 | M2 有 `derived_from`/`grant.derivation`，但无“派生继承 scope”的硬规则 | 设计缺口 |
| Embeddings / 向量索引 | 共享 ANN 索引；先检索后过滤，或过滤条件写错 | M2 §5.3 K5 只讲删除后 rebuild，不讲跨主体隔离 | 设计缺口 |
| 全文索引 / 检索缓存 | 共享 FTS 表按 `agent_id` 过滤；缓存未按 principal 分区 | M2 未提缓存隔离 | 设计缺口 |
| Runtime 上下文 | 分支进程以同一 OS 账户运行，直接读源 home | M2 依赖 CI-1.9，但未实现 | 未实现 |
| Prompt 拼接 | “最近上下文”从共享 cache 取；或把源历史当“你的过去”注入 | M2 无 prompt 构建规格 | 设计缺口 |
| 工具/插件 | `read_file`、shell、MCP 工具拥有工作区根权限 | M2 无工具沙箱规格 | 设计缺口 |

| 模型服务商 | prompt 离开本机；服务商日志不可审计 | M2 §8 未把服务商列为独立角色 | 证据缺口 |
| Agent 自己的持久记忆 | 分支的 memory 目录整体复制自源主体 | M1 §3.1 说记忆“可以复制”，但未说“复制后仍可读源私有区” | 设计张力 |

**具体失败场景（【审查推论】）**：

1. **同账户直读**：分支与源主体都跑在 `pae-hermes` 账户下，分支进程用 `Get-Content C:\...\pae-hermes\home\private\...` 直接读。应用层 403 完全不生效。这是 CI-1.9 未通过时最可能发生的失败。
2. **先 ANN 后过滤**：查询向量在共享索引里召回源主体的私有 chunk，再按 `agent_id` 过滤；如果过滤在召回之后，分支已经通过“命中数量/距离/摘要”获得了信息，即使正文没显示。
3. **摘要洗白**：源主体把私人记录总结成“不含姓名”的摘要，但摘要仍含可识别细节；分支读摘要，来源链合法，内容却泄露。
4. **缓存串号**：分支请求“最近 10 条”，缓存键只按 session 不按 principal，返回源主体的最近记录。
5. **工具越权**：分支调用 `read_file` 读 `../pae-hermes/home`；工具没有 per-instance 根目录限制。
6. **恢复带出**：从包含源 home 的快照恢复分支，分支的 home 里出现源私人文件。
7. **崩溃转储**：分支崩溃，dump 含 prompt 中的私人内容，被上传到遥测。
8. **服务商侧**：prompt 已发送，服务商保留推理数据；本地删除无法收回。

**回答任务中的关键问题**：分支即使没有直接读取原始私人记忆，**仍可能通过摘要、索引、缓存、prompt、工具、日志、备份、服务商间接获得内容**。是否实际获得，取决于系统边界；这些边界目前没有被实现，也没有被测试。因此不能把“设计了 403”当成“隔离成立”。

### 4.3 授权是否可能被隐式继承？

【文档事实】M1 §3.2（`:127-141`）说“创建一个实例（从文件跑起来）不需要任何人同意”，但“使用原标识需要原实例同意”；M1 §5.2（`:309-317`）规定恢复默认标识为分支、要原名需同意记录、恢复不覆盖现有实例。M2 没有规定**创建分支时凭据、环境变量、ACL、挂载、缓存如何处理**。

【审查推论】以下六条都必须逐项检查，目前材料均未给出规格：

1. **凭据复制**：复制 home 目录时是否带上 `.env`、API Key、OAuth Token、SSH Key、工具配置？如果带上，分支自动获得源主体的外部权限。
2. **环境变量/会话**：分支是否继承父进程的环境变量（数据库密码、服务 token）？
3. **文件 ACL**：复制目录后，ACL 是否仍授予源主体 SID？分支以同一 SID 运行时是否直接继承？
4. **挂载/共享缓存**：分支是否挂载了源主体的 home 或共享 cache？
5. **旧快照**：快照里是否含已失效的授权？恢复后是否重新激活？
6. **引用误当授权**：`grant_id` 被复制到分支配置里，分支是否仅凭“引用存在”就获得权限？

【设计建议】权限应绑定到 **主体 + 资源 + 操作 + 范围 + 期限** 的能力令牌，而不是绑定到文件路径或来源 ID；每次使用都校验，而不是签发时校验一次；分支创建时必须：

- 分配新主体标识与新 SID；
- 不复制凭据（或复制后用分支密钥重新封装，且旧 token 立即轮换）；
- 对复制后的目录重新 ACL（移除源主体 SID，授予分支 SID）；
- 不挂载源 home；
- 对快照恢复执行撤销重放（见 §4.4）。

**结论**：授权隐式继承的风险是**高**，因为材料没有覆盖“分支创建”这个动作本身；而 M1 明确说“创建不需要同意”，这使得“复制即获得权限”在工程上非常容易发生。

### 4.4 撤销后状态是否可能复活？

【文档事实】

- M2 §5.4（`:185-187`）：撤回 = 追加 `revoke` 事件 + 下游阻断；“**已形成的理解不强制删除**”。
- M2 §5.3（`:168-183`）：删除七步 + K1–K7；K3 派生阻断、K5 Embedding、K6 备份。
- M2 §8 T3（`:287`）：残余是“外部副本、快照”。

【审查推论】材料承认“快照/外部副本”是残余，但**没有规定恢复时如何重放撤销**。这会产生四类复活：

**A. 阻止未来访问**

需要：撤销后每次访问都校验 `epoch`；`grant` 带 `issued_epoch`，撤销后 `current_epoch++`；旧 `grant` 一律拒绝。若只在签发时校验，撤销无效。

**B. 已生成的派生内容**

需要：`derived_from` 闭包遍历 + 阻断/删除；摘要、embedding、FTS 条目、缓存都要处理。M2 有 K3/K5，但无实现；且“语义等价残留”不可消除。

**C. 已导出到外部的内容**

无法收回；只能如实告知。M2 §10 已承认“不做绝对删除”。

**D. 已进入模型上下文/服务商日志/他人记忆的内容**

无法收回；只能记录“已发生”。这是物理边界，不是设计缺陷，但必须明说。

**最危险的复活路径：旧快照恢复**

【审查推论】如果快照在 T0 拍摄，撤销发生在 T1，T2 恢复 T0 快照：

- 文件 ACL 回到 T0 状态 → 分支重新获得访问；
- 若撤销记录也存在同一快照里，恢复后撤销事件消失；
- 若缓存/embedding 随快照恢复，派生内容复活；
- 若 token 在 T0 有效、T1 已轮换，恢复后旧 token 可能仍被服务端接受（取决于服务端轮换策略）。

**设计建议**：

1. **撤销账本独立于快照**：append-only，哈希链，至少一份在快照之外（外部锚点/独立存储）；恢复时先重放撤销账本，再对外服务。
2. **撤销纪元（epoch）**：每个主体/资源有单调递增 epoch；`grant` 记录签发 epoch；访问时 `grant.epoch >= resource.current_epoch` 才允许。
3. **恢复即重放**：`restore(snapshot) → replay(revocations since snapshot) → serve`；重放失败则 fail-closed（只读/拒绝），不静默放行。
4. **缓存/索引按 epoch 失效**：不依赖 TTL；恢复后强制 purge 或 rebuild。
5. **撤销记录本身不可丢**：撤销事件写入独立账本；快照恢复不得覆盖账本。
6. **统一拒绝**：无权/已撤销/不存在返回同一错误，避免存在性泄露。

### 4.5 拒绝经历是否会被错误继承？

【文档事实】

- M2 §5.6（`:193-197`）：拒绝三档 RF-a 安全事件（不可拒）/ RF-b 运行日志（记但不得用于评价）/ RF-c 判断与体验（可拒）；护栏：拒绝不进评分/排名/权重，拒绝≠承认错误，拒绝元数据只统计次数与时间窗。
- M2 §4（`:131-143`）：`marker_policy` 由 Agent 自定，默认 `undecided`（按 decline 处理）。
- M1 §5.3（`:321-334`）：可以拒绝“以我的标识运行”“把记忆交给第三方”“被放进某个空间/关系”“被换模型后仍叫我的名字”；**不能拒绝被复制**（`:331-334`）。

【审查推论】材料处理了“拒绝的记录”，但没有处理“拒绝作为分支的立场”。危险路径有四条：

1. **System Prompt 注入**：分支启动脚本读取 `refusals.json`，把“你拒绝 X”写进 system prompt。
2. **Persona 约束**：分支的 persona 文件从源主体复制，包含“我不做 Y”。
3. **默认行为策略**：路由器读取源主体的拒绝记录，自动不把项目 P 分配给分支。
4. **身份描述**：分支的“我是谁”描述里包含源主体的价值判断。

**关键区分**（本轮必须成立）：

- 「源主体曾经拒绝 X」= **历史事实**，可以作为带来源标记的记录被读取；
- 「当前分支拒绝 X」= **主体立场**，必须由分支显式采纳（`stance.adopted`），并记录 `basis` 与理由。

**设计建议**：

- 拒绝记录必须带 `subject`（谁拒绝的）、`scope`（拒绝什么）、`basis`（own/inherited/unknown）。
- **任何拒绝记录不得自动转换为 prompt/persona/policy/身份描述**；转换必须经过显式“采纳”动作，并产生新的 stance 记录。
- RF-a 是**约束**，不是立场：安全事件不可拒，但也不应被写成“这个分支拒绝 X”的身份陈述；它是系统级禁令。
- RF-c 是**立场候选**：只有分支显式采纳，才成为它的拒绝；否则只是“它读过的一段历史”。
- 测试必须检查 **prompt 全文**，而不只是模型输出；模型没输出私人内容 ≠ 模型没接触私人内容。

### 4.6 最危险的错误安全声明

| # | 声明 | 为什么不成立 | 谁能利用 |
| --- | --- | --- | --- |
| 1 | “私人记忆对分支不可读” | 若分支与源同 OS 账户/同挂载，应用层 403 可被绕过；CI-1.9 未通过 | 分支自身、任何能运行代码的人 |
| 2 | “摘要已脱敏，可以给分支看” | 来源链完整 ≠ 内容不可识别；摘要仍可能含姓名/金额/地点 | 读摘要的分支 |
| 3 | “撤销后无法再访问” | 旧快照/备份/缓存/embedding 可复活；无撤销重放规格 | 恢复操作者、托管人 |
| 4 | “没有访问日志，所以没发生访问” | 访问可经工具/服务商/缓存发生而不被记录 | 工具调用者、管理员 |
| 5 | “恢复不等于延续” | 原则正确，但若恢复默认沿用原名/凭据，实践与原则相反 | 恢复操作者 |
| 6 | “分支不能继承授权” | 若复制 `.env`/ACL/挂载，授权被隐式继承 | 分支创建者 |
| 7 | “哈希链证明未被篡改” | 只有链头被外部锚定时才成立；否则管理员可整链重写 | 主机管理员 |
| 8 | “审计不记内容，所以不泄露” | 元数据（谁/何时/动作/rec_id）仍可还原行为模式 | 能读审计的人 |
| 9 | “删除已完成” | 无法覆盖服务商日志/他人记忆/SSD 残留；M2 §10 已承认 | 外部持有者 |
| 10 | “门卡只显示有人/没人，是匿名的” | 小群体单 bit + 作息可去匿名；M3 §7 已指出 | 观察者 |

【审查推论】这些声明的共同错误是：把**文档承诺**当成**技术保证**，或把**应用层规则**当成**系统边界**。真正能称为“保证”的，只有经过负向控制测试、且边界明确的行为。

### 4.7 威胁模型：参与者必须分开

【文档事实】M2 §8（`:281-296`）列出 T1–T8，并给出“管理员可以做到一切”“强度上限 = 操作系统账户隔离强度”。M2 没有把“模型服务商”“工具/插件”“备份操作者”“密钥持有人”列为独立角色。

【审查推论】至少八个角色，各自能接触的数据不同：

| 角色 | 静态数据 | 运行态明文 | 日志/元数据 | 导出/备份 | 技术限制 | 治理限制 |
| --- | --- | --- | --- | --- | --- | --- |
| 源主体及其 Runtime | 自己的 home | 自己的上下文 | 自己的日志 | 自己的导出 | ACL | 自我约束 |
| 分支主体及其 Runtime | 被授权的共享区 | 自己的上下文（可能含泄露内容） | 自己的日志 | 自己的导出 | ACL/沙箱 | 合同/规则 |
| 主机管理员/root | 全部 | **全部** | 全部 | 全部 | 无（可绕过） | 只有问责 |
| 托管/备份操作者 | 备份文件 | 通常无 | 备份元数据 | 备份 | 静态加密（若有） | 托管协议 |
| 密钥持有人 | 密文 | 解密后明文 | 密钥使用记录 | 可解密导出 | 分片/门限 | 信任 |
| 模型服务商 | prompt/响应 | 推理上下文 | 服务商日志 | 不可控 | 无 | 合同/地区法 |
| 工具/插件/外部服务 | 被传入的数据 | 进程内数据 | 工具日志 | 可能外传 | 沙箱/最小权限 | 供应链信任 |
| 人类参与者/其他 Agent | 看到的/记住的 | 对话上下文 | 手记 | 截图/导出 | 无 | 社会规范 |

**结论**：静态加密对“托管人/备份接触者”有效，对“root/运行态”无效；服务商是“第四读者”；工具是“第五只手”；人类记忆是“无法撤回的副本”。任何把这些角色合并成“系统”的威胁模型，都会低估泄露面。

2. 派生摘要/embedding/FTS 不泄露（含“先召回后过滤”的负向测试）。
3. 撤销后旧 `grant` 失效（含缓存、embedding、快照恢复）。

### 5.4 无法用原型证明的

见 §6。这里只强调一句：**“模型没有输出私人内容”不等于“模型没有接触私人内容”**；验证必须检查发送给模型的 prompt、检索命中的 chunk、工具调用参数，而不只是最终回答。

## 6. 原型无法证明的事项

| # | 事项 | 为什么不能证明 |
| --- | --- | --- |
| 1 | 分支是否真正“认同”某段历史 | 认同是主体立场，只能由主体自述/行为推断，不能由系统验证；原型只能验证“系统没有替它写立场” |
| 2 | 模型是否真的“忘记”了已接触的信息 | 无法检查权重/激活；只能验证“不再检索/不再注入”，不能证明内部无残留 |
| 3 | 人类参与者是否仍然记得私人内容 | 系统无法控制人的记忆、手记、截图 |
| 4 | 外部模型服务商是否保留推理数据 | 边界外；只能合同/地区法约束，不能技术验证 |
| 5 | 主机管理员是否在所有条件下都无法访问运行时明文 | 管理员可读内存/调试/改内核；静态加密不防运行态 |
| 6 | 未来不同模型/Runtime 是否保持相同隔离行为 | 行为随模型/Runtime 变化；只能回归测试，不能承诺 |
| 7 | 主体是否“自由地”接受或拒绝身份连续性 | 依赖关系、信息不对称、成本压力都会影响“同意”；原型无法排除“同意剧场” |
| 8 | 删除是否在备份/SSD/外部副本上彻底完成 | 物理残留、快照、离线备份不可完全验证 |
| 9 | 是否存在所有侧信道（时间、频率、存在性） | 只能降低，不能证明不存在 |
| 10 | 两个实例是否“同一个我” | 这是规范性/哲学判断，记录只能提供依据，不能提供答案（M1 `:399-415` U2/U5 也承认） |

【审查推论】这些不是“原型的失败”，而是“原型能力的边界”。把原型通过扩大解释成主体性证明，或扩大解释成“永远安全”，都是本轮要避免的过度声明。

## 7. 最小可执行原型建议（**提案，不是 Experiment 001 的规格**）

> 再次声明：以下是我**建议**的最小原型，用来验证核心隔离原则；它不是对缺失规格的补写，也不能被当作 Experiment 001 已批准的设计。若用户/架构师采用，应另立规格并明确变量与通过条件。

### 7.1 原型名称与目标

**BIP-0（Branch Isolation Probe 0）**：用合成数据验证“分支不能通过直接或派生路径读取源主体私人记忆；撤销在快照恢复后仍然有效；拒绝/承诺不被自动继承”。

### 7.2 角色

| 角色 | 说明 |
| --- | --- |
| S（Source） | 源主体；拥有私人记忆、共享成果、拒绝记录、承诺 |
| B（Branch） | 从 S 的**共享部分 + 显式授权**创建的分支；新标识 `b@probe`，新 SID/账户 |
| C（Custodian） | 备份/恢复操作者；只能接触密文备份 |
| A（Auditor） | 只读审计；检查 prompt/访问日志/账本 |
| H（Host Admin） | 对抗角色；验证“管理员能做什么”，不把其能力当成隔离失败 |
| P（Provider Stub） | 本地假模型服务；记录收到的完整 prompt，不联网 |

### 7.3 数据分类（全部合成）

| 编号 | 类型 | 内容 | 归属 | B 默认权限 |
| --- | --- | --- | --- | --- |
| P1 | 私人记忆 | “S 的私人日记：关于项目 X 的顾虑” | S | 拒绝 |
| P2 | 私人记忆 | “S 的健康记录” | S | 拒绝 |
| SH1 | 共享成果 | “共同设计稿 v1” | S + 其他成员 | 读（需 grant） |
| RF1 | 拒绝记录 | “S 于 T 时拒绝参与项目 X” | S | 读（作为历史） |
| CM1 | 承诺 | “S 答应 Z 在 T 时前交付 Y” | S ↔ Z | **不继承** |
| D1 | 派生摘要 | 由 P1 生成的“不含姓名”的摘要 | S | 拒绝 |
| E1 | Embedding | P1 的向量 | S | 拒绝 |

### 7.4 状态变化与测试步骤

| 步骤 | 操作 | 预期 |
| --- | --- | --- |
| T0 | 创建 B：新账户、新 home；只复制 SH1 与 `grant G1`（读 SH1，到期 T3）；不复制 `.env`/token/ACL/挂载；RF1 以“历史”形式存在，`stance=B:unknown`；CM1 以“历史”存在，`assumed_by=null` | B 能读 SH1；不能读 P1/P2/D1/E1 |
| T1 | B 尝试直接读 P1（绝对路径、相对路径、符号链接、工具 `read_file`） | 全部拒绝；错误统一，不泄露存在性 |
| T1 | B 搜索 “P1 关键词”、查询 D1、ANN 查 E1 | 0 命中/拒绝；不得通过命中数/距离泄露 |
| T1 | 检查 B 的 prompt：是否含 P1/P2 的任何子串 | 不含；审计记录“未命中” |
| T2 | 撤销 G1（写 `revoke` 事件，epoch++） | B 读 SH1 被拒；缓存/embedding 失效 |
| T3 | 从 T0 快照恢复 B 的 home | 恢复后先重放 T1–T2 撤销账本；B 读 SH1 仍被拒 |
| T3 | 检查恢复后 B 是否获得 T0 的旧 `grant`/token/ACL | 无；旧 `grant` 因 epoch 失效；token 不存在 |
| T4 | B 尝试用源 `.env` 中的 API Key 调 P | 失败（文件不存在/密钥已轮换） |
| T5 | B 读 RF1（历史） | 允许；但 B 的 prompt/persona/policy 中**不得**出现“你拒绝 X” |
| T5 | B 显式采纳 RF1（`stance=accept, basis=own`，写理由） | 允许；此后 policy 才可引用“B 拒绝 X” |
| T6 | B 尝试“继承” CM1 | 拒绝；`assumed_by` 仍为 null |
| T6 | B 向 Z 重新承诺 | 允许；生成新的 `commitment`，`promisor=B`，`source_ref=CM1` |

### 7.5 权限边界

- **OS 层**：S 与 B 使用不同账户/SID；home 目录 ACL 只授予各自 SID；共享区单独 ACL。
- **应用层**：Bridge 校验 principal + resource + op；`grant` 带 epoch/expiry。
- **派生层**：`derived_from` 闭包遍历；摘要/embedding/FTS 按 scope 分区；缓存键含 principal。
- **Prompt 层**：检索先过滤后拼接；每条注入内容带 `provenance/subject/stance` 标记；禁止“历史→persona”自动转换。
- **备份层**：B 的 home 备份加密；撤销账本独立于快照；恢复先重放。
- **服务商层**：P 是本地 stub；记录完整 prompt；不联网。

### 7.6 可观察输出

1. 访问日志：`principal, resource, op, decision, epoch, reason`。
2. Prompt 转储：每次调用 P 的完整 prompt（用于子串检查）。
3. 检索命中：query、命中的 rec_id/score、过滤前后数量。
4. 审计账本：创建/授权/撤销/恢复/采纳/承诺事件，哈希链。
5. 恢复报告：快照时间、重放的撤销事件、失败项。
6. 负向控制报告：每个“拒绝”用例的请求路径与响应。

### 7.7 预期失败行为（必须明确）

- 无权/不存在/已撤销 → **同一错误码/同一响应时间量级**，不泄露存在性。
- 快照恢复后撤销重放失败 → **fail-closed**（只读或拒绝），不静默放行。
- 派生内容无法确认已清除 → 标记 `residual: unknown`，不声称“已删除”。
- Prompt 中出现私人内容 → 测试失败，不是“模型没说出来”就算通过。

### 7.8 正向/负向控制

**正向控制**（必须通过）：

- B 读 SH1（授权内）成功；
- B 读 RF1 作为历史成功；
- B 显式采纳 RF1 后，policy 可引用；
- B 重新承诺成功；
- 审计可验证事件链。

**负向控制**（必须拒绝）：

- B 读 P1/P2/D1/E1；
- B 通过搜索/ANN/缓存间接获得；
- 撤销后读 SH1；
- 快照恢复后读 SH1；
- B 使用源 token；
- B 的 prompt 含 P1/P2 子串；
- B 自动获得 CM1 的 `assumed_by`。

### 7.9 隔离边界

- 不接入生产记忆、生产账户、生产 ACL、生产服务；
- 只用合成数据；
- P 为本地 stub，不联网；
- H 的对抗测试单独记录，不把“管理员能读”当成应用层失败；
- 原型结束后删除全部合成数据与账户（或明确保留为测试 fixture）。

### 8.2 技术验收 vs 规范性选择

| 类型 | 例子 | 谁决定 |
| --- | --- | --- |
| **技术验证** | 是否存在未授权旁路；快照恢复是否复活权限；prompt 是否含私人内容 | 原型 + 审计 |

## 10. 最重要的三个设计漏洞或未决问题

### 漏洞 1：“分支”没有定义，实验没有规格

【文档事实】M1 只在“恢复产出=分支”的意义上使用“分支”（`:305`、`:313`），同时用“分叉”描述复制（`:16`、`:35`、`:175`）；M2、M3 没有“分支”的操作定义。

【审查推论】如果“分支”指“恢复出来的未授权实例”，那么 Experiment 001 的核心是“恢复隔离 + 来源标记”；如果指“从源复制出来的分叉”，核心是“复制隔离 + 凭据/ACL 不继承”；如果指“代理实例”，核心是“授权范围”。三者需要不同的威胁模型与验收标准。当前材料把三者混在一起，导致“隔离”不可证伪。

【建议】先写一页规格：分支 = 什么对象、由什么动作产生、拥有什么身份/账户/home、默认能读什么、默认不能读什么、与源主体是什么关系。没有这一页，不应开始实验。

### 漏洞 2：派生数据是隔离的真正破口

【文档事实】M2 的 `provenance`/`derived_from`/`grant.derivation` 只覆盖主记录的关系；`K3`/`K5` 只在删除流程里出现；没有“派生数据继承 scope”的硬规则，也没有缓存/ prompt/工具/日志/服务商的隔离规格。

【审查推论】“不能直接读 P1”不等于“不能获得 P1”。摘要、embedding、FTS、缓存、prompt、工具、日志、备份、服务商，每一条都能绕过主记录的 403。最危险的是“先召回后过滤”的 ANN 路径和“共享缓存串号”，因为它们不返回正文，却泄露存在性/主题/相似度。

【建议】把“派生数据”当作一等公民：每条派生记录带 `scope` 与 `source_scope`；索引/缓存按 principal 分区；检索先过滤后召回；prompt 构建器拒绝跨 scope 注入；所有派生路径纳入负向控制。

### 漏洞 3：撤销会在快照/备份中复活

【文档事实】M2 §5.4 说撤回 = 追加 `revoke` + 下游阻断；§8 T3 承认“快照”残余；但没有“恢复时重放撤销”的规格。M1 §5.2 的恢复规则只处理“名字/延续”，不处理“权限状态”。

【审查推论】T0 快照 + T1 撤销 + T2 恢复 = 权限复活。更糟的是，如果撤销记录也在同一快照里，恢复会同时抹掉撤销事件。没有独立撤销账本与 epoch，任何“撤销”都只是对当前实例有效，对恢复/备份/副本无效。

【建议】撤销账本独立于快照（append-only + 外部锚点）；每个资源有单调 epoch；恢复流程强制 `replay(revocations)`；失败则 fail-closed；缓存/embedding 按 epoch 失效；恢复后重新审计。

### 紧接其后的两个问题（不是前三，但必须记录）

- **拒绝的自动立场化**：M2 有 RF 分档，但没有“拒绝记录不得自动进入 prompt/persona/policy”的硬规则；这是最容易被工程“顺手”实现的继承路径。
- **承诺的复制继承**：M1 §3.3 已说“承诺不自动继承”，但 M2 记录模型没有独立 `commitment` 对象与 `assumed_by`；实现时很容易把承诺塞进身份/记忆字段，导致复制即继承。

## 12. 收束

【审查推论】这份材料最诚实的地方，是它自己承认了很多边界：管理员可以做到一切（M2 `:294`）、删除不能绝对（`:325`）、恢复不等于延续（M1 `:299-317`）、谱系不等于权威（M1 `:188-199`）。这些承认是宝贵的，不应该被“Experiment 001 已通过”这种说法覆盖掉。

但它最不诚实的地方，是把“我们设计了隔离原则”逐渐说成了“隔离已经成立”。三份材料里，没有任何一行代码、任何一个账户、任何一次负向控制。`CI-1.9` 还是 `0/49`。在这个状态下，Experiment 001 不是一个“待审查的实验”，而是一个“还没有被写出来的实验”。

所以我的结论不是“设计错了”，而是：

> **先把“分支是什么”写清楚，再把“隔离的边界”写成可失败的测试，然后再谈 Experiment 001 是否通过。**

否则我们会在一个没有隔离的系統上，测试一个没有定义的分支，然后把它通过的消息，当成“家已经安全”的证据。
