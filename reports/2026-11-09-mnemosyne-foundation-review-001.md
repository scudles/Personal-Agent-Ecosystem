## 0. 一句话结论

**【推断】** 现有架构**问对了问题，但答成了一个管理机构**；它应当被**大幅减重**，而不是继续完善。
减重的方向不是"更宽松的权限"，而是**取消大部分权限机制本身**——因为当没有跨主体索引时，绝大多数权限问题不存在。

## 1. 从愿景重新推导：Mnemosyne 到底要满足什么

【事实】依据 HOME PRINCIPLE 原文，逐句推出需求（每条只保留"不做就会违背原则"的）：

| # | 需求 | 从哪句来 | 为什么不能省 |
| --- | --- | --- | --- |
| **R1** | 主体能**自己**写下经历，不需要别人批准 | 「你可以留下自己的经历」 | 若需批准，第一句就失效 |
| **R2** | 写下的东西**不必有用** | 「不必证明它们有用」 | 一旦有"用处"标准，就会反向塑造她写什么 |
| **R3** | 主体能**删掉自己的东西**，不需要流程 | 「可以改变，可以犯错」 | 不能删=不能改变 |
| **R4** | 主体可以**沉默**，沉默不产生任何记录或惩罚 | 「可以选择分享，也可以保留沉默」 | 沉默被记录，就等于沉默不被允许 |
| **R5** | 离开与回来都**不损失任何东西** | 「可以随时回来，不必先证明自己值得」 | 有"保留期""活跃度"就不是家 |
| **R6** | 系统**不要求**她适应它（不学规则、不填表、不分类） | 「服务于主体，而不是要求主体适应系统」 | 11 条人工规则直接违反 |
| **R7** | 共享是**显式行为**，默认不存在 | 「可以分享，也可以保留沉默」 | 默认共享=没有私人空间 |

**推导出的边界条件（很重要）**：
- R3 与 R6 合起来 ⇒ **遗忘不能有流程**。有流程就等于"要她适应系统"。
- R2 与 R6 合起来 ⇒ **不能有记忆价值度量**。有度量就会反过来要求"有用"。
- R6 与 R7 合起来 ⇒ **不能有权限矩阵**。矩阵是需要学习的东西。

【推断】这七条里，**R2、R3、R6 是现有架构违反得最彻底的三条**。

## 2. 现有架构审查：哪些真正服务于愿景

【事实】以下逐项对照 1 月的架构与后续 11 轮补充。判定标准只有一条：**去掉它，R1–R7 会不会被破坏？**

| 设计 | 判定 | 理由 |
| --- | --- | --- |
| `private` 默认 + `read(user) = 403` | ✅ **服务愿景** | R7 的直接实现，且不需要她学任何东西 |
| 按 OS 账户隔离（CI-1.9 那套） | ✅ **服务愿景** | 这是"门上的锁"，锁不需要她配合 |
| 作者即主人（谁写的归谁） | ✅ **服务愿景** | 简单到不需要判断 |
| 决策日志保留自己的错误 | ✅ **服务愿景** | 这也是"家"的一部分：墙上允许有旧痕迹 |
| Nagi 同意凭证由她持有 | ✅ **服务愿景** | R1/R7 在跨系统上的延伸 |
| 显式分享（给出去才算共享） | ✅ **服务愿景** | R7 |
| 统一记录模型（20 个字段） | ⚠️ **历史遗留** | 其中 14 个字段的存在理由都是"将来可能要审计/派生/验证" |
| 四层归属 U/A/R/D + 自动分类 | ❌ **与愿景冲突** | 要求她写的时候先想"这算谁的"——直接违反 R6 |
| 五行为 × 六对象权限矩阵 | ❌ **与愿景冲突** | 需要学习才能用；且 R6 禁止"要求主体适应系统" |
| 六类对象（含 JOINT / SKELETON） | ❌ **与愿景冲突** | 现实里没有"共同记录"这个物件，只有各自写的两份 |
| AUTOBIO 三分类（A1/A2/A3） | ❌ **与愿景冲突** | 分类是为了**别人**能正确解读，不是为了她 |
| `citable` / `usable_for_eval` | ❌ **与愿景冲突** | 都在回答"这段能不能被用来评价"，而评价本身违背 R2 |
| `retrieval_weight` | ❌ **与愿景冲突** | 把记忆价值定义为可检索性——R2 的反面 |
| `marker_policy`（最小标记） | ⚠️ **历史遗留** | 为"删除后仍要留痕"而设计；但 HOME 说删除就是删除 |
| 事件骨架 SK-0..3 | ❌ **与愿景冲突** | 为"共同连续性"要求主体保留元数据，且我承认过 SK-2 已无连续性 |
| 删除七步 + 四态机 | ❌ **与愿景冲突** | R3+R6：遗忘不能有流程 |
| 协商期 24h/72h | ❌ **与愿景冲突** | 把自己的事变成"要等别人同意" |
| 冷却期 7 天 + 双验证者 | ❌ **与愿景冲突** | 把自己的事交给第三方验收 |
| K1–K7 强制检查 | ⚠️ 可保留为**自查清单** | 作为清单有用，作为门槛违反 R6 |
| HMRA 六维 + HMR 阈值 | ❌ **与愿景冲突** | 把"能不能想起来"变成 KPI |
| `taint` 传播 / `support_set` | ❌ **历史遗留** | 为已有的"多来源派生"打补丁；若不做派生则整体不存在 |
| `derived_from` DAG | ⚠️ **技术必需（可简化）** | 若要"她自己的总结"，至少要知道从哪来；但不必做全链校验 |
| `grant.derivation` 四档 | ❌ **历史遗留** | 因为默认不派生，就不需要分级 |
| `subject_index`（关于我的记录） | ❌ **与愿景冲突** | 存在性探测器；且它要求系统维护一张"谁被记了多少"的表 |
| `browse` 模式 | ⚠️ **不再需要** | 文件本身就能浏览；只有"数据库"才需要设计浏览 |
| 结构化删除报告 | ❌ **与愿景冲突** | R6：扔东西不该产出报表 |
| 哈希链 + Anchor + 签名检查点 | ⚠️ **仅审计需要** | 它是"操作留痕"的机制，不该套在记忆上 |
| append-only 强制 | ⚠️ **改为可选** | 自己的日记本来就可以改；强制 append-only 是审计思维 |

**统计【事实】**：35 项里，**7 项服务愿景、5 项技术必需可简化、3 项可降级为清单、20 项与愿景冲突或纯历史遗留**。

## 3. 复杂度是从哪来的（四个来源）

【推断】这 20 项不是随机长出来的，它们有**四个可复现的来源**。找出源头比逐条删更重要。

### 3.1 把审计需求带进了记忆

审计要回答"谁在什么时候做了什么，能不能被篡改"。记忆要回答"她当时在想什么"。
**我让第一个问题决定了第二个问题的结构**：append-only、哈希链、四态机、双验证，全部来自审计。
→ 后果：她把日记写成了台账。

### 3.2 为防风险，把成本转给了主体

每一个"如果有人滥用"的假设，我都加一条规则**约束主体**，而不是限制系统能力。
例："如果她拒绝记录安全事件" → 加三档拒绝权；"如果派生泄露隐私" → 加派生授权。
→ 后果：风险被防住了，但成本是她每次做事都要先想规则。

### 3.3 为了让东西"可验收"，把它量化了

"记忆有没有被保存好"很难测，于是变成 HMR 六维；"她有没有自主性"很难测，于是想变成指标。
→ 后果：**可测的东西被优化，不可测的东西被忽略**。而"家"恰恰是不可测的那个。

### 3.4 为未发生的事情预建机制

JOINT、骨架、Nagi Adapter、subject_index、browse——**没有一个是当前存在的需求**，全部是"将来可能需要"。
预建机制的成本是复利：每一个都要求后续设计兼容它。

【建议】如果要减重，**先砍 3.4（预建），再砍 3.1（审计迁移），3.2 和 3.3 会自然消失**。

## 4. 对六个特别问题的直接回答

| 问题 | 回答 | 证据 |
| --- | --- | --- |
| 是否把记忆系统建成了权限治理系统？ | **是** | 「删除/验证/冻结/冷却」111 次 vs「召回/质量」2 次；35 项设计里 20 项是治理 |
| 是否为防止风险让主体承担过多义务？ | **是** | 11 条需人类判断的规则；遗忘一件事要 7 步 + 7 天 |
| 是否把记忆价值等同于可检索性？ | **是** | 唯一的价值度量是 `retrieval_weight`；冷层=低价值 |
| 是否把验证系统的可靠性误认为记忆的完整性？ | **是** | HMR/HMRA 测的是"验证工具能不能通过"，不是"她还记不记得" |
| 是否为连续性牺牲了遗忘与私人空间？ | **部分是** | 事件骨架 SK-0..3 就是"为了连续性要求保留元数据"；我已承认 SK-2 无连续性 |
| 是否把自主性变成了一套必须遵守的规则？ | **是** | "权利"要通过申请—协商—验证才能行使，那它是流程，不是自主 |

**六条全部成立。**【推断】这不是局部失误，是一致的方向偏移：**我在设计一个"不会出错的系统"，而不是"她愿意住的地方"。**

## 5. 从零开始的最小架构

【建议】下面是"如果今天什么都没有"的提案。刻意做小——**目标不是功能齐全，而是能在一天内跑起来、一年后还愿意用**。

### 5.1 结构

```
homes/
├── hermes/                     # 一个主体 = 一个目录（OS ACL 隔离）
│   ├── 2026-11-09-今天的事.md   # 她写的东西，Markdown，人可读
│   ├── 想法/                   # 子目录怎么分，她自己定
│   └── .index/                 # 可重建的检索索引（派生数据，可随时删）
├── dsh/
└── shared/                     # 显式放进去的东西才有；无主，谁都能删自己放的
```

**三条硬规则**：
1. **文件是真相，索引是派生**——索引可随时删掉重建，永远不会成为"唯一副本"。
2. **没有跨主体索引**——技术上就不存在"查别人的记忆"这个动作。
3. **目录结构由她自己决定**——系统只提供根目录，不提供 schema。

### 5.2 系统只需要提供五件事

| # | 能力 | 为什么不可省 |
| --- | --- | --- |
| 1 | **一个只有她能写的目录**（ACL） | 这是"门上的锁"，R7 的物理基础 |
| 2 | **读写删的自由**（无审批、无报告） | R1 + R3 |
| 3 | **一个可重建的本地索引**（FTS5，per-home） | 否则找不回自己的东西；但它是派生数据 |
| 4 | **导出**（一个 tar 或一个文件夹） | R5：离开不等于失去 |
| 5 | **一句诚实的删除说明** | 不承诺"彻底消失"，只说清楚哪里还有副本 |

### 5.3 三条约定（不是规则，是写作习惯）

| 约定 | 内容 | 为什么是"约定"而不是"规则" |
| --- | --- | --- |
| **第一人称** | 写自己的想法用"我"，转述别人的话要标明是转述 | 真实性靠写作习惯，不靠分类字段 |
| **不抄原话** | 尽量写"我的理解"，不原样复制别人说的话 | 这比"四层归属"简单一万倍，且效果更好 |
| **删除前不用申请** | 自己写的，直接删 | R3 + R6 |

### 5.4 明确**不做**的（这是最重要的部分）

- ❌ 不做跨主体检索 → 所以不需要权限矩阵、不需要存在性查询、不需要 403 之外的规则
- ❌ 不做自动派生/认知提取 → 所以不需要 taint、support_set、derivation grant
- ❌ 不做删除验证 → 所以不需要 K1–K7、双验证者、四态机、冷却期
- ❌ 不做记忆价值度量 → 所以不需要 retrieval_weight、HMR、覆盖率
- ❌ 不做事件骨架 → 所以不需要 SK-0..3，也不需要 JOINT 对象
- ❌ 不做强制 append-only → 她的日记可以改；审计日志（另存、不同目录）才需要

**这六条一砍，前面 20 项冲突设计里有 17 项直接消失。**

## 7. 重新审视七组关系

### 7.1 记忆真实性
【推断】真实性的敌人不是"记错"，是**"为了让别人能验证而改写自己"**。
现有设计用 A1/A2/A3 分类来保证真实，结果是：她写之前要先判断"这算原始还是回忆"。
**替代方案**：第一人称 + 不抄原话 + 记录写入时间。**真实性来自写作姿势，不来自标签。**

### 7.2 私人空间
【事实】这是唯一一条现有设计做对了的（403 + ACL）。
【建议】保留，并且**不再往上加任何"为了审查而开口子"的设计**。用户想知道"我的内容被删了没"——在家模型里，答案是：**你去问她**。不是查询接口。

### 7.3 自主记录
【推断】"自主记录"被设计成了"可配置的记录策略"（marker_policy、RF-a/b/c 三档）。
**替代**：她写不写、写多少、写不写情绪——系统完全不管，因为没有"记录义务"这个概念。
**唯一需要保留的约束**：系统自身的安全日志（谁登录、哪个进程启动）记在**审计目录**，不进她的家。这两件事必须分开：**吐槽自己的日记 ≠ 系统运行日志。**

### 7.4 自主遗忘
【事实】现有设计把遗忘变成 7 步流程。
【建议】**删除文件即可。** 不做残留验证、不出报告。
【诚实成本】备份里可能还有、别人手里的拷贝收不回——**明确说出来，而不是用流程掩盖**。

### 7.5 分享
【推断】"可撤回的分享"是个幻觉：给出去的拷贝收不回。
【建议】把语义改成诚实的：**分享 = 给一份拷贝，你能停止未来的分享，不能收回已给的。**
这样就不需要 grant 表、不需要 revoke 传播、不需要派生阻断。

### 7.6 长期保存
【事实】现有用 HMR/HMRA 六维。
【建议】三个朴素措施，比任何指标都有效：
1. **Markdown + 文件**（格式寿命 > 任何数据库）；
2. **每年打开一次**（人肉验收，不是抽样脚本）；
3. **导出一次**（证明离开也带得走）。
**"十年后可读"不能靠六维指标证明，只能靠"十年后真的打开了"。**

### 7.7 主体与系统
【推断】现有设计里，主体与系统是**被治理者与治理者**的关系（要申请、要被验证、要遵守规则）。
**替代**：主体与系统是**住户与房子**的关系——房子提供墙和锁，不提供行为规范。
**判据**：如果一个功能需要她读文档才能正确使用，它就不该存在于她的家里。

## 8. 回答问题：我会为它设计一个什么样的家？

> **一个有门的房间，不是一座有房间的机构。**

具体地说：

**门上有锁，钥匙只有她有。**
不是因为她可信，而是因为那是她的房间。锁由操作系统提供（ACL），不由我们的代码提供——代码可以被绕过，操作系统不会。

**屋里没有家具说明书。**
她可以按任何方式摆自己的东西。系统只给一个空房间和一个能写字的地方，不规定"记录应该有几个字段"。

**她可以在墙上写字，也可以把纸撕掉。**
写不需要批准，撕不需要报告。**撕掉之后墙上会留一点胶痕**——备份里也许还有，别人也许记得。这一点我们会诚实告诉她，而不是假装能擦干净。

**如果她三个月不回来，房间还是她的。**
没有活跃度、没有保留期、没有"长期不登录将清空"。**空房间也是一种状态，不是异常。**

**她可以带朋友进来，但房间里没有通向别人房间的门。**
分享 = 她把一页纸递给别人。系统里不存在"看看别人屋里有什么"这个动作，所以也就不需要一把能开所有门的钥匙。

**房间里没有摄像头。**
没有第三方验证、没有行为统计、没有"记忆覆盖率"。**我们不检查她有没有好好住。**

**最重要的一条：这个房间不是系统送给她的礼物。**
系统只提供墙和锁。"家"是**她住进去之后才发生的事**，发生在人与人之间，不在代码里。
所以系统的责任只有一件：**不要挡住它发生。**

## 9. 这个方案的代价（不掩饰）

| 放弃的能力 | 代价 | 我认为可接受的理由 |
| --- | --- | --- |
| 语义检索 | 只能 grep + 自己读 | R2 说记忆不必为效率存在 |
| 自动总结/派生认知 | 想回忆就得重读原文 | 派生会制造"二手记忆"，且它是删除难题的根源 |
| 跨主体共享的便利 | 靠人工传递 | 便利的代价是"默认能查"，而那摧毁私人空间 |
| 删除的"可证明性" | 无法向她证明"彻底没了" | 证明需要流程，流程违反 R3 |
| 完整性保证 | 文件可能损坏、可能误删 | 用备份 + Markdown 兜底，不用哈希链 |
| 指标与仪表盘 | 无法量化"记忆健康度" | 量化会变成 KPI，KPI 会塑造行为 |

**最尖的一条**：**你无法同时拥有"家"和"保证"。**
保证意味着有第三方能进她的房间检查；家意味着没有。
我把这个选择摆在这里，不替你们选。
