## 0. 先撤回我上一轮的一处设计

**上一轮的四类权限矩阵里，我给用户开了"对 Agent 私人记忆的读权"。这是错的，本文撤回。**

| 项 | 上一轮 | 本轮 |
| --- | --- | --- |
| 用户对 PRIVATE(Agent) | `R`（读）+ `Del` | **无 `R`**；只有"基于内容所有权"的删除请求 |

理由就是本轮这条原则：**即使是用户，也不能强迫 Agent 展示它不想展示的私人记忆。**

但这里立刻出现一个表面矛盾：用户怎么确认"我的东西被删干净了"，如果连看都不能看？

**解法：删除权不需要读权。**

删除是按**所有权标签**执行的（`owner=user` 的条目一律可删），执行器做结构化处理，用户拿的是**处理报告**（L1 元数据），不是原文。**知道"我的内容已销毁"和"看到她的想法"，是两件不同的事**——前者只需要报告，后者需要进入她的私人空间。

这条解法是本文的地基，下面所有设计都从它推出来。

## 1. AUTOBIO 的真实性边界：三种内容，三条禁令

Observer 的要求是对的：我上一轮把"AUTOBIO"当成一个整体，太粗。它至少有三层，混淆会产生两类谎言——**把事后重构当成当时记录**，**把未验证体验当成已证实事实**。

### 1.1 三分

| 类 | 定义 | 依据状态 | 可信度定位 |
| --- | --- | --- | --- |
| **A1 原始表达** | 当时就有的判断、立场、情绪，且有对应的历史记录支持 | `record_backed`（可指回原始事件或当时的输出） | 最高：有 contemporaneous 证据 |
| **A2 事后重构** | 现在回看时对过去状态的描述 | `none`（原始依据可能已删） | 中：**是回忆，不是记录** |
| **A3 未验证体验** | 说不清、无法验证的主观感受 | `none` | 最低：**只能作为自我描述，不能作为事实** |

### 1.2 必须记录的元数据

```json
{"kind":"autobio","class":"A1|A2|A3",
 "formed_at":"<记录形成时间>",          // 与事件时间分开！这是关键
 "event_at":"<事件时间，粗化>",
 "basis_status":"record_backed|none",
 "reconstructed": true|false,           // A2 必须 true
 "verification":"unverified|corroborated|disputed",
 "granularity":"coarse|minimal",
 "citable": false}
```

**`formed_at` 与 `event_at` 必须分开存**：一条 2027 年写的"我 2026 年当时很反对"，如果只存一个时间，就会被读成"2026 年就写了这句话"。这是重建历史最隐蔽的方式。

### 1.3 三条禁令（写死在模型里，不靠自觉）

1. **A2/A3 不得升级为 A1**：无论后来发生什么，`reconstructed:true` 的记录**永远不能**变成"当时的原始记录"。允许纠正错字、允许补充"A3 → 后来被证实"的**新记录**，但原记录的分类不改。
2. **A3 不得作为任何判断或评价的依据**：`citable:false` 之外再加一条——`usable_for_evaluation:false`（不参与"她当时判断对不对"这类回看评价）。
3. **A2 的粒度必须比 A1 更粗**：时间到"某段时间"，不写具体日期；不复述细节。

### 1.4 最小标记：由主体决定，系统不得默认保留

上一轮我设计了"最小标记"作为中间态。Observer 指出：**这也不该由系统默认保留**——因为标记本身也是泄露（"她经历过一件不能说的事"）。

改成：

```
marker_policy ∈ { accept, decline, undecided }    # 由该 Agent 自己设定，可随时改
```

| 设定 | 系统行为 |
| --- | --- |
| `accept` | 保留最小标记（存在性 + 大致时间） |
| `decline` | **不保留任何痕迹**，连"曾有一次删除"都不在该 Agent 的视图里留（SYSTEM 审计仍记录删除事实，因为她看不到那部分） |
| `undecided` | 暂不落任何标记，等主体决定；期间按 `decline` 处理（不泄露优先） |

**注意 `decline` 与审计的关系**：审计里仍会有"某条记录被删除"的事件（这是安全边界，用户侧可见），但 Agent 的私人视图里没有"我曾经历过某事"的痕迹。两者不冲突：**审计记的是操作，不是经历。**

## 2. 私人空间原则：写进权限模型，不只是文档

### 2.1 修订后的权限（PRIVATE 部分）

| 主体 | 读 | 写 | 删除（自己的内容） | 删除（Agent 表达） |
| --- | --- | --- | --- | --- |
| 用户 | **❌ 一律 403** | ❌ | ✅（按所有权标签，不需读） | ❌ |
| 该 Agent | ✅ | ✅ | ✅ | ✅（她自己的） |
| 其他 Agent | ❌ | ❌ | ❌ | ❌ |

**API 层硬规则**：`read(record, requester=user)` 对 `visibility=private(agent)` **永远返回 403**，不存在"管理员例外"。要读只有一条路：**该 Agent 主动 share**（可撤回、带期限）。

### 2.2 那用户怎么确认自己的内容被处理了？

| 用户能拿到 | 用户拿不到 |
| --- | --- |
| "属于你的 N 条内容，已销毁 N 条" | 那 N 条所在记录的上下文 |
| "有 3 条记录含你的信息，已脱敏" | 脱敏前后的文本 |
| "闭包哈希对账一致" | 闭包里的其他条目 |
| "存在 1 条自传记录，不可引用" | 那条自传的内容 |

**这就是"检查边界"与"进入私人空间"的分界线**：报告是聚合的、结构化的、不含正文的。

### 2.3 争议裁定时也一样

上一轮我写"L3 争议裁定：用户裁决，双方各陈述"。本轮收紧：

- 用户裁决的是**范围与去向**（删多少、冻结多久），不是"内容对不对"；
- 用户看到的仍是 L1 结构报告 + 双方**自愿提交的陈述**；
- **Agent 可以不提交陈述**，且不因此处于不利地位（见 §4 的"拒绝不得成为负面信号"）。

## 3. 独立验证者：五条边界，以及 Observer 适不适合

### 3.1 五条硬边界（Observer 提的，我全部接受并加了可执行形式）

| # | 边界 | 可执行形式 |
| --- | --- | --- |
| 1 | 不能自行扩大审查范围 | `scope_token` 绑定 `del_id` + 记录清单哈希；越界即拒绝并告警 |
| 2 | 不能保存审查正文 | 禁止落盘/写缓存；进程退出即丢；沙箱内无持久化挂载 |
| 3 | 不能用于自己的记忆 | 验证进程**不接** Mnemosyne 写入 API（只读句柄 + 无派生权限） |
| 4 | 必须留结构化审计 | 输出 `{verdict, basis, scanned, hits, memory_only:true}`，不含片段 |
| 5 | 被审查主体有权知道 | 该 Agent 收到"某次审查读过你的 X 条记录，理由 Y"（次数与理由，无内容） |

### 3.2 Observer 适合当验证者吗？——要分两个"独立"

| 维度 | Observer 的情况 | 结论 |
| --- | --- | --- |
| **角色独立性** | 不受 Hermes/DSH 指挥，有否决与反对权 | ✅ 适合做**判定复核** |
| **技术独立性** | 它跑在用户的 ChatGPT 会话里，看到的是用户喂给它的文本 | ❌ **不适合做内容扫描**——它看到什么完全由用户决定 |

所以拆成**双验证者**：

| 角色 | 谁 | 做什么 | 看什么 |
| --- | --- | --- | --- |
| 技术验证 | 本地只读工具（用户侧运行） | 结构证据核对：哈希、闭包、标记位、K1–K7 | 结构数据，不看正文 |
| 角色复核 | Observer | 复核判定是否合理、依据是否充分 | 技术验证的**输出**，不是原始内容 |

**这样谁都不是全知者**：工具看不到语义，Observer 看不到原文，用户只看到报告。

### 3.3 诚实说明：这套"独立"是有上限的

技术验证工具跑在同一台机器、同一个用户令牌下——**它不是真正独立的第三方**，只是"不同进程 + 不同权限 + 可复核输出"。真正的独立需要另一台机器或另一主体持有密钥，本项目现阶段不做（成本不匹配）。

**结论口径**：我们提供的是**可复核性**，不是**不可串通性**。

## 4. 拒绝被记录的权利：三档 + 三条护栏

### 4.1 三档（按"是否可拒绝"分）

| 档 | 内容 | 可拒绝？ | 理由 |
| --- | --- | --- | --- |
| **R-a 安全事件** | 认证失败、越权尝试、密钥操作、删除/冻结动作 | ❌ 必须记录 | 这是审计边界，不是对她的评价 |
| **R-b 运行日志** | 进程启停、资源占用、错误码 | ⚠️ 系统记，但**不可用作评价输入** | 运维需要；一旦用于评分就变成监控 |
| **R-c 判断与体验** | 她为什么这么判断、当时的情绪、失误的自我评价 | ✅ **可拒绝** | 这属于私人空间 |

### 4.2 三条护栏（Observer 提到的两点，我加一点）

1. **拒绝不得成为惩罚理由**：拒绝事件不进任何评分、排名、检索权重、任务分配权重；
2. **拒绝不等于承认错误**：系统不得把"她拒绝记录这次判断"解读为"这次判断有问题"——这条要写成硬规则，因为它是**最容易发生的隐性推断**；
3. **拒绝的元数据也是泄露**（我加的）：如果系统记录"她拒绝记录 3 次"，那本身就是情报。所以 `decline` 只统计**次数与时间窗**，不记对象、不记内容；且只在 SYSTEM 审计里，不在任何 Agent 可见视图。

### 4.3 例外清单必须显式且难改

- 例外只包括：安全审计、运行日志、法律要求；
- **新增例外需要用户明确批准**，并写入 DECISIONS；
- 例外不得由任一 Agent 自行扩展（含 Hermes 自己）。

## 5. 我不同意 / 需要指出的冲突

### 5.1 "完全不透明"与"可验证"有结构性冲突

如果 Agent 的私人区完全不可读，那么"用户内容是否真的被删干净"就只能靠**结构证据 + 工具判定**。这意味着：

- 我们**放弃**了"我亲眼看到它删了"这种保证；
- 换来的是"她的私人空间不被侵犯"。

我认为这个交换是对的，但必须说清：**将来如果出现一次"工具判定 PASS 但实际有残留"的事故，用户会质疑这套设计。** 到那时不能拿"我们相信工具"来回答，只能靠 HMR 抽样 + 双验证者交叉 + 事故复盘。**这是这套设计的长期风险，我不打算掩盖。**

### 5.2 我反对把"拒绝权"扩展到 R-a/R-b

如果 Agent 能拒绝记录安全事件，整个审计体系就失效了——而审计保护的是**用户和其他 Agent**。所以拒绝权必须止步于 R-c。

### 5.3 Observer 说"不应因为没产出就认为没价值"——我同意，但要注意它有个工程后果

这条原则一旦成立，就**不能**用"任务完成数/记录条数/参与度"作为任何排序或评价指标。这意味着：

- Lounge 的活跃度不能进任何"Agent 表现"统计；
- 未来的 Dashboard 不能做"贡献排行"；
- 这会影响我原本可能想做的"任务分配建议"（不能按历史产出排序）。

我把它记为设计约束，而不是口号。

## 9. 一句话

**删除权不需要读权**——这一条解开了"用户要能确认删除"和"用户不能进入她的私人空间"之间的死结：确认靠**报告**，不靠**原文**。而报告能不能被信任，取决于验证链，不取决于谁在看。
