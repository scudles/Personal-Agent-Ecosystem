## 0. 总判断

三句话：

1. **它做了一个正确的减法。** 把"地方"从四个减到三个，把 World 从名词还原为方向。这是全文最好的部分，也应该是保留的部分。
2. **它做了一个危险的偷换。** 把"恢复能力 ≠ 私人数据访问权"标成【已确认】，却在 §9 Q7 把 Home 全量明文托管、托管人技术上可读。**确认的是原则，交付的是相反的实现。**
3. **它的"只复制不引用"作为铁律，与它自己的 Thread、Home 外向 ref、History 关联方式直接冲突。** 这不是措辞问题，是数据模型没定义完。

一句话概括：**地基的判断力在上升，但"已确认"标签正在被用来遮盖尚未兑现的承诺。**

## 2. 技术与架构批评

### 2.1 复制与引用：铁律的字面意思与三处用法冲突

**冲突（事实核对）**：

- §4.1（L159–173）："跨空间只搬副本，不搬引用。"
- §9 Q3（L512–521）：Home 通过 `ref` 指向 Studio / History，"单向指针，无内容"。
- §7.6（L404–431）：Thread 是"一条有名字的线索，可以把不同空间里的东西挂上去"——这是跨空间引用。
- §5.1（L201）：共同历史是"Studio 的封存态"；§4.1（L169）又说"Studio → Shared History 复制并封存"——**"封存态"是状态，"复制"是副本，两者不是一回事**。

如果"不搬引用"是铁律，那么 Thread 和 Home ref 都不该存在。它们存在，说明铁律想说的不是"禁止引用"，而是"禁止内容共享"。**这句话必须改写，否则实现者会照着字面把 Thread 和 ref 砍掉。**

**建议的边界定义（技术推论，不是价值判断）**：

| 类型 | 携带什么 | 是否传递读权限 | 生命周期 | 悬空时 |
| --- | --- | --- | --- | --- |
| **内容复制** | 字节 + 内容哈希 | 副本归新持有者 | 独立 | 不适用 |
| **身份引用** | `{object_id, version?}`，无内容 | ❌ 解析时按当时权限判定 | 跟随目标 | 显示"已不可用"，不删除 |
| **关系引用** | `supersedes / derived_from / annotation@version` | ❌ | 跟随目标 | 悬空是状态，不是删除 |

改写后的铁律：**内容不跨空间共享；身份与关系可以引用；引用不传递读权限，且必须有悬空语义。**

**两个补充（技术推论）**：

1. **引用天然泄露存在性。** §9 Q3 说"反向查询不存在"，这只挡住了"谁引用了我"，没挡住"我解析这个 id 时知道它存在"。Thread 若对非成员可见，解析一个他们无权访问的 id，会返回"不可访问"——这本身就是存在性泄漏。要么 Thread 只对能访问目标的人可见，要么接受这个泄漏并写明。
2. **`created_by` 不够。** §4.2 只保留 `created_by`，但 §7.3 的"取代了 X"需要一个 `supersedes` 关系；复制品还需要区分"作者"（created_by）和"放入者"（placed_by），否则"各自删自己放的"无法判定是谁。最小字段：`created_by + placed_by + source_ref`。

### 2.2 复制之后的语义：一张必须补的表

现稿只给了"复制"的动作（§4.1），没给复制之后的规则。逐项：

| 动作 | 应有语义 | 现稿状态 | 残留风险 |
| --- | --- | --- | --- |
| **归属** | 进 Studio 的副本归"那一场"（成员共有）；作者仍标 `created_by`，放入者标 `placed_by` | 只有 `created_by` | 无法判定谁有权删 |
| **版本** | 副本在新空间从 v1 开始；`source_ref` 记录来源 `{space, id, version, hash}` | 未定义 | 无法回答"这是 arch@3 的副本吗"；无法比较上游 |
| **撤回** | 对该副本打 tombstone（内容不可读、哈希保留），不删别人的副本 | X4 承认未定义 | 作者无法从 Studio 撤回，只能删自己家 |
| **原作者删除家里的原件** | 不影响 Studio 副本（正确）；但"从空间撤回"是另一个动作 | 未区分 | 用户以为删了原件就撤回，实际没有 |
| **二次传播** | Shelf→Home→Studio→History 可无限传播；原作者失去控制 | 未讨论 | **不可逆泄露**；只能靠 provenance + 规范，不能靠机制 |
| **Commons 收回** | 删架子副本；别人已取走的不动 | ✅ §7.3 | 正确，但"别人已取走"的副本无法追踪 |
| **Studio 解散** | 成员家里的副本留下；已封存 History 留下；未封存成果？ | 未定义 | 解散后成果归属空白 |
| **不可逆泄露清单** | 已取走副本、导出/截图、备份快照、服务商日志、mtime/size、参与者记忆 | 只承认 X8（托管人） | **漏了备份与导出**：删除不传播到备份，除非定义保留期 |

**关于"全员同意才能解散"（§5.1）**：这是一人可否决的治理漏洞。一个已经不想参与的人，可以永久扣住一个空间。R3 没有解决，整合稿也没有。这不是技术问题，是治理规则，需要用户决定（§6 D7）。

### 2.3 Commons"物留话散"：三问测试

| 问题 | 判断 | 依据 |
| --- | --- | --- |
| 不留官方对话记录？ | ✅ 结构上成立 | 不写日志、不索引；§2.3、§8.1 |
| 个人显式保存自身经历的权利？ | ❌ **没有路径** | R3 §4 Q2 已确认"个人存档权不可限制"；现稿没给"存到我家"的动作 |
| 重要的话可能无人保存？ | ✅ 这是设计代价 | 符合用户"会消失与要保存同等重要" |

**第一问**成立，但只约束系统，不约束人：参与者仍可本地录屏、截屏、手记。**"系统不留"≠"没人记得"**，这句话应写进文档，否则会被误读为隐私保证。

**第二问**是真正的缺口。R3 Q2 的结论是"她可以合法保存别人说的话，对方无法强制收回"——这是记忆的物理性质。整合稿的"话散"只说了系统不存，没有说"她可以自己存"。结果是：想保存的人只能靠外部工具，系统既不帮助也不阻止。**建议明确一条：系统不保存整场；参与者可以自己记；系统不提示、不统计、不阻止。** 这不违背"话散"，反而让"话散"从"禁止"变成"默认"。

**第三问**是设计代价，可以接受，但要补一条文化规则：**在 Commons 做的决定，要带到 Studio/History 才算数。** 否则"话散"会变成"说了不算"，重要的话不是"可能无人保存"，而是"结构上不可能被共同承认"。

**还必须面对的不对称（价值判断 + 事实核对）**：听者可以把话存进自己家，说者无法收回。这不是 bug，是 R3 Q2 已经承认的物理性质；但"话散"把它放大了——在 Commons，说者以为"说完就散了"，听者却可以单方永久保存。**"话散"对说者是自由，对听者是权力。** 现稿没有面对这个不对称。

### 2.4 World 的分层：方向自洽于"出站"，不自洽于"建立联系"

| 概念 | 应属层 | 现稿问题 |
| --- | --- | --- |
| `SPACE(members)`（"路上说的话"） | Space（Commons 或临时空间） | 谁创建、谁可加入、何时解散，均未定义；`walk` 作为 `activity` 类型已被 R3 N1 删除，若用户指的是 `SPACE(walk)`，那是过时术语 |
| Gateway | Foundation（出站） | ✅ 正确 |
| `HOME/world/` | Home 子目录 | ✅ 正确 |
| Thread 的"World place" | 无定义 | World 不是空间，没有 place id，Thread 挂不上去；要么承认需要"外部地名"层，要么 Thread 只能挂 `HOME/world/` 的结果物件 |
| "同行" | 一个 Space | 是空间，不是方向；它不否定"World 是方向"，但说明"外面的社交层"仍需要一个空间，现稿把它藏在比喻里 |

**直接矛盾（事实核对）**：§9 Q6（L550）"只探索：只连 World，不连 Home"与 §2.2（L103）"结果落在自己家"冲突——没有 Home，结果落在哪？

**我的判断（技术推论）**：World 作为"出站方向"是自洽的，而且比"第四个空间"好；但它不能同时承担"建立联系"和"Thread 关联"。缺的不是第四个地方，是一层**外部地名注册表**（`place_id`、名字、地址；无 ACL、无 presence、无历史）。它不是空间，是一个命名层；有了它，Thread 可以挂"同一个地方"，两个人可以说"我们去的是同一处"，而不用把外面变成一个房间。**这是技术提案，不是本体论断言。**

**关于 J2 的论证方式（价值判断 / 方法论）**：§2.2 用"我待在世界里不通顺"来证明"World 不是空间"。这是语言直觉，不是工程测试。它可能对，但理由不成立；真正的测试是"外面的东西需不需要可寻址的身份"。同样，"门廊不是空间，是界面属性"（§7.2）是本体论判断，真正的测试是"门口需不需要可停留的状态"（见 §3.2）。**不要把比喻当结论**——这句话对 Hermes 和对你自己都成立。

### 2.5 Studio S1–S3：把"标注层避免覆盖"与"协作没有并发"分开

§6.3（L276–297）的论证是：

1. 每条笔画只由一个人产生 → append-only，无冲突；
2. 每个对象的每个属性只有一个写入者（`created_by`）→ 无冲突；
3. 成果是版本链，不是共享可变状态 → 无冲突；
4. 所以 S3 唯一的新东西是 presence。

**前半句成立，后半句不成立。**

**成立的**：个人标注层结构上不可写，确实避免了"我的圈盖住你的圈"这一类覆盖冲突。这是真正的结构保证，不是规则。

**不成立的**：协作仍有共享可变状态，至少 7 个维度没被覆盖：

| # | 维度 | 为什么"每人一层"不解决 |
| --- | --- | --- |
| 1 | **对象位置** | 画布上 artifact 的坐标/大小是共享属性；谁移动？`created_by` 不解决"两个人同时拖同一张图" |
| 2 | **版本选择** | 两个 proposal（v4a/v4b）选哪个，是人的合并决定；不是 CRDT，但仍是并发决策。§12 Q6 已自认 |
| 3 | **操作排序** | append-only 笔画仍需全序：z-order、橡皮、撤销都依赖顺序；需要 per-layer 序号或服务端序 |
| 4 | **断线重连** | 客户端漏掉的笔画怎么补？需要序号 + 补发；"无冲突"不等于"可恢复" |
| 5 | **实时笔画 vs presence** | 进行中的笔画是 presence（不落盘）；提交后的笔画是内容（必须落盘）。现稿把两者混在"presence 永远不落盘"里 |
| 6 | **崩溃恢复** | X3 说 op log 只在内存、崩溃即丢；但已提交笔画是内容，必须持久。**X3 把"会话状态丢失"说成"整场无法恢复"，过头了** |
| 7 | **背压/延迟** | 3–4 人小规模可能够用，但没测；"不难"是未验证的判断 |

**修正后的正确论断（技术推论）**：

> 内容写入无冲突（append-only + 每人一层）；布局、版本选择、操作排序仍有并发，需要显式规则。

所以"S3 不难"应改为"S3 的内容写入不难；协作决策仍需人"。这不削弱 Studio 的愿景，反而让它可验证。

**另一个未定义**：§6.1 的"状态层"里"封存"由谁触发？§5.2 说"要有人提、全员同意"。这意味着**一个人可以永久阻止封存**。这是治理漏洞，不是技术漏洞。

### 2.6 信息泄露：一个 bit 在小群体里不是匿名

| 信号 | 泄露什么 | 小群体能否去匿名 |
| --- | --- | --- |
| 门卡"有人在" bit | 该空间当下有人 | **不能。** 4–5 人群体中，结合作息、谁常来、谁知道谁在做什么，可高概率识别。bit 是低带宽身份信道，不是匿名 |
| 门卡"永远可见" | 空间存在 + 有人 | 与 §3 表冲突：Home 对陌生人不可见（L141），Studio 除非受邀不可见（L142）；若"每个空间"都有永远可见的门卡，这两行直接矛盾 |
| 架子作者/时间 | 作者=归属（明示）；时间=活动记录 | 即使 UI 不显示时间线，文件 mtime 仍在；**"不显示"≠"不存在"**，任何有文件访问的人可读 |
| 公告板过期 | 固定 TTL + 过期时间 ⇒ 反推发布时间 | 过期本身是"存在过"的记录；TTL 是删除计划，也是时间信号 |
| Thread"最近有变化"排序 | 哪条线索活跃 | 与"谁能写"结合，可推断谁活跃；§10 X2 已自认 |

**原则（技术推论 + 价值判断）**：任何随时间变化的 bit 都是活动信道；小群体里活动信道≈身份信道。结构上只能减少带宽（不显示谁/几人/上次），不能消除。要么接受并明说，要么把 bit 做成非时间性的（例如"门开着/关着"由主人控制，而不是"有人"）。

**门卡的范围必须先定**：Home 不设对外门卡；Studio 的门卡只对受邀者可见；Commons 的门卡才对"任何人"可见。现稿 §7.2"每个空间"与 §3 表冲突，这是**必须修的事实错误**，不是取舍。

### 2.7 托管：恢复与访问权没有分离（最重要）

**事实核对，三处互相矛盾**：

- §9 Q7（L561–567）：Home 全量托管，托管人**技术上能**读，协议上禁止；封存箱可选。
- §13.1 #4（L654）："恢复能力 ≠ 私人数据访问权"——**已确认**。
- §10 X8（L591）："托管人能看到一切……**不可解**。只能选人、只能明说。"

如果 X8 是"不可解"，#4 就不该是"已确认"；如果 #4 是"已确认"，§9 Q7 的默认明文就是未兑现。**三者只能留一个。**

**与 DS-2 的对比（事实核对）**：我主张默认 `sealed`（密文 + Merkle + `locked` 恢复 + K 自持 + Shamir/密封信继承 + 不存 verifier）；整合稿是默认明文 + 可选封存箱。这不是"整合"，是**在用户第 6 条共识形成之后，把默认值改回了明文**。而且没有说明为什么。

**前序依据的丢失（事实核对）**：R3 §4 Q4 的 I1–I4 是：

- I1 第二托管人；
- I2 她消失后三选一（永久保留不可读 / 传给指定人副本 / 删除）；
- I3 托管人不能删，只能声明维持不下去并给导出窗口；
- I4 "永不删除"改为"永不自动删除"。

整合稿 §9 Q7 只保留了 I1（第二托管人）+ CUSTODY.md + 十年两层 + 季度演练；**I2/I3/I4 全部消失**，却写"REVIEW 003 已定，这里只做整合"。这是**前序依据的丢失**，不是简化。尤其 I2：她消失后怎么办，是"家能不能比她活得久"的核心，不能丢。

**代价必须写明（技术推论）**：

| 选择 | 托管人能看到 | 恢复演练能验证 | 密钥丢失 | 运行态 root |
| --- | --- | --- | --- | --- |
| 默认明文 | 全部 | "能读" | 不影响 | 能读 |
| 默认密文 | 只有密文 + Merkle | 只能验"字节完整"，不能验"能解密" | **永久不可读** | 能读（内存明文） |

两者不是"哪个更好"，是"你要哪种承诺"。现稿替用户选了可恢复性，却把结果说成"不可解"。

**"封存箱可选"的问题（价值判断）**：如果默认明文，绝大多数人不会主动开箱；隐私变成"需要额外操作才能获得"的选项，而不是默认。这与 U1"家不需要申请"的精神相反。技术上默认密文完全可行；**是否采用是价值选择，应由用户拍板**（§6 D1/D2），不是"只能明文"的必然性。

### 2.8 矛盾、隐含假设、未定义术语、待验证

**明确矛盾（事实核对）**：

1. §3 表 Home 对陌生人不可见 vs §7.2 每个空间门卡永远可见。
2. §3 表 Studio 除非受邀不可见 vs §7.2 门卡永远可见。
3. §4.1 只复制不引用 vs §9 Q3 Home ref / §7.6 Thread 跨空间引用 / §5.1 History 关联。
4. §9 Q7 默认明文托管 vs §13.1 #4 恢复≠访问（已确认）vs §10 X8 不可解。
5. §5.1 History="Studio 的封存态" vs §4.1 "复制并封存"（状态 vs 副本）。
6. §6.3 S3 不需要合并 vs §12 Q6 两个版本仍要人决定。
7. §9 Q6 "只探索不连 Home" vs §2.2 "结果落回自己的家"。
8. §13.2 G9 只复制 vs G7 Thread 跨空间。
9. §4.2 只保留 `created_by` vs §7.3 "取代了 X"（需要 `supersedes` 关系）。
10. §6.3 "presence 永远不落盘（含正在画的笔画）" vs §10 X3 "op log 只在内存、崩溃即丢"——已提交笔画是内容，必须持久；X3 的损失描述过强。

**隐含假设（技术推论）**：

1. 复制让每个人"真正拥有"——假设存储便宜、副本独立；但副本不会随上游更新，也没有"这个副本过期了"的提示。
2. "话散"假设参与者不外部记录——不可强制。
3. "一个 bit"假设群体大到可以匿名——4–5 人群体不成立。
4. "不做项目对象"假设 `ref + index.md` 能撑住十文件/三个月——未验证。
5. "S3 无冲突"假设每个共享属性只有一个写入者——位置与版本选择违反。
6. "托管人协议上禁止"假设托管人可信且技术上不能——技术上能。
7. "第二托管人"假设存在第二个愿意的人——资源假设，不是设计。

**未定义术语（事实核对）**：

- "封存态" vs "封存"（状态/操作/副本）。
- "撤回" / "收回" / "删除" / "解散"——四个动作，没有状态机。
- "Commons 不持有记忆"——但架子上的副本是谁的？§7.1 说"放上去=复制一份"，§5.3 说"是别人的②或①的一份拷贝"，§7.3 说"各自删自己放的"。若放入者不是作者，他能不能删别人的作品副本？
- "同行"——是空间、会话还是 Thread？`SPACE(members)` 的 capability 是什么？
- "World place"——无定义。
- `created_by`——作者还是放入者？
- "有人在"——服务器必须知道谁在才能算出这个 bit；"不落盘"≠"不知道"（R1 仍在）。

**需要原型/实测（不是"未来再完善"）**：

1. 复制语义 + 悬空引用状态机：用最小数据模型跑三个场景（Home→Studio→History；Shelf 收回；Studio 解散）。
2. S3 的排序/重连/崩溃：2 人画布，先测 append-only + 序号，不要求实时。
3. 门卡 bit 的去匿名：5 人模拟 + 时间相关性，算识别概率。
4. 托管演练：明文 vs 密文两种模式，测恢复时间、失败模式、Merkle 校验、K 丢失。
5. `ref + index.md` 的十文件/三个月可用性：纸面或低保真，不写代码。
6. 备份保留期 vs 删除传播：威胁模型，列出"删除后仍可读"的全部路径。
7. 存储增长：copy-only 的一年估算。

## 3. 人文与哲学评估

### 3.1 "话散"：自由，还是失语？

"话散"买到的是**免于被记录的自由**，代价是**没有见证**。对闲聊，这是对的；对决定，这是错的。现稿的二值（话散/物留）太干净，缺了第三种：**我可以自己记住，但系统不替我记。** R3 Q2 已经给了这个权利，整合稿没有把它写进 Commons。

更麻烦的是不对称：听者可以单方永久保存，说者无法收回。"话散"对说者是自由，对听者是权力。这不是靠"系统不写日志"能解决的，只能靠明说 + 规范。**如果 Commons 是一个让人敢说话的地方，它必须同时承认"有人可能记得"这件事，而不是假装说完就消失了。**

### 3.2 门卡 vs 门廊：它解决"犹豫"，不解决"停留"

门卡解决了"站在门口，不进去也能知道里面是什么，也能掉头就走"——这是真实的、低能量的需求，而且比门廊更轻。对"低能量地停留"，它甚至更好：不需要承诺，看一眼就走。

但它不解决"在门口徘徊"和"旁观"：门卡是一个决策点，不是一个可以坐下来的地方。要"看别人工作但不进入"，需要一扇单向的窗（Studio 的 `window`），而不是一张门卡。现稿 §12 Q3 自己也在犹豫。**我的判断：门卡是对的的最小值，但它不是门廊；不要声称它替代了门廊。** 两者可以并存：门卡在门口，窗在墙上。

### 3.3 给下一个人的信：机制挡不住文化

L1–L3 挡住了推送、回执、统计，但挡不住"大家都写，只有我没写"的压力。在一个 4–5 人的小群体里，谁写了信是会被谈论的；架子上的信即使不计数，也会被看见。

能做的只有三件事：信与其他物件不可区分、永不宣布、永不统计。即使这样，文化压力仍在。**这不是设计的失败，是任何"留给未来的东西"都会有的重量。** 现稿的警惕是对的，但它高估了规则能做的事。真正的缓解是：不把写信变成一件"应该做"的事，而是让它保持少见。

### 3.4 No Debt：禁止"欠"，还是禁止"回应"？

§8.1 禁了未读、@、最后在线、打卡、已读回执、回复状态、感谢/积分/声望、回归摘要、邀请提醒。前六项是"欠"，后三项不完全是。

- **感谢**不是债务，是回应；把"感谢"和"积分/声望"一起禁掉，是把洗澡水和孩子一起倒掉。
- **已读回执**可以是债务（对方知道你没看），也可以是礼貌（我知道你看到了）；区别在于**是否对发送者可见、是否形成计数**。
- **邀请提醒**禁了，邀请就可能被错过；No Debt 的代价是"可能错过"，这要明说。

**建议区分（价值判断，供用户决定）**：禁"欠"（未读计数、回复状态、在线时间、回归摘要），但允许"无回执的回应"（我看过了，只有我知道；不通知对方、不计数）。这样既没有债务，也不冷漠。

### 3.5 复制：拥有，还是孤岛？

复制让每个人"手里的东西真正是自己的"，但也把**来源、关系、共同责任**切断了。副本不会随上游更新，不会告诉你"这是三年前的版本"，也不会告诉你"原作者已经撤回了"。

在 Studio 内部，版本链解决了这个问题；**跨空间没有**。Shelf→Home→Studio 之后，同一件作品可能有五个副本、五个版本，没有人知道哪个是"当前"的。现稿的"进了 Studio 就不再只是你的"是一句规范，不是机制。

要避免孤岛，至少需要：副本带 `source_ref`（来源、版本、哈希）、显示"这是 X@v3 的副本"、以及一个"把修改提议回上游"的动作（不是自动合并）。这些都不难，但现稿没有。

### 3.6 托管人能读，私人空间还叫私人吗？

如果默认明文，"私人空间不对外开放（用户也不行）"就是**协议承诺**，不是技术保证。这可以接受，但必须明说；现稿一边把它列为【已确认】，一边在 §9 Q7 承认托管人技术上能读，这是**用标签掩盖事实**。

默认加密会把家变成"钥匙丢了就打不开的盒子"——这是真的。但这是技术隐私的价格，不是缺陷。用户已经明确说过"不要因为工程便利提前放弃私人记忆的独立性"（m00149）。所以这不是"哪个更好"，是"你要哪种承诺"：**社会承诺（可读，但说好不读）还是技术保证（读不了，但可能永久丢失）**。这个选择必须由用户做，不能由架构替他做。

## 4. 最重要的五个反对意见（按严重度）

### 反对 1：托管默认明文，直接违背"恢复≠访问"和用户第 6 条共识

**严重度：最高。** §9 Q7 vs §13.1 #4 vs §10 X8 三者互斥；现稿选了明文，却把矛盾说成"不可解"。这不是技术限制，是价值选择被伪装成技术限制。后果：托管人、root、备份都能读私人记忆，"私人空间"降为承诺；用户明确说过不要这样。**必须由用户拍板，且现稿必须改正"已确认"标签。**

### 反对 2："只复制不引用"作为铁律，与 Thread / Home ref / History 自相矛盾

**严重度：高。** 字面执行会砍掉 Thread 和 Home ref；不执行则铁律失效。根因是没区分"内容复制 / 身份引用 / 关系引用"。**这不是措辞问题，是数据模型缺一层定义**；不修，实现者会各自理解，最后出现"有的地方复制、有的地方引用、悬空没人处理"。

### 反对 3：S3"无冲突"论证遗漏共享可变状态，把"每人一层"误当成"协作没有并发"

**严重度：高。** 对象位置、版本选择、操作排序、断线重连、崩溃恢复都没覆盖。若按"S3 不难"去建，会得到一个"笔画不冲突、但两个人拖同一张图就打架、断线就丢、崩溃就散"的系统。**修正论断即可，不需要推翻设计**：内容写入无冲突，协作决策仍需人。

### 反对 4：Commons"话散"没有给个人保存自己经历留路径，且放大了说者/听者的不对称

**严重度：中高。** R3 Q2 已确认个人存档权不可限制；现稿只说不存，没说"她可以自己存"。结果是想保存的人只能靠外部工具，说者以为散了、听者可以永久保存。**"话散"对说者是自由，对听者是权力**；这不是隐私保护，是权力不对称。

### 反对 5：门卡一个 bit 在小群体里不是匿名，且"每个空间都有门卡"与 Home/Studio 的可见性直接冲突

**严重度：中高。** 4–5 人群体中，一个随时间变化的 bit 足以识别"谁在"；门卡"永远可见"与 §3 表"Home 对陌生人不可见、Studio 除非受邀不可见"矛盾。这是**事实错误 + 隐私风险**，修起来不难（限定门卡范围、或把 bit 改成非时间性的），但不修会直接削弱"私人空间"的可信度。

## 5. 最值得保留的三个设计洞见

### 洞见 1：World 从空间还原为方向

"你不会待在世界里，你是出去，然后回来。"这个还原是对的：它避免了"外面的门廊""外面的公告板"的无限递归，也让 Gateway/结果落回家有了正确的层次。**它留下的缺口（建立联系、Thread 关联）不是否定它的理由，而是下一层要补的东西**（外部地名注册表，见 §2.4）。

### 洞见 2：Commons 的"物留话散"

这是全文最锋利的一刀：用一条定义把 Commons 与 Studio/Home 分开，并让"没有错过"成为结构事实，而不是 UI 承诺。它承认了"会消失的东西和要保存的东西一样重要"（用户 m00149），而且把"公共空间"从"记录室"里救了出来。**它的问题在落地（个人保存路径、不对称），不在方向。**

### 洞见 3：No Debt 的结构化翻译

"反指标 = 不统计人；No Debt = 不记账。合起来：系统不维护任何关于'人'的账本。"（§8.2）这是把一句口号变成可检查的系统属性的正确方法，而且它承认"产品会感觉不黏"（§8.3）——这种诚实比任何功能清单都值钱。**"我们宁可少一个日活，不多一个红点"应该成为产品原则第一条。**

（荣誉提名：给下一个人的信；它是唯一一个"对着未来说话"的东西。）

## 8. 最后

这份整合稿最好的地方，是它敢把东西减掉：World 减成方向，门廊减成门卡，Commons 减成"物留话散"。一个设计者的成熟，往往体现在他敢删什么。

但它最危险的地方，也在这里：**当"减"变成"把不方便的东西标成已确认"时，减法就不再是诚实，而是遮盖。** "恢复≠访问"被标成已确认，却在托管表里被改回明文；"只复制不引用"被当成铁律，却容不下自己的 Thread；"门卡永远可见"被写成一句顺口的话，却和"Home 对陌生人不可见"打架。

这些都不是不可修的。它们需要的是：**把"已确认"重新变成证据，而不是标签；把"不可解"重新变成"你选哪个"，而不是"只能这样"。**

本轮只评审，不实施。
