## 1. U3：多进程并发追加

### 1.1 实测：1600 条并发没有插穿

`tools/poc/append_concurrency_probe.py`（只写 `%TEMP%`，4 进程 × 400 条 × ~200 字节）：

```
worker 结果 (id, 写入成功数, err): [(0,400,0), (1,400,0), (2,400,0), (3,400,0)]
期望记录 1600 · 实际行 1600 · 写入报告成功 1600
无法解析的行(插穿/截断): 0
pad 长度异常的行: 0
每个 worker 内部顺序单调: True
每个 worker 条数正确: True
结论：PASS —— 单次 WriteFile 的记录在并发追加下未互相插穿
```

### 1.2 这个结果的正确解读（别当成保证）

- **支持**：把「一条记录 = 一次 `WriteFile`」当作记录边界，在本地 NTFS 上是可行的；
- **不支持**：Win32 的 API 契约里**没有** POSIX `O_APPEND` 那样的原子追加承诺。这次没插穿，是文件系统实现行为 + 单次写足够小的结果，**不是协议保证**；
- **所以**：仍然要**带长度前缀与校验**，让"万一插穿"变成**可检测的损坏**，而不是"读起来像正常数据"。

### 1.3 记录格式（自定界，可检测）

```json
{"v":1,"seq":123,"n":456,"sha":"<前 16 字节 sha256>","body":{...}}\n
```

| 字段 | 作用 |
| --- | --- |
| `seq` | 全局单调，链的输入 |
| `n` | 本条字节长度（不含换行），用于交叉校验行边界 |
| `sha` | `body` 的哈希截断，检测截断/串行 |
| 末尾 `\n` | 人可读 + 行解析 |

读取端规则：**任何一条解析失败 → 该段标记 `corrupt`，`verify_audit` 报 `audit_segment_corrupt@seq`，且 Bridge 拒绝新任务准入**（失败关闭，不跳过）。

### 1.4 单写者优先（并发尽量进队列，而不是进文件）

设计上仍然是**单写者**：

```
Agent 进程 ──(IPC)──▶ Recorder（单实例，持锁）──▶ 单次 WriteFile ──▶ 文件
```

- Recorder 启动时用**命名互斥体**（`Global\PAE-Recorder-{instance}`）保证单实例；
- 抢不到互斥体 → 直接退出并报错（不允许两个 Recorder 同时写）；
- 并发来自**客户端**，由 Recorder 内部串行化；文件层面不指望并发安全。

**理由**：并发写文件即使在实测中"没出事"，也无法提供可证明的顺序保证；而 `seq` 的单调性正是哈希链的前提。

### 1.5 短写与半行（必须 fail-closed）

`WriteFile` 成功返回但 `lpNumberOfBytesWritten < len` 是可能的（磁盘满、配额、卷错误）。规则：

1. 短写 → **立即** `FlushFileBuffers` + 在段尾写一条 `segment.corrupt` 记录（若还能写）+ 进程退出码非 0；
2. **不允许**"重试补齐半行"——补写会让读取端看到一条拼接记录；
3. 若连 `segment.corrupt` 都写不进去 → 该段永久标记不可用（外部状态文件由用户侧维护），Recorder 拒绝服务。

### 1.6 持久化策略（两个使用方要求不同）

| 使用方 | 每次 flush? | 说明 |
| --- | --- | --- |
| 审计（安全关键） | **是**（`FlushFileBuffers` 每条） | 慢但可接受：审计是低频事件 |
| 记忆归档（Mnemosyne） | 批量（每 N 条或 T 秒） | 吞吐优先；掉电可能丢最后一小批，**但不会乱序或半行** |

两者用**不同的文件/不同的 flush 策略**，不共用配置。

### 1.7 尚未验证

| # | 项 | 为什么 |
| --- | --- | --- |
| N1 | 跨卷/网络盘行为 | 本次只测本地 NTFS |
| N2 | 大记录（>1 MB）是否仍单次原子 | 未测；设计上**禁止**大记录进日志（见 1.8） |
| N3 | 断电/蓝屏下的最后一条记录 | 需要故障注入，暫不做 |
| N4 | 杀进程时的半行 | 可用 `taskkill /f` 在写一半时注入，属 PLANNED |

### 1.8 大载荷不过日志

单条记录上限 **64 KB**（含 body）。超过的（图片、长文本、附件）：

```
blob 文件：D:\PAE\<owner-home>\blobs\<sha256>      （内容寻址，一次写入不再改）
日志记录：{"type":"blob.ref","sha":"<sha256>","size":N,"mime":"…"}
```

好处：①日志保持小记录（1.2 的实测结论才有意义）；②大文件不需要 append 语义；③去重天然（同内容同 sha）。

## 2. U4：段文件轮转与原子性

### 2.1 硬约束：Recorder 自己轮转不了

ACL 设计里 `audit` 目录对 Recorder 只有 `R`（无 `WD` 无 `AD`），所以它**既不能新建段文件，也不能删除旧段**。这不是疏漏，是刻意的：能建文件就等于能伪造历史段。

于是轮转必须是**双方协作**：

| 角色 | 能做什么 |
| --- | --- |
| 用户侧任务（提升权限） | 预建下一段、原子切换指针、归档已封存段 |
| Recorder | 读指针、在**记录边界**切换、写 `seal` 标记；指针无效时**失败关闭** |

### 2.2 双段 + 指针清单

```text
D:\PAE\audit\
├── events-0001.jsonl     ← 段 1（Recorder 只能追加）
├── events-0002.jsonl     ← 段 2（预建，空）
└── segments.json         ← 指针清单（用户写、Recorder 只读）

segments.json:
{
  "version": 1,
  "active": "events-0002.jsonl",
  "sealed": [{"name":"events-0001.jsonl","last_seq":8421,"hash":"ab12…","sealed_at":"…"}],
  "updated_at": "…"
}
```

**为什么是"双段"而不是"按日期新建"**：Recorder 无权创建，所以下一段必须**提前存在**；任何时刻至少有一个空段可用，切换就不会因为"没有可写段"而卡死。

### 2.3 切换协议（7 步，顺序不能乱）

```text
① 用户任务：确保 next 段存在（空文件，继承 ACE）
② 用户任务：写 segments.json.tmp → MoveFileExW(MOVEFILE_REPLACE_EXISTING|WRITE_THROUGH)
③ Recorder：在下一条记录的**边界**读到新 active
④ Recorder：向**旧段**追加 {"type":"segment.seal","seg":1,"last_seq":N,"tail_hash":H}
⑤ Recorder：向**新段**追加 {"type":"segment.open","seg":2,"first_seq":N+1,"prev_hash":H}
⑥ Recorder：从下一条记录起改用新段句柄（旧句柄关闭）
⑦ 用户任务：等 segment.seal 被 Anchor 锚定后，才允许压缩/归档旧段
```

**关键不变式**：

- **⑦ 之前不许动旧段**。归档 = 移到冷存储；删除必须等锚点覆盖，否则"删段"就成了绕过审计的后门。
- ④ 与 ⑤ 之间若崩溃：新段存在但没有 `open` 记录 → 下次启动时 Recorder 看到 active 段首行不是 `open` → **失败关闭**（不猜、不补写）。
- 切换永远发生在记录边界，**绝不在一行中间**。

### 2.4 指针读取与损坏处理

Recorder 每条记录前读一次 `segments.json`（小文件，开销可忽略），规则：

| 情况 | 行为 |
| --- | --- |
| JSON 可解析、`active` 指向存在的文件 | 正常 |
| JSON 可解析、`active` 指向**不存在**的文件 | **失败关闭**（无权限建文件，也不许退回旧段猜） |
| JSON 解析失败（半写/损坏） | 用上一次有效指针继续**当前段**，连续 3 次失败 → 失败关闭并告警 |
| `segments.json` 不存在 | 失败关闭（启动即拒） |

**为什么不"自动回退到最后已知好段"**：回退意味着在没有用户指示的情况下继续写历史，可能写进已经该封存的段——那会破坏"段边界 = 锚点边界"的对应关系。

### 2.5 原子替换的具体做法

```powershell
# 用户侧（有全权）
$tmp = "D:\PAE\audit\segments.json.tmp"
Set-Content -LiteralPath $tmp -Value $json -Encoding UTF8
[IO.File]::Replace($tmp, "D:\PAE\audit\segments.json", $null, $true)   # 或 MoveFileEx + WRITE_THROUGH
```

要点：同卷替换在 NTFS 上是原子的；`WRITE_THROUGH` 保证元数据先落盘，避免"指针换了但内容没落地"。

### 2.6 段大小与触发条件

| 条件 | 阈值 | 谁触发 |
| --- | --- | --- |
| 段字节数 | 64 MB（可配） | 用户侧定时任务（如每 5 分钟检查） |
| 段年龄 | 24 小时 | 同上 |
| 手动 | — | 用户 |

Recorder 不做"我看到段满了就切"——它没有创建权，切了也没地方写。**触发权在用户侧**，这是权限设计的直接后果，写在这里防后人"顺手给 Recorder 加 WD"。

## 3. 这些设计**没有**解决的问题

| # | 问题 | 说明 |
| --- | --- | --- |
| V1 | Recorder 仍可追加伪造记录 | 只有 HMAC（Agent 侧签名）+ 交叉核对能发现；`BLOCKED` |
| V2 | 用户/管理员可删除整段 | X-E6 已如实记录；锚点只能"发现" |
| V3 | 段封存与锚点的时间差 | 若段未封存就被归档，链会断；靠协议 ⑦ 与 `verify_audit` 检测 |
| V4 | 单写者 = 单点 | Recorder 挂掉 → 审计停摆 → Bridge 拒绝准入（符合失败关闭，但可用性下降） |
| V5 | 大载荷的 blob 目录谁清理 | 目前没设计 GC；需要"引用计数 + 用户批准"策略 |
