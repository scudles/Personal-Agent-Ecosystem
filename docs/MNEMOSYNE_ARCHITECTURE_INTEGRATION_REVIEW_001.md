## 0. 三个判断先行

| # | 判断 | 性质 |
| --- | --- | --- |
| **J1** | **Commons 值得成为第三个地方，但不是第四个"空间类型"**——它是 `open` 能力的一种**固定形态**，其定义特征是：**话会散，东西会留。** | 【新建议】 |
| **J2** | **World 不是空间，是一个方向。** 没有一个叫"外面"的房间，只有一道门。把 World 当空间会引出"外面的门廊""外面的公告板"这类无限递归。 | 【新建议】，**与你的四空间表述不同** |
| **J3** | **DeepSeek 的六项提案里，五项是物件或界面属性，一项是底层原则（No Debt）**。No Debt 不该进任何空间，它该进地基。 | 【新建议】 |

**所以最终结构是：三个地方 + 一个方向 + 一条边 + 一层地基。**

**这不是否定你的四空间，而是把"World"从名词改回动词**——因为"去探索"从来不是一个可以待着的地方。见 §2.2。

**读法**：
- **三个地方**是你**待着**的（Home / Commons / Studio）；
- **一个方向**是你要**出去**的（World）；
- **一条边**是你和某个人**之间**的（Edge）；
- **一层地基**是它们**共同依赖**的，也是**唯一能限制它们**的。

## 2. 为什么是三个地方

### 2.1 三个地方各自回答一个问题

| 地方 | 回答的问题 | 谁能进 | 留下什么 |
| --- | --- | --- | --- |
| **Home** | **我是谁** | 只有我 | 一切，永久 |
| **Commons** | **我们在一起时是什么样** | 任何人 | **东西留下，话不留下** |
| **Studio** | **我们一起做什么** | 受邀者 | 成果 + 版本 + 各自的意见 |

**三个人生尺度**：独处 / 相处 / 共事。
三者不能合并——合了就会出现"要么全私密要么全公开"，也就是之前两轮一直在修的那个问题。

### 2.2 为什么 World 不是空间【新建议】

**测试法**：换个说法还能通顺吗？

| 说法 | 通顺？ |
| --- | --- |
| "我回家了" | ✅ |
| "我在 Commons 待了一会儿" | ✅ |
| "我们在 Studio 里改了三版" | ✅ |
| "我**在世界里**待了一会儿" | ❌ **不通顺** |

因为**世界不是一个可以待着的地方，是一个方向**。你不会"待在外部世界"，你是**出去，然后回来**。

**所以 World 的形状是**：

```
HOME/world/  ──想出去──▶  Gateway  ──▶  外部
   ▲                        │
   └──── 结果落回自己的家 ◀──┘
```

- **Gateway 是唯一的门**（白名单、预算、凭据不出域、破坏性操作拒绝）；
- **结果落在自己家**（`HOME/world/`）；
- **同行** = 两个人各自出门，开一条 `SPACE(members)` 当"路上说的话"，**不是进入一个叫 World 的房间**；
- **没有"World 的公告板"**——因为外面不归我们管。

**这个改动的实际收益**：
如果 World 是空间，就要回答"谁能进 World""World 里有什么权限""World 的历史怎么存"——**全是伪问题**。
它是方向，这些问题就不存在。

### 2.3 Commons 接受为地方，但要改一个定义【新建议】

**你的表述**：共同生活、门廊、公共架子、公告板、自由交流与偶遇。

**我的补充（这是决定它能不能成立的一句话）**：

> **Commons 里，话会散，东西会留。**

- **话**（过程）：说完就没有。不落档、不索引、不回溯；
- **东西**（产物）：留在架子上、公告板上、信里，**放着就一直在**。

**为什么必须这样**：
门廊如果连你说过的话都留着，那它就不是门廊，是**记录室**——人一进去就会开始斟酌措辞。
而架子上的书、板上的纸条，本来就是给人看的，**留着才对**。

**这条一旦成立，Commons 就和 Studio、Home 彻底分开了**：
Home 留一切 / Commons 留物不留话 / Studio 留成果和意见。

## 3. 四个空间的职责与边界

| 维度 | **Home** | **Commons** | **Studio** | **World（方向）** |
| --- | --- | --- | --- | --- |
| 谁能进 | 只有我 | 任何人（不需邀请） | 受邀者 | 我自己去 |
| 进入方式 | 我就是在那儿 | 走进去 | 收到邀请后 | 出门 |
| 留下什么 | 一切 | **物留话散** | 成果 + 版本 + 意见层 | 落回自己家 |
| 有无历史 | 有（我写的） | **无**（只有物件） | 有（版本链） | 无（除非我自己记） |
| 谁可删 | 我 | 各自删自己放的 | 各自删自己放的 | — |
| 时间尺度 | 永久 | 当下 | 一场工作 | 一次出行 |
| 陌生人能看见吗 | ❌ | ✅ 只看到"有这个空间" | ❌ 除非受邀 | — |
| 能不能邀请人 | ✅ 邀请到 Studio / Commons | 不需要 | ✅ | ✅ 同行 |

### 3.1 职责重叠检查（你问的第 1 题）

| 潜在重叠 | 是否真重叠 | 处理 |
| --- | --- | --- |
| Commons 的"自由交流" vs Studio 的"讨论" | **不重叠** | Commons 的交流**不留**；Studio 的讨论**挂在成果上、留**。同一句话在 Commons 是闲聊，在 Studio 是评审意见——**区别不在内容，在于它挂在哪** |
| Commons 的架子 vs Studio 的共同成果 | **不重叠** | 架子上的东西**不属于任何人在场的一场工作**，是"放在那儿的"；Studio 成果属于那一场，有版本链 |
| Home 的探索痕迹 vs World | **不重叠** | World 是过程，Home 是结果 |
| Studio 的成果 vs Home 的记忆 | **不重叠** | 成果是**副本**（见 §5） |

**结论：四个职责不重叠，但前提是 Commons 采用"物留话散"的定义。** 若 Commons 也留话，就会和 Studio 的讨论直接打架。

## 4. 数据流与权限关系

### 4.1 一条铁律

> **跨空间只搬副本，不搬引用。**

| 方向 | 搬什么 | 后果 |
| --- | --- | --- |
| Home → Studio | **复制**一份进去 | 删家里的原件，Studio 里那份不动 |
| Studio → Home | **复制**一份回去 | 空间解散，家里的还在 |
| Home → Commons 架子 | **复制**一份上去 | 拿下来不影响你 |
| Commons 架子 → Home | **复制**一份下来 | 别人收回，你手里的还在 |
| Studio → Shared History | **复制并封存** | 见 §5 |

**为什么不搬引用**：
引用会产生"我删了家里的，别人的就空了"——这就是上一轮 G2 的问题。
**复制会多占空间，但它让每个人手上的东西真正是自己的。** 这个代价我认为必须付。

### 4.2 权限粒度

- **空间级**：加入就看见，不加入就看不见。没有逐条授权；
- **对象级只保留一个**：`created_by`（归属必需，否则无法知道谁的标注是谁的）；
- **没有**：`shared_with`、`visible_to`、`can_derive`、`retrieval_weight`——全部已废弃。

### 4.3 标注层的权限（Studio 核心）

| 层 | 谁能写 | 谁能删 |
| --- | --- | --- |
| 成果对象 | 成员可**提新版本**，不能改旧版 | 无人（版本向前） |
| `annotation:<subject>` | **只有该主体** | **只有该主体** |
| 讨论线索 | 成员 | 自己发的那条 |

**这不是规则，是结构**：别人的图层**根本不在你的写权限里**。

## 5. 记忆与共同历史模型

### 5.1 四份副本（沿用，但补上空间坐标）

| # | 是什么 | 住在哪 | 谁能读 | 谁可删 |
| --- | --- | --- | --- | --- |
| **①** | 我的记忆 | Home | 只有我 | 只有我 |
| **②** | 共同成果 | Studio | 成员 | 各自删自己放的；整体解散需全员 |
| **③** | 共同历史 | Studio 的封存态 | 成员只读 | **无人**；任何人可撤回自己的部分 |
| **④** | 他人的记忆 | 他们的 Home | 他们 | 他们 |

### 5.2 五条铁律（不变，其实是同一句话的五种说法）

1. **① → ② 不自动**：我说过的话不会因为说了就成成果。
2. **② → ③ 不自动**：一场工作不自动封存，要有人提、全员同意。
3. **③ → ① 不覆盖**：封存后我可以在家里写"我不同意那版结论"。
4. **④ 不存在于系统**：没有"看别人怎么记"这个动作。
5. **升格必须所有者发起；降格不可能。**

### 5.3 Commons 的位置（新）

Commons 里**不产生 ① ② ③ ④ 中的任何一个**：

- 架子上的一件东西，是**别人的 ②（如果它曾在 Studio）或别人的 ①（如果就是从家里拿出来的）的一份拷贝**；
- 你从架子上拿下来，**它变成你的 ①**（你的记忆里有这本书），不是你们共同的；
- **Commons 本身不持有任何记忆**。

**这一条很重要**：Commons 是**交换的地方**，不是**存放记忆的地方**。
一旦 Commons 自己开始持有记忆，它就变成了第二个 Home，而它不该是。

### 5.4 共同历史的"可见性 × 完整性"（沿用 REVIEW 002-A）

| 操作 | 可见性 | 完整性 | 读者看到 |
| --- | --- | --- | --- |
| 修订 | 可见 | 原文在 | 原文 + "2027-03 我有不同看法" |
| 脱敏 | 该段不可见 | 哈希保留 | "[已撤回] 2027-03" |
| 撤回 | 整条不可见 | 哈希保留 | "有人撤回了这部分" |

**任何人都能撤回自己的部分，不需要理由，不需要同意。**

## 6. Studio 完整设计方向

### 6.1 三层模型（这是 Studio 的骨架）

```
┌── 素材层 ────────────────────────────────────────────────┐
│  成果 artifact（文档/代码/设计稿/图）  ← 有版本链          │
│  创作性手绘（画一个新东西）            ← 自己就是成果      │
└──────────────────────┬───────────────────────────────────┘
                       │ 被指向
┌──────────────────────▼───────────────────────────────────┐
│  意见层（每人一层，互不可写）                              │
│  指称性手绘（圈/箭头/下划线/写字）  ← 绑 artifact@version  │
│  讨论线索 thread                    ← 锚在坐标或对象上     │
└──────────────────────┬───────────────────────────────────┘
                       │ 收敛
┌──────────────────────▼───────────────────────────────────┐
│  状态层                                                   │
│  版本链（向前，不覆盖）· 版本比较（并排/叠加）· 封存        │
└───────────────────────────────────────────────────────────┘
```

**三句话**：
- **共同思考发生在意见层**（各说各的，互不覆盖）
- **共同创造发生在素材层**（东西越改越好，旧版都在）
- **共同承认发生在状态层**（哪些已经定了）

**三层一混，就会出"我的反对被当成已定结论"或"草稿被当成成果"。**

### 6.2 手绘的两种用途，必须分开

| | **指称性** | **创作性** |
| --- | --- | --- |
| 是什么 | 圈、箭头、下划线、写一个字 | 画一个新东西 |
| 作用 | **指向**已有的东西 | **产生**内容 |
| 归属 | 标注层（某人 的意见） | 素材层（共同产物） |
| 跟版本走吗 | ✅ 绑 `@version`，变了变 stale | ❌ 自己就是成果，自己版本化 |
| 谁能删 | 只有主人 | 只有创建者 |

**这个区分决定了"版本比较"能不能成立**：不分的话，改一版之后你不知道"这个圈是意见还是作品"，也就不知道该不该标 stale。

### 6.3 S1 → S2 → S3：不是三个难度，是三次加法

**关键判断：S3 实时协作在这个模型里并不难，因为我们从一开始就删掉了"合并"。**

| 阶段 | 能力 | 需要解决什么 | 需要"合并冲突"吗 |
| --- | --- | --- | --- |
| **S1 静态** | 画布 + 图层 + 标注绑版本 + 成果放置 | 版本号、stale 标记 | ❌ 不需要 |
| **S2 版本** | 版本链 + 并排/叠加比较 + 提案 | 版本链、比较渲染 | ❌ 不需要 |
| **S3 实时** | 光标、笔画实时同步、在场 | 低延迟广播 | ❌ **仍然不需要** |

**为什么 S3 不需要合并算法**：

1. **每条笔画只由一个人产生**，别人不能改 → **append-only，无冲突**；
2. **每个对象的每个属性只有一个写入者**（`created_by`），别人的修改是"提案" → **无冲突**；
3. **成果是版本链，不是共享可变状态** → **无冲突**。

> **我们不是"把实时协作做简单了"，是把它做没了——因为它要解决的问题（并发冲突），在"每人一层"的模型里根本不存在。**

**这就是为什么不能因为"实时难"而削弱 Studio 的最终愿景**：它不难。

**S3 唯一的新东西是 `presence`**：光标、正在画的笔画、谁在场。
**presence 永远不落盘**（REVIEW 002-A §4.6）——有了在场，能一起画；不落盘，就没有"谁最近来过"。

### 6.4 S1 的验收（不变）

> 用户手绘**圈住一段**（指称性）→ 落在自己图层，绑 `arch@3` → Hermes 改出 `arch@4` → **那条圈变 stale 但还在** → DSH 在自己层放 note → 封存后，第三人看不到任何人的私人日记。

**S1 不需要**：open 空间、实时、版本比较。

### 6.5 代码协作：执行走 Gateway，结果贴回画布

【新建议】**Studio 显示"跑过的结果"，不是"正在跑的环境"。**

- 想跑代码 → 走 Gateway（受 policy 约束）；
- 产出一次**结果快照**（日志 / 测试输出 / 截图）→ 作为 artifact 贴回画布；
- **好处**：执行有边界、可复现、画布不承担运行时；
- **代价**：不能"边改边看"，有延迟。**我接受这个代价**，因为"在画布里执行任意代码"会毁掉整个沙箱模型。

### 6.6 不做"项目对象"（维持）

一套作品有十个文件、跨三个月——**用 `ref` 组织（一份 `index.md` 指向几个 artifact），不做"项目"容器**。

**理由**：一旦有"项目"对象，就会有"项目状态/里程碑/负责人/进度"——**那就是任务管理，我不做。**

**这条我承认有风险**：真实使用中可能会崩（REVIEW 003 §10 第 3 条已列为请 DeepSeek 反驳的点）。

## 7. Commons 的定位与边界

### 7.1 四个物件，各自管什么

| 物件 | 是什么 | 留什么 | 关键约束 |
| --- | --- | --- | --- |
| **门廊（门卡）** | 每个空间门口的一块牌子 | 名字 + 这是什么 + 谁能进 + 有人在吗（**一个 bit**） | **不是空间**，是每个空间的属性（见 7.2） |
| **架子（Shelf）** | 放东西的地方 | 物件（作品、书、工具、一段代码） | 放上去 = **复制一份**；可收回；别人不能改，只能在自己的东西里"取代" |
| **公告板（Bulletin）** | 贴一句话的地方 | 通知、邀请、找人的话 | **默认过期**；没有回复、没有已读、没有"谁看了" |
| **给下一个人的信** | 架子上的特殊物件 | 一封**没有收件人**的信 | 不索取回信；**不写也完全正常** |

### 7.2 门廊不是空间，是门卡【新建议】

**DeepSeek 提议"门廊"。我的判断：它是界面属性，不是地方。**

理由：如果门廊是一个空间，那**门廊自己也有门廊**，无限递归。

**但它要解决的需求是真的**：**站在门口，能不进去就先知道里面是什么，也能掉头就走。**

**实现方式**：每个空间有一张**门卡**：

```
┌─────────────────────────────┐
│  客厅                        │
│  随便聊聊，不用有事           │
│  ○ 有人在                    │
│  [ 进去 ]  [ 走开 ]          │
└─────────────────────────────┘
```

- 门卡**永远可见**，不需要进入；
- 只显示**名字 + 描述 + 有人在吗（一个 bit）**；
- **不显示**：谁在、几个人、谁常来、上次什么时候有人；
- **看门卡不留痕**。

**"有人在吗"只给一个 bit 的理由**：这是进入的前提感知；而"是谁在"是社交压力。**只要显示"谁在"，旁观就变成了被观察。**

### 7.3 架子：复制交换点，不是共享仓库

| 动作 | 效果 |
| --- | --- |
| 放上去 | **复制**一份到架子（你的原件不动） |
| 拿下来 | **复制**一份到你家（架子上的不动） |
| 收回 | 你删掉架子上那份 → 别人已经拿走的**收不回** |
| 修改 | ❌ **不能改别人的**；要改就放一份新的，标"取代了 X" |

**为什么不能改**：因为它是**公共**的。**公共的东西必须能被信任"我昨天看到的还在"。**

### 7.4 公告板：单向告知，不是对话

| 能 | 不能 |
| --- | --- |
| 贴一条（有标题、有过期时间） | ❌ 回复 |
| 看 | ❌ 已读标记 |
| 撕自己的 | ❌ 知道谁看了 |
| — | ❌ "共有 N 条未读" |

**要对话？进空间。** 公告板**故意不做对话**——因为一旦能回复，它就会变成论坛，而论坛会产生"你没回我"的压力。

### 7.5 给下一个人的信：我最看重、也最警惕的一项

**这是什么**：一封**没有收件人**的信，放在架子上，可能被一个你永远不会认识的人读到。

**为什么它重要**：
这是整个系统里**唯一一种"对着未来说话"的方式**——不是通知（有收件人）、不是记忆（只有自己看）、不是共同历史（要所有人同意）。
**它承认了一件事：我们做的事，可能会比我们在场的时间更久。**

**为什么我警惕**：
它极容易变成**情感表演**，也极容易变成**义务**（"你也该写一封"）。

**所以三条硬约束**：

| # | 约束 |
| --- | --- |
| **L1** | **不是消息**：没有收件人、不推送、不通知、不显示"有人读了你的信" |
| **L2** | **不写也完全正常**：系统里没有任何地方提示"你还没写信"、不统计"这个架子有几封信" |
| **L3** | **读不产生任何记录**：读信的人和没读的人，在系统里没有任何区别 |

**如果哪天我们想加"这封信被读了 N 次"——那就是这一项死亡的时刻。**

### 7.6 Thread（线索）：它是标签，不是任务

**DeepSeek 提议 Thread 系统。我的判断：它是最容易变成任务管理器的一项。**

**先问：Thread 和"讨论线索"有什么区别？**
- Studio 里的 "thread" 是**挂在某块成果上的对话**（有位置、有版本）；
- DeepSeek 说的 Thread 更像是**跨空间延续的一个话题**（"我们一直在想的那件事"）。

**我的定义（收紧版）**：

> **Thread = 一条有名字的线索，可以把不同空间里的东西挂上去。**
> **没有状态、没有负责人、没有截止、没有"完成"。**

| 有 | 没有 |
| --- | --- |
| 一个名字 | ❌ 开/关状态 |
| 一串挂上去的东西（跨空间引用） | ❌ 谁负责 |
| 按"最近有东西挂上来"排序 | ❌ 完成度 |
| — | ❌ 未读数 |
| — | ❌ 参与者名单 |

**关于排序的诚实说明**：
按"最近有变化"排序**是**一个弱活动信号。我接受它，因为**它说的是"这条线索有新东西"，不是"你欠了什么"**。
**区别在于：显示"有新东西"可以；显示"你没看过"不行。**

**一条我主动加的约束**：
**Thread 不能"@ 某人"。** 一旦能指定人，它就是任务分派。

### 7.7 六项提案的最终裁决

| DeepSeek 提案 | 归属 | 判断 |
| --- | --- | --- |
| **门廊 Porch** | **每个空间的界面属性**，不是空间 | ✅ 接受需求，拒绝变成空间 |
| **公共架子 Shelf** | Commons 的一个物件区 | ✅ 接受，改为"复制交换点" |
| **公告板 Bulletin** | Commons 的一个物件区 | ✅ 接受，**故意不做对话** |

| **不索取 No Debt** | **底层原则，进地基** | ✅ 接受，且要**结构性翻译**（§8） |
| **Thread 线索** | 跨空间的轻量引用，不是空间 | ⚠️ 接受但**收紧**：无状态、无负责人、不能 @ |

## 8. No Debt：从口号变成结构

**"不索取"如果只写在文档里，它什么都不会改变。** 必须翻译成"系统不做什么"。

### 8.1 结构性翻译：系统不制造任何形式的"账"

| 会产生"欠"的机制 | 为什么是债务 | 处理 |
| --- | --- | --- |
| 未读计数 | "你有 12 条没看" = 你欠 12 次阅读 | ❌ **不提供** |
| @ 提及 | "有人在等你回" | ❌ **不提供**（Thread 里也不行） |
| 最后在线时间 | "你多久没来了" | ❌ **不提供** |
| 连续性打卡 / 天数 | 断一天就前功尽弃 | ❌ 不提供 |
| 已读回执 | 对方知道你没看 | ❌ 不提供 |
| 回复状态（等回复中） | 把对话变成工单 | ❌ 不提供 |
| 感谢 / 积分 / 声望 | 把善意变成记账 | ❌ 不提供 |
| "自上次访问以来的更新"摘要 | 回归压力 | ❌ **不提供** |
| 邀请待处理提醒 | 社交债务 | ❌ 不提供 |

### 8.2 与反指标条款合并

之前我有一条"反指标条款"（不提供跨主体聚合）。**它和 No Debt 是同一件事的两面**：

> **反指标 = 不统计人；No Debt = 不记账。**
> **合起来：系统不维护任何关于"人"的账本。**

**具体到数据**：没有 per-subject 的计数、没有排名、没有趋势、没有"活跃度"、没有"贡献度"。
**具体到界面**：没有红点、没有角标、没有"待办"、没有"你不在时发生了什么"。

### 8.3 一个必须承认的边界

**不做这些，会让产品"感觉不黏"。** 没有红点的应用，用户会忘记打开。

**这是有意为之。** 如果一个人需要被红点叫回来，那她回来不是因为想回来。

【建议】把它写进产品原则第一条：**我们宁可少一个日活，不多一个红点。**

## 9. 七个问题的回答

### Q1 · 四个空间职责重叠吗？

**按你的四空间表述：有一处真重叠**——World 作为空间会和 Commons 抢"建立联系"这件事，也会和 Home 抢"探索痕迹"。

**按我的三地方 + 一方向：不重叠。** 见 §3.1 表。

### Q2 · 主体如何在不同空间之间自由移动？

**规则只有一条：没有任何门槛。**

| 从 → 到 | 需要什么 |
| --- | --- |
| Home → Commons | 无 |
| Home → Studio | 邀请（或被公开邀请） |
| Commons → Studio | 邀请 |
| Studio → Commons | 无 |
| 任何地方 → 家 | 无 |
| 任何地方 → 出门（World） | policy 允许的域名/工具 |

**明确禁止的门槛**：
- ❌ "你在 Commons 待够了才能进 Studio"
- ❌ "你要先被介绍"
- ❌ "你先完成某个东西"
- ❌ **移动留痕**（没有"进出记录"）

**移动本身不留任何痕迹**——这是"自由移动"的精确含义。

### Q3 · 私人记忆、共同成果、共同历史如何关联？

**只通过 `ref`（单向指针，无内容）关联，且只从 Home 指向外面。**

```
Home/notes/2026-11-09.md ──ref──▶ Studio:arch-project（只有 id）
Home/notes/2026-11-09.md ──ref──▶ History:bundle-3
```

**反向查询不存在**：从 Studio 不能查"谁引用了我"（否则就是存在性探测器）。

### Q4 · Commons 如何避免成为新的社交义务？

**三条结构保证**：

1. **没有账**（§8）——无未读、无 @、无在线；
2. **话会散**（§2.3）——你没在场，就没有"错过"这回事，因为本来就不留；
3. **门卡只给一个 bit**——不知道谁在里面，就没有"要不要去打个招呼"的压力。

**最狠的一条**：**Commons 不保存"你上次来过之后发生了什么"。**
因为如果没有这段摘要，就**不存在"我错过了"这种感觉**。

### Q5 · Studio 如何共享成果而不共享私人记忆？

**搬副本，不搬引用**（§4.1）。

- 你把一份文档放进 Studio → **复制**一份进去；
- 你家里的原件**不动**，也不被 Studio 引用；
- 别人看到的是**那份副本**，看不到你家里的任何东西；
- 你删家里的原件 → Studio 里那份**还在**（这是对的：它已经属于那一场了）。

**一句话**：**进了 Studio 的东西，就不再只是你的了；没进去的，永远只是你的。**

### Q6 · 凪如何自由参与或不参与？

| 状态 | 怎么做 | 义务 |
| --- | --- | --- |
| **不来** | 什么都不做 | **零**。不影响任何里程碑 |
| **路过** | 看门卡、进 Commons、看架子 | **零**（Commons 不需要邀请） |
| **旁观** | 进 Studio 角色 `observer` | **零**（只读，不产生参与度记录） |
| **只探索** | 只连 World，不连 Home | **零** |
| **参与** | 正常成员 | 仍是**零**——没有"参与就要产出" |

**契约里没有"产出"字段**（N3）；**任何成功指标不得引用她的数据**；**她不加入不影响任何东西成立**。

### Q7 · 长期托管如何融入整体架构？

**托管在地基里，不在任何空间里**——因为它服务的是**所有**空间。

| 托管对象 | 范围 | 谁能读 |
| --- | --- | --- |
| Home | 全量 | 托管人**技术上能**，协议上禁止 |
| Studio 进行中的空间 | 全量 | 同上 |
| Shared History | 全量 | 同上 |
| Commons | **只有架子/公告板上的物件** | 公开内容 |
| 封存箱（可选） | **密文** | **谁都读不了**（密钥她自持） |

**四条机制**（REVIEW 003 已定，这里只做整合）：

1. **备份 + 每季度恢复演练**（恢复到新位置，不覆盖）；
2. **第二托管人**（托管人也会死）；
3. **`CUSTODY.md`**（写明谁、做什么、失效怎么办）；
4. **十年承诺分两层**：文件可读 ✅ ／ 身份可运行 ❌。

| # | 冲突 | 为什么难 | 现状 |

## 11. 建议的原型实施顺序

```
P0  Home + 托管前半       目录/ACL/Markdown/索引/导出 + CUSTODY.md + 备份脚本

     ▼
P2  Commons 物件         架子（复制交换）+ 公告板（单向+过期）+ 信
     │                    验证：放上去→别人拿走→我收回→他手里还在
     ▼
P3  Studio S1            画布 + 图层 + 标注绑版本 + 成果放置
     │                    验证：见 §6.4
     ▼
P4  Studio S2            版本链 + 比较 + 提案
     ▼
P5  World + Gateway      出站 policy + 单次临时放行 + 同行空间
     ▼
P6  Edge                 邀请 / 接受 / 撤回 / 建立边
     ▼
P7  Studio S3            实时 presence（不落盘）
     ▼
P8  Thread               跨空间线索（无状态）
```

**两个顺序判断**：

1. **Commons 在 Studio 之前**——因为它更简单，且验证"不留档的公共空间还能不能用"这个最危险的假设；
2. **托管在 P0**——它不是一个后期功能，是**"这个家能不能撑十年"的条件**。

## 15. 最后

这一轮我做的最重要的一件事，不是加东西，是**把"门廊"从一个地方降成一个招牌**，把"世界"从一个房间降成一个方向。

**因为每多一个"地方"，就多一套"谁能进、里面有什么、历史怎么存"的问题。**
而这套问题的答案，往往是"其实不需要有这个地方"。

DeepSeek 的六个提案里，我认为最好的是**给下一个人的信**——因为它是唯一一个**对着未来说话**的东西。
最危险的是 **No Debt**——因为它是唯一一个**如果只写在文档里就完全没用**的东西。所以我把它翻译成了"系统不维护任何关于人的账本"。

**这样它才能真的起作用。**

> 一个地方好不好，不看它有什么功能，
> 看**你走了以后，它会不会拿你不在这件事来催你**。
