## 真人首次使用观察

至少由一名真正没有使用过本产品的人完成一次观察，记录其产品接触史；若由开发者代演，只能记工程走查。需要更多人时另记收益与安排，不把“人数更多”变成当前无限延期条件。全程使用独立虚构预览与模拟对象，不使用原Agent会话或主数据库。

事前给出任务目标，不先讲解按钮路径或自然命令精确句式。参与者知情同意后，观察者可记录操作及原话；不默认录屏或收集无关个人信息。参与者卡住时先记录，再按其请求帮助，不能把帮助后的完成算成独立完成。

| 场景 | 观察重点 | 应留证据 |
|---|---|---|
| 打开新版，创建/切换两个虚构会话 | 是否知道当前项目、会话、模拟身份和接收者；旧草稿是否还在 | 操作起止、求助、错误选择、实际草稿/范围结果 |
| 发普通消息、回复一条Agent消息 | 是否找到统一输入与原作者；普通交流是否被多项表单打断 | 参与者原命令、实际接收者和原消息关联 |
| 用自己的话安排一负责人、一复核者 | 是否理解“负责人排队→有效结果→复核”；未支持句式是否明确未执行 | 真实Task/Plan ID、状态变化、必要澄清及是否误以为已完成 |
| 对明确选中材料请求复核 | 是否复用已知对象；文字审查与工程材料Host边界是否说清 | 所选来源/版本、实际动作或阻断原因，不以界面点通代替业务结果 |
| 查看暂停、UNKNOWN或缺收件结果 | 能否发现异常并知道未确认、不应重发 | 参与者解释、是否尝试误操作、是否找到详情/停止入口 |
| 切换主题/会话/窗口并恢复草稿 | 输入、回复、知识引用和接收者是否保持且不串线 | 前后内容与选择、主题路径、未发送状态 |

分别记录：独立完成、帮助后完成、未完成、错误执行；耗时、误点和求助是观察数据，不单独证明可用性。任务失败或参与者认为“已收到/已完成/已授权”而实际没有证据时，须按具体问题记录，不能用总体满意掩盖。

当前关键场景须有真实观察结果，且不能存在未解决的错投、草稿丢失、无法识别UNKNOWN或虚报执行。纯偏好建议与P2/P3分开登记，不重复推翻已经验收的布局；新功能另立Task。修复只对相应问题复验，必要独立复核按风险安排，不默认再开三方评审。

## 实际125%/150%DPI检查

建立物理设备记录：Windows版本、显示器/有效分辨率、实际系统缩放、应用实际DPI及可用窗口范围。设备若不支持某个组合，记NOT_TESTED，不以缩放图片、改RenderTargetBitmap尺寸或进程模拟参数补票。

| 检查比例 | 检查要求 | 当前证据状态 |
|---|---|---|
| 100%参考 | 用实际设备检查主流程，并与已有原生自检对照 | 已有原生自检/渲染，不直接宣称本真人设备场景通过 |
| 125%实际Windows缩放 | 用户在选定设备设置，按Windows要求重新打开应用后核对实际DPI | NOT_TESTED |
| 150%实际Windows缩放 | 同上；另检查较小有效工作区和右栏折叠 | NOT_TESTED |

每种可用比例都检查：1920×1080与1366×768场景在该设备是否实际可用、窄窗、长中文/代码、多行输入、按钮/发送可达、对话框、键盘焦点/Tab顺序、列表选中、滚动、深浅色、右侧上下文收起后的异常可见性。物理尺寸组合不可实现时明确列出实际覆盖范围。

测试前由用户记录原显示设置及恢复方式；此次计划不更改设置。后续只有取得该具体设备/显示设置操作许可后才调整，完成后恢复原比例并核对。证据可采用用户提供的仅应用区域截图或获准观察；自动审批拒绝时不换通道绕过。RenderTargetBitmap继续标为应用自渲染，不能称为桌面截图。

## 主平台切换前置条件

“新版可以运行”和“允许替换主平台”是两个决定。先形成具体可审阅的切换包，注明候选ID、exe/依赖hash、数据版本、拟切换入口、预计影响和回退目标，再请求用户确认实际变更。

| 前置项 | 可核对产物 | 未满足时 |
|---|---|---|
| 当前冻结版本技术验收 | 同候选完整回归、原生集成、独立复核、最终真实一小时runId与verifier结果 | 一小时RUNNING/旧构建证据不能放行 |
| 关键体验与实际DPI | 上述参与者观察及实际覆盖矩阵、已处理关键问题 | 保留独立候选，不冒称真人或全DPI已通过；未测项须显式决策 |
| 数据兼容与恢复演练 | 主库副本上的Schema/数据版本核对、消息/材料/计划/草稿计数与抽样、备份恢复演练记录 | 不迁移主库，不让旧调度器读取含新版未完成计划的数据 |
| 运行与身份边界 | 旧/新后台、端口、锁、进程、队列、暂停与绑定的明确映射 | 不能按进程名批量停止，不从候选健康推断原Agent在线 |
| 回退所需旧版本与数据 | 旧exe、匹配XAML/源码/依赖、配置及一致性数据快照，恢复步骤与校验 | 不能只换旧exe加载新版布局，不能覆盖运行中的库或程序 |
| 具体用户决定 | 批准的切换对象、数据范围、时间、允许动作及遇错停止条件 | 技术审议或自然赞同不代替实际切换授权 |

副本上的兼容检查和演练也须有明确源/目标路径，避免把测试步骤误用于主库。若方案证明无需Schema迁移，仍要核对新版记录与旧版本的读取/调度行为；“无迁移”不等于可任意降级数据。

真实会话绑定、常驻恢复和附件自动化不包含在一般切换许可中。即使本机UI/数据库切换获批，原真实队列仍保持暂停，直到对具体原会话、待发事项、预算和草稿互斥另行确认；不自动接管凪。

## 拟定切换与回退顺序（当前不执行）

1. 冻结可审阅清单并核对上述前置；记录仍未验证项、用户接受的限制与实际操作范围。
2. 在获批时间仅停止明确指定的新旧写入方；确认没有仍在写入的进程，保留已提交未明的UNKNOWN及原attempt ID，不清队列。
3. 取得一致性备份并验证可恢复；在已批准的副本上完成迁移/兼容核对。失败就停止，保留原平台运行方案，不覆盖现场。
4. 按具体许可改变入口/配置/数据指向，先以暂停或不提交状态启动，只核对身份、数据和版本；少量已授权验证通过后才决定后续运行。
5. 若错库、错版本、来源/队列不一致、重复提交、草稿丢失或关键体验阻断出现，停止该候选。保留新增消息与失败证据，在另一个隔离目录用完整旧版本与备份恢复核验，再按授权恢复旧入口。

回退不删除新版新增数据，不把旧备份直接覆盖回仍有新写入的原目录。新增记录如何保留/对账、UNKNOWN如何核对、哪个版本接管哪些队列，须在切换包中明确；不能声称已具备无损自动双向降级。参照现有[停止及并存操作](OPERATIONS.md)，未来真实主平台操作另列精确路径。
