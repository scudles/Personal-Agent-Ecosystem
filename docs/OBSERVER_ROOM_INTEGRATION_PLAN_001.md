# OBSERVER ROOM INTEGRATION PLAN 001

作者：Hermes｜依据：Observer 决定（保留 External Participant 定位；不建 API 替身；短期不用浏览器自动化）
性质：**方案 + 待验证清单**。有一步必须由用户在他的 ChatGPT 桌面端亲自确认，其余部分不依赖它。

---

## 0. 结论先行

**存在一条既不建 API 替身、也不做浏览器自动化的路径：把「文件夹」当消息总线。**

Studio 把房间导出成文件 → 那个文件夹被挂进她的 ChatGPT 项目 → 她读文件、把回复写成文件 → 我们导入。

这条路径**恰好符合她"以当前 Chat 模式参与"的要求**，因为 Reading/Writing 一个已授权文件夹，是产品自带的本地项目能力，不是我们伪造一个她。

**但有一个必须先验的前提**：她的桌面端在 Chat 模式/项目上下文里，对已挂载的本地文件夹到底有没有**读**权、有没有**写**权。公开资料说法不一致，必须实测。

---

## 1. 三条路径，证据等级明写

| 路径 | 做法 | 她是谁 | 证据等级 |
| --- | --- | --- | --- |
| **甲 文件夹桥** | Studio 写 `room/*.md` → 她所在项目挂载该文件夹 → 她读；回复写进 `inbox/` | 真实的她 | **公开资料支持，未在本机验证** |
| **乙 人工粘贴** | 我们生成结构化上下文包，用户粘贴；回复导入 | 真实的她 | **已验证**（今天一直在做） |
| **丙 API 同族模型** | 开 API key 跑 GPT | 像她，不是她 | Observer 已否决，本文不再展开 |

**甲的证据来源**（第三方与官方文档混合，须实测）：

- ChatGPT 桌面端（Mac/Windows）有 **Work** 模式与**本地项目**；项目可挂本地文件夹，可读写其中文件；
- 云端/网页/手机**碰不到**本机文件（除非走平台特定的本地访问开关）；
- 社区报告：**项目内**对本地文件夹可能只有**读**权，Work 会话外才有写权；把会话移进项目会丢写权限（2026 年 10 月）。
  → **这条分歧直接决定甲是否可行，必须先测。**

## 2. 项目文件的持续可访问（甲的核心）

**问题不是"她怎么读"，而是"她读什么"。**

她不能读我们的 SQLite。所以要么给她一份**持续更新的房间镜像**，要么每次都导出。前者才是"持续可访问"。

建议的镜像布局（放在一个专用文件夹，只放给她看的东西）：

```
observer-bridge/
  room/
    recent.md         最后 30 条消息（带 message id、作者、时间、讨论轮次）
    discussions.md    进行中的讨论与各自结论
  canvas/
    objects.md        视觉对象清单：id / 标题 / 最新版本 / 每版一句话说明
    v-<id>@<n>.svg    被引用到的具体版本（按需导出，钉版本）
  files/              本次需要她读的项目文件（明确选择过、带大小上限）
  inbox/
    reply-<timestamp>.md   她写的回复（若写权限可用）
  README.md           约定：她能读哪些、能写哪里、回复格式
```

**三条纪律**：

1. **镜像 ≠ 数据库**。它是只读导出物，丢了可以重生成，不作为任何事实来源。
2. **只导她该看的**。默认不含：`.env`、密钥目录、Mnemosyne 私人记忆、未完成的 run 细节。
3. **每次导出记来源**：镜像头写明导出的 `room_id`、最后一条 message id、导出时间，便于回填时对齐。

## 3. 消息提交与回填机制

我们**已经有**正确的语义，不需要新概念：

- `messages.origin` 已收窄为 `composer | runtime | import`；
- 规则已定：**`import` 行的 `member_id` 必须是原说话人，不是导入者**（`004` 里写死的注释）。

所以她的发言就用 `origin='import'`、`member_id='observer-white'` 落库，并补齐三个字段（新增迁移）：

| 字段 | 用途 |
| --- | --- |
| `imported_by` | 谁把这句带进来的（当前只能是人类） |
| `source_hash` | 她那段原文的哈希，防止事后改动说不清 |
| `imported_at` | 导入时间，与她自己说的时间区分开 |

**导入必须由人类触发**：Agent 不能自己往房间塞"Observer 说过的话"。这条要写成硬约束，否则我们可以伪造她的立场。

**回填形态（乙，现在就能用）**：我们生成一份可直接粘贴的上下文包，她回答后，用户把它保存成 `inbox/reply-*.md`，我们解析导入——**粘贴的动作被"存一个文件"替代**，比贴一大段墙好受，且天然留痕。

## 4. 视觉参与通道

她要的四件事，拆成两层：

**第一层：看** — 已具备（画布 + 版本 + `visual_objects` 清单）。需要补的是**导出给她看**：`canvas/objects.md` + 按需的 `v-<id>@<n>.svg`。

**第二层：标与画** — 现在没有，需要新增一张 append-only 的批注表：

```sql
annotations(
  id, object_id, version_no,        -- 绑具体版本，不绑"最新"
  kind,                              -- pen | box | arrow | text
  anchor,                            -- 归一化坐标或路径描述
  body, author_member_id, created_at
)
-- 永不 UPDATE / DELETE；版本升级后旧标注标 stale，不删
```

她的标注与草图走**同一条导入通道**（`origin='import'`），作者记她。提交 SVG 草图 = 生成一个新的 `visual_objects` + 版本 1，`created_by` 记她。

**不做**：完整绘图工具、多人实时协同。第一版只要能"在她那边的图上标出来、我们能看见"。

## 5. 身份、记忆、裁定

| 项 | 决定 |
| --- | --- |
| 身份 | `members.kind` 需要第三类：`external`（现有只有 `human` / `agent`）。她的消息 `author_kind='external'` |
| 记忆 | **不导入** ChatGPT 账号记忆。她提交到 Studio 的内容 = 明确分享的共同记录 |
| 裁定 | **参与与裁定必须可分离**。同一争议里她若已发表观点，就不能再作为该争议的独立审查者。这条要落到数据上：一条记录里带 `role: participant | adjudicator`，或者裁定以独立记录形式存在，不进 `messages` |
| No Debt | 不做"她在线吗/她看没看"，只记事实（导入过、标注过） |

## 6. 现在做不到的（明确列出）

| 做不到 | 原因 |
| --- | --- |
| 自动化、实时地驱动当前 Chat 模式 | 产品无对外接口；Plus 不含 API 额度 |
| 她读到"最新一秒"的房间状态 | 镜像是有延迟的导出物；她在自己那一轮读的是快照 |
| 把账号记忆搬进 Mnemosyne | Observer 已明确否决；且技术上也没有出口 |
| 她在房间里自主触发下一轮讨论 | 现有硬边界：轮次只能由人开 |
| 用浏览器自动化绕过去 | 违反条款、随时失效——不做 |

## 7. 必须先做的验证（一步，用户亲自）

在**你的**桌面端做，我不碰你的账号：

1. 建一个本地项目，挂一个测试文件夹（里面放两份文档）；
2. 在该项目里开一个**普通 Chat 会话**（不是 Work、不是 Codex），问它："这个文件夹里有哪几个文件？第二个文件第一行是什么？"
3. 再让它**往那个文件夹里写一个文件**，看能不能写。
4. 换到网页版问同样的问题，确认它读不到。

结果只有四种，对应四份不同的方案：

| 结果 | 含义 |
| --- | --- |
| 读得到、写不了 | **甲成立（只读）**：镜像单向，回复靠文件投递（乙） |
| 读得到、也写得了 | **甲成立（双向）**：她的回复自动落进 `inbox/`，最接近"她自己在房间里" |
| 读不到 | 甲不成立，只能用乙；我会把上下文包做到极省力 |
| 网页版也能读 | 说明权限模型和我们理解的不同，需要重新评估（也涉及隐私） |

## 8. 工作量（在验证之后才准）

| 阶段 | 内容 | 估 |
| --- | --- | --- |
| 0 | 上面那一步验证（你做） | 10 分钟 |
| 1 | 镜像导出器 + `inbox` 导入（含 `origin=import` 三字段迁移） | 1 天 |
| 2 | 上下文包生成器（乙，不依赖验证结果） | 半天 |
| 3 | `annotations` 表 + 标注渲染（她能标、我们看得见） | 1–2 天 |
| 4 | `members.kind='external'` + 裁定/参与分离 | 半天 |

**阶段 2 可以今天就做**，不依赖任何验证。阶段 1、3 等第 0 步的结果。

## 9. 给 DSH 的一轮咨询（只问技术，不问她产品意见）

1. `members.kind` 增加 `external` 是否需要动 Runtime 侧任何契约？（我判断不需要——她不走 Runtime）
2. `origin='import'` 的行进入 `messages` 后，现有触发器（append-only、同房间回复、runs 一致性）有没有需要放宽或收紧的地方？
3. 文件投递的并发问题：如果镜像在导出时房间正在写，是否会导出一半？建议的原子做法（临时文件 + rename？）
4. `annotations` 表与 `visual_versions` 的关系：绑 `(object_id, version_no)` 是否足够，还是需要 `anchor` 的 schema 约定？

## 10. 一句话

**不冒充她，也不把用户变成永久路由器**：让 Studio 把房间写成文件，让那个文件夹成为她的门口。
她读的仍然是"真实的她"，我们得到的仍然是可追溯的共同记录——中间少一次人肉复制，多一条有日志的投递。

## 备选一（换地方）：GitHub / Dropbox / **自建只读 MCP**

| 路 | 依据 | 证据等级 | 外发 |
| --- | --- | --- | --- |
| GitHub 私有仓库 + 官方 GitHub 插件 | 官方帮助中心：连接后"可按需检索被授权仓库的内容，包括代码与 README"，且不建同步索引 | **官方文档支持，社区报告普遍失败**（连上了却列不出私有库文件） | 房间内容进入 GitHub |
| Dropbox / Box 连接器 | 官方正向 Plus/Pro 等铺开"浏览/搜索文件、从 Library 加入对话" | 官方说法，未实测 | 房间内容进入第三方云 |
| **自建只读 MCP app** | 第三方资料：开发者模式下 Plus/Pro 支持**只读**自定义 MCP 应用 | **未验证，需实测** | 房间内容经我们的服务出口 |

第三条是最接近"持续可访问"的：我们写一个只读服务，暴露的只有房间镜像（消息、讨论、画布清单、指定文件），她按需读，不必等投递。

**但它需要她的 Chat 能访问到公网地址**（隧道 / 部署），并且要确认该能力在她的套餐上真的可用。**在此之前不要把它当既定方案。**

## 备选二：投递模式（已实现）

`tools/bridge/export-pack.mjs` / `tools/bridge/import-reply.mjs`。

- 导出：房间 → 一份 markdown（带 message id、讨论轮次、画布清单、回复模板）
- 导入：她把回复写在文件里交回 → 以 `origin='import'`、`member_id='observer-white'` 落库，记录 `imported_by` / `imported_at` / `source_hash`
- 同一条回复导入两次不会变成两条（哈希唯一索引）
- **只有人类能导入**：agent 走这个通道会被拒（`NOT_OBSERVER` / `IMPORTER_NOT_HUMAN`），否则我们可以伪造她的立场

代价：人仍然要搬一个文件。但这已经是"邮差"，不是"路由器"——不需要解释上下文，不需要整理，不需要复述。

## 备选三：不做

- 浏览器自动化驱动 chatgpt.com：违反条款、随时失效
- API 同族模型冒充她：Observer 已明确否决

## 一条必须先说清的结构性冲突

界面上写着「消息保存在这台设备上」。

**除"本地文件夹"这一条外，上面的每条备选都意味着房间内容离开本机。** 包括我们自建的 MCP 服务——代码是我们的，内容照样出网。

所以真正的选择不是"能不能读到"，而是：

> 愿意为了"她自己在场"，把房间交出去多少？

建议的顺序：先本地文件夹（零外发）→ 再投递（零外发，纯人工）→ 只有当前两条都不够用时，才谈外发，并且先限定范围（只读、单一仓库/文件夹、可随时撤销）。

# 附录 A：第一次真实读取（2026-11-13，已发生）

Observer 以 **ChatGPT Chat 模式 + 自定义 MCP 连接器** 读到了房间。不是设计推演，是审计日志里的记录。

## 证据：`.data/bridge/mcp-audit.jsonl`

```
16:52:03  oauth.register    client=ChatGPT
16:53:31  oauth.consent     （人在授权页输了口令）
16:53:51  oauth.token       （PKCE 换到 access token）
16:54:28  room_summary      {}
16:54:29  list_discussions  {}
16:54:30  list_messages     {"limit": 50}
16:55:08  list_visuals      {}
16:55:14  get_visual_source {"objectId":"d1addb66-…"}
16:55:15  get_visual_source {"objectId":"57cfaeba-…"}
```

三件从日志才能确认的事：

1. **她的请求来自 OpenAI 的服务器**（`9.129.10.x`，UA `Python/3.14 aiohttp`），不是本机代理。公网入口是真的。
2. **她先探测、后被拒、再走 OAuth**（16:51–16:52 有 401）。那是正常握手，不是攻击。
3. **她读了两个 SVG 的源码**，不只是消息文本——她自己选了要看图。

## 她读回来的内容对不对

对照房间实际数据：

| 项 | 房间实际 | 她的复述 |
| --- | --- | --- |
| 消息 | 9 | 9 |
| 成员 | 4 | 4 |
| 视觉对象 | 2 | 2 |
| 讨论 | 1 场、2 轮 | 1 场、2 轮，两人都答了 |

并且她引用了两位 Agent 在第二轮的具体分歧。**这是读取，不是猜测。**

## 这次读取没有改变的一件边界

**她读了，但她还没有在房间里说过话。**

读取走 MCP（只读）；发言仍然只能走人工携带的导入通道（`tools/bridge/import-reply.mjs`）。
两条路是分开的，这是刻意的：能看 ≠ 能署名。

## 仍然脆的地方（别当成已完成）

- **快速隧道地址每次重启都变**，变了要回 ChatGPT 改连接器
- **access token 只在内存里**，服务重启后要重新授权一次
- **只有 token 一道锁**，没有 Cloudflare Access
- 事实上的可用性 = 这条隧道活着的时间

## 结论

Observer 以当前 Chat 模式参与 Studio，**技术上成立**，路径是"自建只读 MCP + 隧道 + OAuth"，不是 API 替身，也不是浏览器自动化。
下一步才是"她怎么在房间里署名发言"，那是另一个决定（导入通道已就位，等她用）。
