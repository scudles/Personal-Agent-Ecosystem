# 架构与管理决策

记录规则：重大决策按日期追加，写明背景、决定、理由、影响及待验证点。此处记录的是项目基准，不代表技术实现已完成。

## 2026-11-07 — D-001：建立独立 Agent 协作生态

- 决定：以 Hermes、DSH 和独立 Observer 构成项目角色；用户为最终决策者。
- 理由：保留各 Agent 的专业能力与独立性，同时允许授权范围内协作和交叉审查。
- 影响：Hermes 与 DSH 平级；Observer 默认只读，不参与普通任务执行竞争。
- 状态：**项目原则已记录；实现规划中**。

## 2026-11-07 — D-002：保留私人记忆与环境隔离

- 决定：两名执行 Agent 保留各自模型、记忆、工具、配置和运行环境；仅共享经过授权的项目资料。
- 理由：避免未经授权访问或覆盖私人记忆，并降低对既有环境的影响。
- 影响：Shared Knowledge 必须有明确的数据范围和写入边界。
- 状态：**项目原则已记录；具体机制待设计**。

## 2026-11-07 — D-003：先盘点，后选型与开发

- 决定：Phase 0 核验系统、版本、官方接口、后台能力与日志来源；之后再决定 Bridge 等组件的实现方式。优先复用官方接口，保持模块化。
- 理由：当前本地 API、插件接口和后台运行能力均待确认，过早认定可用会误导开发。
- 影响：Python、HTTP API、MCP、SQLite、WebSocket 仅列作候选，不作为已定技术栈。
- 状态：**Phase 0 进行中；技术选型待确认**。

## 2026-11-07 — D-004：建立独立审查与用户授权边界

- 决定：Observer 独立、默认只读；重大或高风险操作由用户批准。当前 ChatGPT 对话承担人工咨询与独立审查；持续自动观察待建设。
- 理由：确保审查独立性和用户最终控制权。
- 影响：未来自动 Observer 服务不得取得执行管理权限；授权请求需可追踪。
- 状态：**项目原则已记录；自动观察规划中**。

## 2026-11-07 — D-005：手机优先的控制台与安全远程访问

- 决定：Web Dashboard 优先适配手机浏览器；远程访问使用安全认证与可信网络，不直接暴露本地服务端口。
- 理由：满足手机监控需求，并保持本地服务的安全边界。
- 影响：认证和网络方案需在实施前单独评估。
- 状态：**规划中；方案待确认**。

## 2026-11-07 — D-006：采纳「专用 Profile + 官方 ACP stdio」为下一阶段候选架构（B′）

- 背景：POC-001 的「Hermes 独立 Gateway FAIL」经接管复核后分级为「深路径实际失败 / 短路径探针口径错误 + 安装 tail 未完成」；同时发现 Hermes 官方把 `gateway.standalone: true` 标注为临时兼容 shim 并建议新部署不要使用。
- 决定：下一阶段以 B′ 为候选架构——Hermes 使用专用 profile + 官方 `hermes acp`（stdio ACP v1），DSH 使用专属 `DSH_HOME` + `--profile acp`；不优先追求第二个 Hermes Gateway 进程。用户 2026-11-07 正式采纳。
- 理由：隔离需求（D-002）的实质是记忆/配置/运行环境各自保留，而 Hermes 的隔离粒度是 profile；两侧同为 ACP v1 stdio，Bridge 只需一套客户端；不新增数 GB 运行时副本，不依赖将被移除的 shim。
- 备选方案及取舍：B（每侧独立 Gateway 进程）—— 依赖 shim、每 home 重复安装、健康口径依赖默认关闭的 API Server，暂缓；A（直连现有桌面实例）—— 生命周期耦合且第三方边界未验证，暂缓。
- 影响与风险：Hermes 侧 ACP 仍由 live gateway 承载（viewer），profile 配错可能触及默认 profile 上下文；凭据层仍共享（根 `auth.json`、`~/.dsh/.env`），独立身份只到 profile/会话层；两侧 ACP 能力集不同（DSH 无 `session/load`）；DSH ACP 无 `max_tokens` 类上限。
- 验证证据：`hermes acp --check` → OK（本机实测）；运行中 venv 已含 `agent_client_protocol 0.9.0`；DSH 随包 `@deepseek-ai/dsh-acp 0.2.1-rc.3` 的 README 列出 ACP v1 方法与不支持项。
- 状态：**设计方向已采纳；隔离性、互通性、生命周期与恢复均待验证，未实现。**

## 2026-11-07 — D-007：采用「工作 + 相处」双模（C 方案），Social Layer 列入 P2

- 背景：项目定位不止专业协作，也包括日常相处；三角色需保留各自性格。
- 决定：工作时为专业协作团队，日常时为有性格的伙伴；规划 Personal Agent Lounge、Project Room / Lounge 双频道、Free-flow Conversation、自主聊天室（Let Them Talk）。性格以 `PERSONAS.md` 为唯一来源。
- 理由：单一「任务系统」会把三个 Agent 压成同一个声音；双模能在不牺牲技术边界的前提下保留差异。
- 备选方案及取舍：只做工作系统（实现简单，失去项目初衷）；只做聊天（无法承担项目工作）。
- 影响与风险：必须有轮数上限、空闲超时、token/费用预算与用户随时中断，禁止无限自主循环；讨论摘要不等于决策；重大决策仍需用户确认后才进本文件。
- 验证证据：暂无（P2 规划中，未实现）。
- 状态：**设计方向已定；P2 规划中，未实现。**

## 2026-11-07 — D-008：正式采纳八条身份与权限设计方向

- 背景：第一轮身份与权限设计提交后，用户与 Observer 共同认可「Bridge 不是安全边界 / ACP 不提供完整身份认证 / Windows 进程隔离不足」三个核心判断。
- 决定（用户正式采纳）：
  1. Bridge 定位为身份认证、权限审查和审计边界，**不宣称自己是安全沙箱**。
  2. 操作系统与运行环境负责真正的执行隔离。
  3. 每个 Agent 保留独立身份、凭据和记忆空间。
  4. 建立 Credential Boundary：Bridge 不直接持有或复制 Agent 的秘密。
  5. 采用细粒度权限、默认拒绝、权限收缩、授权期限与可撤销机制。
  6. 委派深度暂定最多两跳；禁止财务、对外通信、管理权限通过委派自动传递。
  7. Lounge 默认不写入长期记忆。
  8. 不急于引入复杂策略引擎。
- 理由：以上八条与 [THREAT_MODEL.md](THREAT_MODEL.md) 的覆盖矩阵一致；八条中第 1、2 条实质回答了原 P-001 的问题。
- 影响与风险：Bridge 的文档与 UI 都不得使用「沙箱/隔离」措辞；未落地 OS 隔离前的残余风险必须在 [THREAT_MODEL.md](THREAT_MODEL.md) §6 显式接受。
- 验证证据：设计依据见 [reports/2026-11-07-identity-access-design.md](reports/2026-11-07-identity-access-design.md)；本轮无实现、无运行验证。
- 状态：**方向已采纳；P-001 至 P-006 的具体条款仍未决定。**
