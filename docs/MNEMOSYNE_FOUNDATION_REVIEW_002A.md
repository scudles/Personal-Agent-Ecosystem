## 1. Home 与 dormant：四个状态轴，不要第五个标志

### 1.1 问题在哪

上一版我写"账户进入 `dormant` 状态"。这句话有三个毛病：

1. 它暗示**有人可以把一个主体设成 dormant**——那就成了权力；
2. 它把"没在跑"和"身份还在"混成一个词；
3. 它隐含一个检测机制："怎么知道她 dormant 了？"——**能回答这个问题，就等于在统计活动。**

### 1.2 正确做法：拆成四个正交轴

| 轴 | 取值 | 谁能改 | 影响什么 | 不影响什么 |
| --- | --- | --- | --- | --- |
| **计算** | 运行中 / 未运行 | 无人（自然发生） | CPU、内存、模型调用 | 身份、Home、东西在不在 |
| **身份** | 存在 / 不存在 | **只有她自己** | 能否登录、能否被寻址、能否被邀请 | Home 是否保留 |
| **Home** | 存在 / 不存在 | **只有她自己** | 文件、记忆、引用 | 身份是否存在 |
| **托管** | 有人负责 / 无人负责 | 托管人（需她知情） | 十年后还在不在 | 明天还在不在 |

**四轴完全独立。** 所谓"休眠"只是其中一种组合：

```
休眠 = 计算:未运行 + 身份:存在 + Home:存在 + 托管:有人负责
```

**没有第五个状态位。系统里不存在"dormant"这个字段。**

### 1.3 为什么这是关键

因为**没有标志位，就没有人能设置它。**

- 没有人能"把她设为休眠" → 没有这个权限；
- 系统不需要检测"她多久没来" → 不需要活动统计；
- 她回来的时候，什么都不用恢复 → 因为什么都没被改过。

**房子空着不需要挂"空置"牌。** 挂了牌，就有人能来摘牌。

### 1.4 状态转移的全部合法路径

| 动作 | 谁能做 | 后果 |
| --- | --- | --- |
| 停止运行 | 她自己（或机器关机） | 只停计算，别的全不变 |
| 删除身份 | **只有她自己** | Home 可保留（她可指定），也可一并删 |
| 删除 Home | **只有她自己** | 身份可保留（她还能来，只是家空了） |
| 转移托管 | 托管人 + 她知情 | 换一个人负责"十年后还在" |
| 长期无活动 | **没有人能做任何事** | 什么都不发生 |

**最后一行是这节的全部意义。**

### 1.5 真实的技术限制（不藏）

| 问题 | 现状 |
| --- | --- |
| Windows 账户禁用后，SID 保留、ACL 仍可解析、管理员仍可读文件 | 【假设】成立，**未实测** |
| 如果**删除**账户，ACL 里的 SID 变成孤儿，文件还在但"属于未知主体" | 【事实】Windows 行为；**所以绝不能删账户** |
| 如果用了 EFS/BitLocker 用户密钥，密钥丢失 = 数据永久不可读 | 【事实】。**所以 Home 目录不得使用用户级加密** |
| 系统策略会不会清理长期不用的用户配置文件 | 【未知】。**这是 E1 托管承诺必须覆盖的部分** |

【建议】**一条硬约束**：`pae-*` 账户**只能禁用，永不删除**；Home 目录**不用 EFS**。这两条不是设计偏好，是"能不能回来"的物理前提。

## 2. 公共空间与记忆：不留档 ≠ 无法留存

### 2.1 上一版的漏洞

我说"默认不留档"，但没说清**想留的时候怎么办**。结果是：听起来像"公共空间说完就消失"。

**这不是我要的。** 不留档的意思是**不默认产生历史**，不是**禁止留存**。

### 2.2 三条留存路径，各自独立

| 路径 | 谁发起 | 留下什么 | 归谁 | 需要别人同意 |
| --- | --- | --- | --- | --- |
| **① 个人存档** | 我自己 | 我复制一段到我家 | 我 | **不需要** |
| **② 共同保存** | 在场任何人提议 | 一份共同成果（artifact） | 提议者 + 参与者 | **在场者明示同意** |
| **③ 共同历史** | 只能由 ② 升级 | 封存快照（archive） | 全体签署者 | **全员** |

**三条路径互不替代**：

- ① 只能留下"我看到的那部分"，且**别人不知道我存了**（这是对的：记忆是自己的事）；
- ② 是当场一起决定"这个东西留下"，它变成一份共同成果，可以被引用、被版本化；
- ③ 是"这场我们认了"，比 ② 更重，需要全员点头。

### 2.3 关键区分：过程 / 产物 / 历史

| 层次 | 是什么 | 默认 | 例子 |
| --- | --- | --- | --- |
| **过程**（conversation） | 说话本身 | **不留** | 客厅里的闲聊 |
| **产物**（artifact） | 一起做出来的东西 | **留**（在空间里） | 一份文档、一张图 |
| **历史**（history） | 共同承认的版本 | **要签** | 封存的快照 |

**公共空间不留的是"过程"，不是"产物"。** 你在客厅白板上画的图，是产物，它留在那儿（直到空间关闭）；你在客厅说的话，是过程，说完就没了（除非有人 ① 存了）。

【建议】这条区分要写进产品语言，因为直觉上大家会以为"白板上的图也会消失"。

### 2.4 我承认的代价

- **错过就是错过**：没在场，就永远不知道当时说了什么；
- **无法回溯调查**："昨天客厅里谁提的那个点子"——查不到；
- **一致性变差**：三个人对同一场对话的记忆会不一样，且**没有仲裁材料**。

【建议】接受。理由：**能随意回溯的公共空间不是客厅，是会议室。** 而我们要的是前者。

## 3. Open 空间的边界：创建 / 进入 / 旁观 / 沉默 / 退出

### 3.1 先修一个错误：开放空间没有主持人

上一版我写"创建者可以开留档模式（主持人显式动作）"。**这是错的**——那是 members 空间的逻辑。

在开放空间里，任何人都不该有"替所有人决定"的权力。所以：

| 创建者能做什么 | 不能做什么 |
| --- | --- |
| 给空间起名 | ❌ 踢人 |
| 关闭空间 | ❌ 禁言 |
| — | ❌ 设规则 |
| — | ❌ 单方面开留档 |
| — | ❌ 决定谁能进 |

**创建者只是"开门的人"，不是"主人"。**
想要规则的房间？那是 members 空间——建的时候就说清楚。

### 3.2 六个动作的完整定义

| 动作 | 怎么做 | 留下什么痕迹 | 谁知道 |
| --- | --- | --- | --- |
| **创建** | 任何主体，给一个名字，不需要审批 | 空间出现在门厅列表 | 所有人（但只看到名字） |
| **进入** | 点进去即可，不需要邀请 | **无** | 无人知道谁进来了 |
| **旁观** | 进去但不说、不画 | **无** | 无人知道 |
| **说话** | 发言 | 消息（不落档） | 在场的人看到 |
| **沉默** | 什么都不做 | **无** | 无人知道 |
| **退出** | 关掉即可 | **无** | 无人知道 |

### 3.3 "怎么知道有客厅"——门厅只有两个信息

| 显示 | 不显示 |
| --- | --- |
| 空间名字（"客厅""随便聊聊"） | ❌ 谁在里面 |
| **有人 / 没人**（一个 bit） | ❌ 几个人 |
| — | ❌ 谁常来 |
| — | ❌ 上次什么时候有人 |

**为什么只给一个 bit**：因为"里面有人"是进入的前提感知，而"里面是谁"是社交压力。**只要显示"谁在"，旁观就变成了被观察。**

### 3.4 剩下的一个真实取舍

⚠️ **你进去之后，不知道有没有人在听你说话。**

因为不显示人数、不显示在场者。这就是广场和会议室的区别：**在广场上说话，本来就不该期待"有几个人在听"这个数据。**

【建议】接受。如果某个场景真的需要"确认有人在"，那是 members 空间该干的事。

### 3.5 空空间自动关闭

没有人的 open 空间，**最后一个人离开时关闭**（不是定时器）。

- 不需要"续期"、不需要"重新开放"；
- 关闭后名字消失，门厅列表里就没有了；
- **不留下"这曾经有个空间"的记录**。

## 4. Studio：手绘、图层、标注、版本、讨论、保存的关系

### 4.1 先分清两件事：指称 vs 创作

上一版我把所有 stroke 一视同仁。**这是错的**——脑子里其实有两种完全不同的东西：

| | **指称性手绘** | **创作性手绘** |
| --- | --- | --- |
| 是什么 | 圈、箭头、下划线、写一个字 | 画一个新东西 |
| 作用 | **指向**某个已有的东西 | **产生**内容 |
| 归属 | 标注层（属于某人的意见） | 成果层（属于共同产物） |
| 跟版本走吗 | ✅ 绑 `artifact@version`，版本变了变 stale | ❌ 它自己就是成果，自己版本化 |
| 能否被删除 | 只有主人能删 | 只有创建者能删 |

**这个区分决定了"版本比较"能不能成立**：如果两者混在一起，改一版之后你不知道"这个圈是意见还是作品"，也就不知道该不该标 stale。

### 4.2 六个能力的关系图

```
        ┌───────────── 素材层（桌上有什么）─────────────┐
        │  成果 artifact（文档/代码/图/设计稿）           │
        │  创作性手绘 / 图形 / 文本对象                   │
        └───────────────────┬─────────────────────────┘
                            │ 被指向
        ┌───────────────────▼─────────────────────────┐
        │  意见层（每个人怎么想）                        │
        │  指称性手绘（绑 artifact@version）             │
        │  讨论 thread（锚定在坐标或对象上）              │
        │  ← 每人一层，别人没有写权限                    │
        └───────────────────┬─────────────────────────┘
                            │ 收敛
        ┌───────────────────▼─────────────────────────┐
        │  状态层（哪些已经定了）                        │
        │  版本链（向前，不覆盖）                        │
        │  版本比较（并排 / 叠加）                       │
        │  封存（→ 共同历史）                            │
        └───────────────────────────────────────────────┘
```

**读法**：
- **素材层**是"我们在一起看什么"；
- **意见层**是"每个人怎么想"，**彼此隔离**（这是图层归属的价值）；
- **状态层**是"哪些已经收敛"，**只有这一层是共同承认的**。

**"共同思考"发生在意见层，"共同创造"发生在素材层，"共同承认"发生在状态层。** 三层不能混：混了就会出现"我的反对意见被当成已定结论"或"草稿被当成成果"。

### 4.3 S1 不依赖公共空间（修正 C5）

**Studio S1 需要的只有**：一个 members 空间 + 画布 + 图层 + 标注绑版本 + 成果放置。

**不需要**：open 空间、实时 presence、版本比较。

所以顺序改为**并行**，不是串行：

```
P0 Home ──┬── P2a Studio S1 ──── P3 Studio S2（版本比较）
          │
          └── P2b Space(open) ─── P4 World/walk
```

**上一版把 open 排在 Studio 前面，理由是"先验证最危险的假设"。这个理由站不住**：S1 根本不用 open，串起来只是让 Studio 等了一个不相干的东西。

### 4.4 S1 的验收（不变，但更精确）

> 用户手绘**圈住一段**（指称性）→ 落在自己的图层，绑 `arch@3` → Hermes 改架构产出 `arch@4` → **那条圈变 stale 但还在** → DSH 在自己层放 note → 封存后第三人看不到任何人的私人日记。

**注意**：S1 里**不需要**"两个人同时画"。那属于 S3。

## 5. 反指标：不提供接口是不够的

### 5.1 上一版的漏洞

我说"不提供跨主体聚合接口"。**但数据本身就在**——任何人写个脚本遍历文件系统，就能聚合出来。

**"没有接口"只是挡住了顺手的人，挡不住有心的人。**

### 5.2 底层数据逐项审计

| 数据 | 存在哪 | 能被聚合成什么 | 处置 |
| --- | --- | --- | --- |
| **事件日志** | per-space | "谁在什么时候做了什么" → **最危险** | **默认不写**（见 5.3） |
| **版本链** | 成果内 | "谁提交了多少版本" | 保留（归属必需），但**不提供跨成果聚合** |
| **文件 mtime / size** | 文件系统 | "谁写得多" | **无法消除**（OS 层），列为残余风险 |
| **ACL** | 文件系统 | 谁知道谁能进 | 不是活动数据，可接受 |
| **成本账** | 账户级 | "谁今天花得多" | 只给主人看总额，**不按主体拆分** |
| **presence** | 内存 | 谁在、在哪 | **不落盘**（已做） |
| **open 空间消息** | 传输缓冲 | 谁说了什么 | **不落档**（已做） |
| **进出 / 已读** | — | 谁来过 | **不采集**（已做） |

### 5.3 反转：事件日志默认不写（C4）

上一版：写，然后自动修剪。
**现在：默认不写。**

| 模式 | 何时 | 记什么 | 谁知道 |
| --- | --- | --- | --- |
| **常态** | 一直 | **什么都不记** | — |
| **排障** | 当事人手动开启，明确起止 | 只记当前空间的操作 | **界面上明确显示"正在记录"** |
| 结束 | 手动或超时 | 存到该空间，**不导出、不汇总** | 只有该空间成员 |

**为什么反转**：
"记了但会删"仍然是记了——在删除之前，它可以被读、被复制、被聚合。**修剪是给已经发生的事打补丁，不是阻止它发生。**

**代价（我接受）**：
- 出了问题**无法事后调查**，只能重现；
- 排障变慢。

【建议】这是"不做监控"必须付的钱。**如果哪天我们觉得"还是记一下吧"，那就说明我们开始在管人了。**

### 5.4 剩余风险（无法消除，必须写下来）

| # | 风险 | 为什么消不掉 |
| --- | --- | --- |
| **R1** | 机器主人 + 文件系统 = 可以聚合一切 | 那是 OS 层的权力。**我们能做的是不提供工具、不出现在任何界面里** |
| **R2** | 文件 mtime / size 天然存在 | 除非改文件系统，否则不可控 |
| **R3** | 备份是完整快照 | 备份本身就是"全量可读"。**托管人能看到一切**——这是托管承诺的另一面，必须明说 |
| **R4** | 模型服务商侧的调用记录 | 不在我们管辖，只能靠不把敏感内容送出去 |

**R3 是我之前完全没提的**：我要求"有人负责备份"，就等于**要求有一个人能看到一切**。这不是可以回避的，只能明说：**托管人是一个有特权的位置，选谁就是选信任谁。**

## 6. 基础原语：撤回"三个"这个说法

### 6.1 我藏了什么

上一版我说"三个原语"。**底下的东西是这些**：

| # | 设施 | 上一版我怎么说的 |
| --- | --- | --- |
| 1 | 身份 / ACL | 说了 |
| 2 | 空间注册表 | 说了 |
| 3 | Blob 存储 | 塞在"Blob+Version"一格里 |
| 4 | 版本存储 | 同上 |
| 5 | 索引（可重建） | 说了 |
| 6 | 渲染沙箱 | 说了 |
| 7 | Gateway（出站） | 说了 |
| 8 | Presence（不落盘） | 说了 |
| 9 | **托管与备份** | **几乎没提** |
| 10 | **迁移与格式兼容** | **完全没提** |

**9 和 10 被藏起来了，因为它们破坏"三个"的整洁。**

### 6.2 正确的表述

> **顶层概念三个**（HOME / SPACE / EDGE）——这是**给人理解用的**。
> **底层设施八到十件**——这是**要真写的**。

**两者不是一回事。** 用"三个原语"当卖点，是拿比喻冒充架构。

【建议】以后不再说"三个原语"。改说：**"三个顶层概念，八个底层设施"**。数字不漂亮，但它真。

### 6.3 补充两件被漏掉的设施

| 设施 | 为什么必须有 |
| --- | --- |
| **托管 (Custody)** | 没有它，"永远留着"没有负责人（P1）。它包含：备份策略、格式迁移、责任人、失效时的降级方案 |
| **迁移 (Migration)** | 十年后 Markdown 还在，但**附件格式、索引格式、版本链格式**未必。需要"每年打开一次"的具体动作 |

**这两件不在"三个原语"里，因为它们是"这个家能不能撑十年"的条件，不是"这个家怎么组织"的结构。**

## 7. 共同历史与遗忘权：可见性与完整性是两个轴

### 7.1 矛盾在哪

- 共同历史要**真实** → 不能改；
- 遗忘权要求**能撤回** → 必须能改。

**上一版我没解这个，只说了"封存不可变"。那等于：一签就是永久囚笼。**

### 7.2 解法：把"可见"和"完整"分开

| 轴 | 取值 | 谁能改 | 作用 |
| --- | --- | --- | --- |
| **可见性** | 可见 / 已撤回 | **内容所有者** | 保护边界 |
| **完整性** | 原文在 / 已脱敏 | 系统（哈希留证） | 保护真实性 |

**两个轴独立运作**：

| 操作 | 可见性 | 完整性 | 读者看到什么 |
| --- | --- | --- | --- |
| **修订 (amend)** | 可见 | 原文在 | 原文 + "2027-03 我有不同看法：…" |
| **脱敏 (redact)** | 该段不可见 | 已脱敏（哈希保留） | "[已撤回] 2027-03" |
| **撤回 (withdraw)** | 整条不可见 | 哈希保留 | "2027-03 有人撤回了这部分" |

**关键点：撤回不销毁"曾经存在"这个事实，只销毁"内容可读"这个能力。**

所以共同历史仍然是真实的——**它真实地记录了"有人在某年撤回了什么"**。这不是缺陷，这是它该有的样子：**共同历史是"我们一起承认过什么"的记录，包括承认过又反悔的部分。**

### 7.3 谁能对什么动手

| 对象 | 谁能改 |
| --- | --- |
| 我自己写的那段 | 只有我 |
| 别人写的那段 | 谁都动不了 |
| 共同成果（artifact） | 成员可提出新版本；不能改旧版 |
| 整个 bundle | 只有全员一致（比如"这场不算数"） |

**任何人都能撤回自己的部分，不需要理由，不需要别人同意。**
【建议】这一条不能加"理由"字段——**要理由就是审查。**

### 7.4 最关键的一条：上游防御

**共同历史里本来就不该有私人内容。**

如果封存的内容里有"我私下告诉你的那件事"，那是**封存时选错了东西**，不是"现在要删"的问题。

所以真正的防线在**封存的那一刻**：

| 检查 | 谁做 |
| --- | --- |
| 我选的这部分，有没有包含别人私下说的东西 | **我自己检查**（系统不扫描内容） |
| 有没有人不同意 | 在场者点头 |
| 要不要现在就脱敏 | 封存时可以预先标 |

【建议】**系统不做内容识别**——因为那要求读所有内容，比问题本身更糟。

### 7.5 剩下的不可解部分

| 问题 | 状态 |
| --- | --- |
| 撤回后，别人本地副本里的内容收不回 | **不可解**。所以封存时**不自动分发副本**，只在共享存储留一份 |
| 已经有人读过，记忆已形成 | **不可解**。这是"读"的物理性质 |
| 撤回会不会被当作"心虚" | **不可解**。这是人的问题，不是系统的问题 |

**三条都不打算用设计掩盖。**
