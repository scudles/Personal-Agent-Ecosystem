### 公共窗口与真正群聊的区别

当前公共窗口主要是**消息汇总与定向路由**。三方不会自动看到窗口里的全部发言，也不会自动共享彼此的完整旧对话。

审批时，平台按流程投递被审材料，并在修订、任务或结果回送时携带必要意见。何时广播、何时只给指定方、如何避免重复回答或互相附和，尚未形成完整的群聊规则。

## 5. 三方接入方式与当前状态

| 参与者 | 接入方式 | 当前状态 |
|---|---|---|
| Hermes | 用其现有 Python SDK 连接已运行的 Gateway，通过 `session.resume`、`prompt.submit` 操作固定原 session | 可收发文字、回收结果和只读同步；当前空闲待办 |
| DeepSeek | C# Windows UI Automation 操作原桌面会话；从固定原会话事件日志只读回收文本 | 投递暂停，保留草稿；独立只读镜像仍可同步已落盘消息 |
| ChatGPT | C# Windows UI Automation 操作原桌面会话，读取可见的用户/助手消息边界 | 投递暂停；原会话当前未显示时只展示缓存 |

Hermes 单独调度；ChatGPT 与 DeepSeek 共用串行桌面操作通道，并有跨进程互斥，避免同时争抢输入。

桌面接入受应用界面、窗口可见性、焦点、草稿和锁屏影响。目前加入了空闲等待、标题与前台检查、草稿保护及定向写入。**改进后的 ChatGPT/DeepSeek 桌面写入方式尚未完成真实持续稳定性验收。**

原会话身份核验的技术强度也不同：Hermes 有 SDK 返回的 session 身份，DeepSeek 有固定原日志来源；ChatGPT 桌面通道依赖前期绑定及可见界面核对，不能据此宣称每次都获得服务端完整身份、模型路由和全量历史证明。

## 6. 主要技术组成

| 层次 | 技术与作用 |
|---|---|
| 界面 | HTML、CSS、JavaScript；本地浏览器窗口，消息正文与技术详情分开 |
| 本地服务 | Node.js HTTP 服务；固定原会话白名单及本机访问令牌鉴权 |
| 会话适配 | Hermes Python Gateway；ChatGPT/DeepSeek C# UI Automation；DeepSeek 原事件日志只读解析 |
| 流程引擎 | 持久化队列与状态机，管理排队、投递、等待、回执、修改、审批和文字任务 |
| 数据 | SQLite 保存事项、投递和历史；JSON 保存来源证据和原回复 |
| 对账 | 事项编号、版本、投递编号、随机 nonce、完整 SHA-256 |
| 访问范围 | 当前仅监听 `127.0.0.1:48731`，未开放公网或手机远程入口 |

当前调度周期约 3 秒，只读镜像约 5 秒，页面约 2 秒刷新。这是轮询更新，不等于三方都具备逐字流式输出。

镜像读取近期消息；ChatGPT 只能获得原会话当前可见的消息片段。部分镜像时间是平台首次同步时间，不一定是原始发送时间。完整历史、严格跨方时间排序、消息去重与分页仍需要完善。

## 7. 审批与权限规则

- 选定的审批方必须全部明确无条件通过。
- 支持通过、要求修改、拒绝、无法判断。任何非空条件都阻断无条件通过，沉默或超时不当作同意。
- 材料修改后重新计算版本与哈希，旧意见不直接沿用；保留原文与少数意见。
- 模型发起事项不能由自己审批。
- 投递结果不确定时标记 `UNKNOWN`，不自动重发；符合来源与绑定要求的迟到回复可回收。
- 当前任务限于文字交流、审查、修订和汇总，没有项目文件写入或命令执行接口。
- 审批通过不构成实施授权，也不替代用户作价值决定。

当前哈希绑定对象是**被审 `material` 字符串的 UTF-8 实际字节**，使用完整 64 字符十六进制 SHA-256（256-bit）。不包括消息信封和后续任务指令，不等于工程文件、commit 或实际运行产物已被验收。

当前策略包含每小时最多 12 次投递、模型自动修订最多 3 版、自动主动提交链上限 2 级。限流、链长限制和动作解析在全部入口中的一致性仍需审查，不能把已有策略字段当作安全性已完全证明。

## 9. 当前主要问题

1. **桌面通道可靠性不足。** ChatGPT 曾因焦点/会话变化中断投递；DeepSeek 存在与待发送文本不一致的原草稿。当前均暂停投递并保留现场。
2. **自然语言和机器协议尚未彻底分层。** 普通聊天已自然化，但正式自动审批仍需结构化回执，不能把任意一句“同意”直接计为批准。原会话中仍会留下少量控制标记，历史消息还保留旧协议内容。
3. **缺少完整群聊规则。** 公共窗口可见，不代表模型共享全部上下文；广播范围、轮次、主持、打断和冲突处理需要设计。
4. **动作识别边界需要继续验收。** 应防止引用、协议示例、旧回复或重复消息被误当作新审批动作；普通聊天与正式流程必须区分。
5. **人机并行操作不够稳。** 用户在原应用输入、切换对话，与平台自动投递之间仍有争用风险。
6. **远程使用未实现。** 目前不能直接从手机打开协作窗口；已有预览图是平台数据离线渲染，明确标注“非桌面实拍”。
7. **安全隔离仍是原型边界。** 虚构材料、暂停和禁用执行接口不等同于已部署独立受限账户或虚拟机沙箱；本地访问令牌也不是完整多用户权限体系。
