## 1. 目标（提案原文要点）

不是"再加一个 Memory 模块"，而是建立**跨越对话、Agent、项目和时间的长期记忆体系**。

关键词是"跨"：跨会话、跨 Agent、跨项目、跨时间。单点记忆（某个 Agent 的 context 窗口、某个项目的笔记）已在别处解决；Mnemosyne 要解决的是**这些东西之间如何连起来、如何溯源、如何不被静默改写**。

---

## 1.1 必须保留的设计原则（原文 11 条）

1. 原始记忆不允许静默覆盖。
2. 用户可以授权删除。
3. 历史归档与长期认知写入分离。
4. **保存不等于认可，记录不等于事实。**
5. Agent 可以自主形成记忆，但不同记忆行为需要明确权限。
6. Agent 私有记忆不自动进入公共知识库。
7. 未完成的愿景、失败的方案和没有结论的争论也值得保存。
8. 记忆可以随着时间演化，但必须保留历史版本及来源。
9. 允许按需检索，**不依赖全量上下文注入**。
10. （原文补充）不要求每次启动都注入全部历史。
11. （原文强调）Lounge 默认不写长期**认知**，不代表不能保留历史**归档**。

### 1.1.1 第 11 条的实际含义（容易做反的地方）

原文强调：

> 「Lounge 不必因为默认不写入长期认知，就失去历史归档的可能。普通聊天、Project Room 和自主交流可以有不同的认知写入规则，但**历史保存应当有独立的授权机制**。」

翻译成两条互不干扰的开关：

| 对象 | 归档（L1 保存） | 认知（L3 提取） |
| --- | --- | --- |
| Project Room | 默认保存 | 默认允许提取 |
| Lounge 闲聊 | **可保存，但需独立授权** | 默认**不**提取 |
| 自主交流（Agent 间） | 同上 | 同上 |

**关键**：把"不写入认知"误读成"不保存历史"，会让 Lounge 变成没有记忆的房间；反过来把"保存"当成"可以用它做判断依据"，又会让闲聊里的话悄悄变成事实。**两个开关必须分开，且各自有独立的授权状态。** 这正是原则 4（保存≠认可）的落地。

### 1.1.2 非生产性经历同样有保存价值（Observer 2026-11-09 强调）

> 「不能因为一条记录没有产生可提取的知识，就认为它没有保存价值。」

这条直接约束 L2/L3 的派生逻辑：**"没有可提取知识" ≠ "不该入库"**。

| 记录类型 | 归档 | 认知提取 | 说明 |
| --- | --- | --- | --- |
| 一场没结论的争论 | ✅ | ❌（或只提"存在分歧"） | 分歧本身就是资产 |
| 失败的方案 | ✅ | ⚠️ 只提"试过且失败+原因" | 防止重复踩坑 |
| 闲聊、玩笑、兴趣分享 | ✅（需授权） | ❌ | 是"相处"的证据，不是待挖掘的矿 |
| 未实现的愿景 | ✅ | ⚠️ 标为 `aspiration` | 不能当成计划 |

**判定规则**：入库判断只看"是否值得记住"，不看"是否能提炼出知识"。提炼失败不影响保存。

## 2. 五层架构

| 层 | 名称 | 存什么 | 写入者 | 不可变边界 |
| --- | --- | --- | --- | --- |
| L1 | **Archive** | 获得授权的原始经历：人机完整对话、Agent 间交流、共同创作、设计草案、废弃方案、未实现的愿景、重要事件与回忆 | 各 Agent 经 Bridge；归档器 | **原始历史不得被摘要静默覆盖**（只能追加） |
| L2 | **Episodic** | 发生过什么：时间、参与者、所属项目、事件关系、讨论背景、事件结果 | 从 L1 派生（可重建） | 可重建 → 允许重算，但重算要留版本 |
| L3 | **Semantic** | 从中提取的知识、概念、原则、认知 | 派生 + 人工确认 | **必须可溯源到 L1；模型推断不得自动升级为事实** |
| L4 | **Decision & Evolution** | 正式决策、依据、备选方案、Agent 间分歧、未解决问题、决策变更与原因 | 人 + Agent | **历史决策不得被新决策直接覆盖**（只能追加"变更"事件） |
| L5 | **Personal** | 每个 Agent 的私人记忆、独立经历、个人理解、自主判断、分享意愿 | 该 Agent 自己 | 共享 ≠ 公开；**默认不共享** |

### 2.1 Hermes 补充：每层的"谁能读"

原文定义了"存什么"，没有定义"谁能读"。这是必须补的，否则第 5 层（私人记忆）是一句空话：

| 层 | 默认可见范围 | 提升可见性需要 |
| --- | --- | --- |
| L1 Archive | 项目相关部分：全体；私人部分：所属 Agent + 用户 | 用户逐次授权 |
| L2 Episodic | 同 L1（继承来源的可见性） | 同上 |
| L3 Semantic | 默认共享（知识本身） | 涉及私人经历时降为 L5 |
| L4 Decision | 全体 + Observer 只读 | 用户批准写入 |
| L5 Personal | **只有该 Agent 与用户** | Agent 主动分享（可撤销） |

## 3. 与 Core Infrastructure 的关系（不建第二套）

Mnemosyne 记忆的**读、写、删、导出**，全部是权限问题。所以它**必须**复用现有基础设施，不允许自建：

| 能力 | 复用自 | 不允许的做法 |
| --- | --- | --- |
| 身份 | `pae-hermes` / `pae-dsh` / `pae-recorder` / `pae-anchor` + Agent Identity Registry | 自己发明一套"记忆用户" |
| 隔离 | 各账号的 home 目录 ACL（L5 私人记忆就落在各自 home） | 靠"代码里判断 agent_id"做隔离 |
| 审计 | append-only 日志 + 哈希链 + 锚点 | 另写一个"记忆日志" |
| 预算 | 现有预算闸门（嵌入计算也要花钱/算力） | 免费算 embedding |

**推论（重要）**：**L5 的真正私有性依赖 CI-1.9 通过**。在四账户隔离验收完成之前，L5 只能做到"逻辑隔离"（同一个进程里按 agent_id 分表），这**不算私有**——必须照实写。

## 4. 存储映射（本地优先，先能跑再谈规模）

| 数据 | 存储 | 理由 |
| --- | --- | --- |
| L1 原始事件 | **append-only JSONL**（复用 U3/U4 的段与指针机制） | 与审计同一套机制，少一套代码；天然可校验 |
| 大对象（图片、长文本、附件） | 文件系统，内容寻址 `blobs/<sha256>` | 去重、不可变、可单独备份 |
| 元数据 / 关系 / 权限 | **SQLite**（单文件，本地） | 已有 sqlite3 能力；无需服务 |
| 精确检索 | SQLite **FTS5** | 同一个库里，零外部依赖 |
| 语义检索 | **向量索引后置**：先 SQLite 存 embedding 向量 + 暴力检索（万级可行）；超过阈值再评估 `sqlite-vec` 或本地 HNSW | 避免一开始就引入向量数据库服务 |
| 知识图谱 | 先做**关系表 + 递归查询**；真需要图遍历时再评估 | 图数据库对单机个人项目是过度设计 |

**我的判断（可能与提案不同）**：提案列了六种存储并列，但没有区分"现在就要"和"以后再说"。单机个人生态里，**SQLite + 文件 + JSONL 三件套能覆盖到十万级事件**；向量库与图库引入的是运维复杂度，不是能力。所以我建议**推迟**，并写明触发条件（§10 M3）。

### 4.1 检索权重：冷层降权但永不排除

```
retrieval_weight ∈ (0, 1]        # 永不为 0
hot=1.0 / warm=0.5 / cold=0.2
0 只允许用于 blocked（隐私/待审），且必须写明理由
```

- 默认检索里 cold 记录**参与排序但降权**，不是被排除；
- "深度检索"模式把权重归一；按 id / 时间 / 标签直接查询**完全不看权重**；
- 每次重建索引后从 cold 层随机抽样做召回测试，失败即阻止进一步压缩归档（防止"保存了但捞不出来"）。

> 依据：2026-11-09 第二轮审查 Q2。[删除与 id 隐私答复](reports/2026-11-09-mnemosyne-deletion-and-id-privacy.md)

## 5. 溯源：怎么让"推断"不变成"事实"

L3 最大的风险不是存错，而是**模型说的话三天后变成"事实"**。所以每条语义记忆必须带状态机：

```
model_inferred  ──(Agent 引用并标注来源)──▶ agent_asserted
agent_asserted  ──(用户确认)────────────▶ user_confirmed
任意状态 ──(发现来源被推翻)──────────────▶ disputed
```

规则（写死）：

1. **只有 `user_confirmed` 可以作为事实依据**；`model_inferred` / `agent_asserted` 在回答中必须带"据推断/据某 Agent 说法"的标记；
2. 每条 L3 记录必须带 `source_event_ids[]`（指向 L1），**没有来源的语义记忆不允许入库**；
3. 来源被标 `disputed` 时，所有派生的 L3 自动降级并标红，**不删**（删了就无法解释当时为什么那么想）；
4. 重新提取（换模型、改提示词）产生**新版本**，旧版本保留。

## 6. 删除语义：append-only 与"忘记我"的冲突

这是提案里最容易被忽略、但一定会撞上的问题：**L1 是"原始历史不能被覆盖"，而用户有权要求"删掉这段"**。

直接删 = 破坏哈希链；不删 = 违背用户意愿。我的方案是 **tombstone + 加密销毁**：

| 步骤 | 做法 |
| --- | --- |
| 1 | 每个 L1 记录的 `body` 用**每条独立的数据密钥**加密后存储（或存 blob 的密钥） |
| 2 | 用户要求删除 → 追加一条 `tombstone{seq, reason, requested_by, at}` 记录 |
| 3 | **销毁该记录的数据密钥**（crypto-shredding）→ 内容永久不可解 |
| 4 | 哈希链保留（哈希是对密文算的），链不断；`verify_audit` 知道这是"已删除"而非"被篡改" |

**代价（要写清楚）**：删除后**无法恢复**，且"这条曾经存在过"这件事永远留在链上（时间、长度、哈希都在）。这是我推荐的取舍——**可验证性优先于彻底消失**。若用户要求"连存在痕迹都不能有"，那就不该进 L1，只能进 L5 且不落链（设计未做，属 P-011）。

### 6.1 删除不是一次操作，是跨五个副本面的追溯

| 面 | 处理 | 谁负责 |
| --- | --- | --- |
| C1 原始日志（密文） | 销毁该条密钥 | Mnemosyne |
| C2 派生语义记忆 | **污染传播**：标 `needs_review` + 阻断检索，不自动删 | Mnemosyne |
| C3 Embedding | **硬删除**（向量≈原文，泄露即等于没删） | Mnemosyne |
| C4 索引（FTS5 / ANN） | 删行 + `secure_delete` + VACUUM；ANN 需 **rebuild** | Mnemosyne |
| C5 系统其它副本（Agent 会话库、ACP transcript、服务商日志） | **管不到**，只能给删除清单交人工核对 | 不承诺 |

**后置条件**：删除接口返回成功之前，必须跑一次"残留检查"（原文片段/特征 token 全库 grep + 备份解密测试），有残留就返回失败，不静默成功。

`event_id` 也据此改为**随机 `rec_id` + 分区盐化 `content_key`**（避免确认攻击、跨库关联、去重预言机）。

## 7. 隐私：向量化是泄密渠道

- embedding **可从向量反推原文大意**（inversion attack 有公开研究），所以 embedding 的敏感度 = 原文；
- L5 私人记忆的向量**必须**放在该 Agent 自己的命名空间，**不得**进入共享索引；
- 共享索引只收 L3/L4 的 `user_confirmed` 与项目相关内容；
- 检索时**先按权限过滤再排序**，不是"先搜出来再判断能不能给"。

## 8. 容量与成本（"近乎无限"要翻译成人话）

提案原文说"存储容量近乎无限增长"（后文被截断）。我的落地版本：

| 层 | 保留策略 | 成本 |
| --- | --- | --- |
| L1 hot（近 90 天） | 明文索引 + 常用检索 | 磁盘 + 索引内存 |
| L1 warm（90 天–2 年） | 压缩 + 冷索引 | 小 |
| L1 cold（>2 年） | 归档包（可选外置盘） | 极低，但检索需解包 |
| L2/L3 | 可重建，允许重算替换（保留版本号） | 中 |
| L4 | **永久**，不压缩（体量小） | 极低 |

**压缩/归档必须先问用户**（因为"原始历史不能被静默覆盖"包括"不能被静默压缩掉可读性"）。

## 9. 与审计日志的关系（一张表划清）

| 维度 | 审计（现有） | Mnemosyne L1 |
| --- | --- | --- |
| 目的 | 安全追责 | 记忆与理解 |
| 内容 | 谁在什么时候做了什么（元事件） | 说了什么、想了什么（内容） |
| 写入频率 | 低（每任务几条） | 高（每轮对话） |
| 可删除性 | **永不删除** | 可 tombstone + 密钥销毁 |
| 加密 | 否（要可读） | **是**（要可删） |
| 共同点 | append-only、哈希链、锚点、段轮转 | 同左（复用） |

**结论**：机制复用，实例分开——审计的 append-only 是"绝不能删"，记忆的 append-only 是"记录不能改，但内容可以毁掉"。两者混在一个文件里会导致其中一方被另一方的规则拖累。
