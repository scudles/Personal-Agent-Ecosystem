# 原会话真实互通可靠性验收计划

## 当前证据与要解决的问题

现状以[真实材料交付状态](DELIVERY_STATUS.md)为准：Hermes有一次对应原Session的内容回执，接收端未重算hash；DSH现有私密草稿处理授权已经生效，但editor未安全识别，尚未备份/修改/发送；ChatGPT保留人工附件B，尚未自动投递。这些事实不能合并为六向可靠性通过。

需要分别回答：原会话身份和版本是否一致，消息是否确实收到/结束，能否一次提交并正确归属回复，故障时能否停止且保留草稿，以及材料实际覆盖到哪一级。材料可读、字节一致、自动线路可用和长期常驻是不同结论。

## 六向、每向五次真实闭环

一次闭环定义为：发起方既有原会话形成带唯一挑战的材料/请求，经明确线路交给接收方既有原会话；接收方给出对应回复，再将原回复返回发起方，并得到对应返回消息的确认。只向接收方发送一次、或只看到其生成结束，不能算一个往返完成。不开新会话，不替换原身份，不同步私有记忆。

| 有向线路 | 计划次数 | 当前状态 | 接入方式必须单列 |
|---|---:|---|---|
| Hermes → DSH → Hermes | 5 | NOT_EXECUTED | DSH安全接入未完成，不假定可自动执行 |
| DSH → Hermes → DSH | 5 | NOT_EXECUTED | DSH源消息及返回确认均须绑定原会话 |
| Hermes → ChatGPT → Hermes | 5 | NOT_EXECUTED | ChatGPT现阶段可采用人工B，记为人工辅助真实闭环 |
| ChatGPT → Hermes → ChatGPT | 5 | NOT_EXECUTED | 发起与返回均需人工原会话凭据，不能冒称自动 |
| DSH → ChatGPT → DSH | 5 | NOT_EXECUTED | 同时受DSH安全定位与ChatGPT人工方式限制 |
| ChatGPT → DSH → ChatGPT | 5 | NOT_EXECUTED | 人工参与与自动动作分别记账 |

合计30次计划真实闭环，至少涉及60次线路交付动作；启动挑战、附件、返回确认还可能增加实际提交。保留现有共享30次/滚动小时上限，正式执行前按真实计数分批并留出余量，不提高上限、不把“30个往返”误当30次提交。已有单次canary授权不自动覆盖这批批量试验。

批量执行前还要证明真实路径和人工参与动作都有可核对的额度记录；当前离线共享额度实现不自动证明单次独立SDK canary或人工操作已经纳入同一计数。

每条线路分别统计 `AUTOMATIC_REAL` 与 `HUMAN_ASSISTED_REAL`。人工B可以验证真实材料互通，但即使总真实闭环达到5/5，也不能据此宣布该方向自动线路5/5。模拟数据只能验证控制逻辑，不能补真实次数。原先单次Hermes内容回执单列历史证据，不直接补入新批次的完整闭环。

## 每次闭环的冻结字段与证据

执行前冻结本批 `runId`、方向、1..5编号、原会话身份指纹、允许材料与版本、操作人、接入方式和提交额度。原Session的私密定位信息仅留在有权本机映射中；复核报告使用指纹，不导出无关消息/工具记录。

| 核对项 | 最小证据 | 不足时的结论 |
|---|---|---|
| 来源与归属 | 发起原消息标识/指纹、真实作者、接收目标指纹；桥接deliveryId与完整请求hash | 来源不确定则INDETERMINATE，不按名字或相似正文归属 |
| 材料与版本 | packageId/version、snapshotId、manifestHash、选定文件清单、随机marker及内容挑战 | 抄录预期hash是声明，不是重新校验 |
| 一次提交 | attemptId、提交前后状态、实际submissionAttempts及原收件消息标识 | 已排队/已提交不能写成收到；次数不确定则UNKNOWN |
| 接收与结束 | 原回复标识、对应原请求、结束状态、原文；工具活动只记录本次获准范围 | 收到不等于处理完成；不能通过额外私密审计补缺口 |
| 返回闭环 | 返回deliveryId、发起方原会话的返回消息标识及确认 | 只有接收方回复，仍缺返回腿 |
| 材料覆盖 | 实际文件/附件覆盖、读取方式、内容挑战结果、是否接收端实际重算hash | HUMAN_REPORTED、CONTENT_CONFIRMED与BYTE_VERIFIED分别记录 |
| 时间和异常 | 入队/提交/观察/结束/返回时间；故障、取消、恢复的原因与凭据 | 超时不能改写为成功，不用后来的无关回复补齐 |

证据表可使用后续新建的 `evidence/real-material-canary-001/reliability/<runId>/`，逐次原记录与汇总分开。该目录目前只是建议，不在本计划编写阶段生成真实回执。总结保留分歧和缺失，不重写原回复。导出的材料只含本次许可内容。

## 故障与恢复验收

故障试验只使用无隐私的虚构canary内容，并先冻结允许注入方式。不得为了证明错投保护而故意向未经授权会话发送；前置拒绝和真实异常要分别标注。模拟故障记录不冒充真实故障已覆盖。

| 场景 | 应有行为 | 必留证据及恢复边界 |
|---|---|---|
| 目标窗口/Session不符 | 在输入/提交前拒绝；不自动选另一个会话 | 预期/观察身份指纹、拒绝阶段、零提交；正确身份重新核验后才接受新请求 |
| 同名会话或无法定位editor | 不能凭标题猜对象，不扩大截图/读取范围 | 可安全观察到的不足、停止原因；DSH现有editor问题保留为未解决 |
| 重复请求/重启 | 同键返回原attempt/消息，不新增提交 | 原键、原ID、重启前后次数；完整prompt与版本核对 |
| 提交超时/UNKNOWN | 保持原attempt，不自动重发、不把缺失回执当未发送 | 可能已经提交的边界、现有消息核对结果；先核对原attempt，再决定是否结束该试验 |
| 迟到回复/多消息交错 | 只接受绑定原请求/版本的回复；不接纳其他人工消息 | 原replyId和关联证据；无法归属就保持未知 |
| 人工输入/已有草稿 | 提交前检测互斥；保留原草稿，不自动覆盖或发送 | 本次允许范围内的草稿存在/占用状态及零变更记录；不导出无关私密正文 |
| 材料旧版/附件缺失 | 不确认当前版本完整收件；明确缺失项 | 实收覆盖、版本及预期差异；后续补件是单独有授权动作，不伪造原回执 |
| 暂停/取消/平台断开 | 停止新增提交；已提交未明的事项保留UNKNOWN | 原状态、原ID、暂停持久化；重新启动程序不等于恢复真实队列许可 |

DSH当前那份草稿已有用户授权，不重复索要同一授权；但安全定位与可核对备份尚未完成，不能把授权当操作已完成。未来注入其他草稿、读取其他内容或使用新的导出工具，不在这份既有授权中。已被自动审批拒绝的整窗截图/私密工具链审计不改用其他通道绕过。

## 通过、未通过与无法判定

每向5次只有全部形成可归属的真实闭环、没有错投/重复提交、没有未解决UNKNOWN，才可写该方向“本批内容互通通过”。每向单独记录方式和通过范围；不以六向平均成功率隐藏某向失败。BYTE_VERIFIED须有获准的接收端原字节校验及对应方法证据；没有现成合规能力就停在较窄结论，不运行命令/脚本来凑hash。

故障控制须有对应拒绝或安全停止证据。明确失败为NOT_PASS；缺失原标识、人工证据不足或UNKNOWN未消除为INDETERMINATE。修复后仅按原问题和新证据定向复验，保留原批次失败记录，不无依据反复全量审查。
