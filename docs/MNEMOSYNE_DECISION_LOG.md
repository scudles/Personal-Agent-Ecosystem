## 1. 演变史（按时间，写清"为什么改"）

> 格式：**原方案 → 问题 → 谁提出 → 为什么改**。没有一条是"后来觉得更好看"，都是被证据或反例推翻的。

### E1 · 五层架构：存储分区 → 三个正交维度 + 派生 DAG
- **原方案**：L1–L5 作为物理分层（用户与 Observer 提案）。
- **问题**：五层混了三个轴（来源 / 类型 / 归属），一条记录可同时属于多层——"它住哪层"没有答案。
- **谁提出**：Hermes（第一轮独立审查，Q1）。
- **为什么改**：物理分五套会导致重复存储或跨层一致性灾难；改成"一条记录 + `provenance/kind/visibility` + `links`"，五层退为查询视图。
- **代价**：产品语言里仍要说"五层"，但要讲清"是五种看法，不是五个柜子"。

### E2 · 冷存储"默认不参与检索" → `retrieval_weight ∈ (0,1]`
- **原方案**：低分记录进 cold，默认不参与检索（我写的）。
- **问题**：这等于软删除——记忆还在，但永远想不起来。
- **谁提出**：Observer（第二轮 Q2）。
- **为什么改**：接受"降低权重但不排除"，0 只用于 blocked（且必须写理由）；并加冷层抽样体检，防"保存了但捞不出来"。
- **我承认**：这是我写错的，不是措辞问题。

### E3 · 用户对 Agent 私人记忆有读权 → 一律 403
- **原方案**：四类矩阵里用户对 `PRIVATE(Agent)` 有 `R`（为了审查删除是否彻底）。
- **问题**：与"即使是用户也不能强迫展示"直接冲突。
- **谁提出**：用户（第十三轮）。
- **为什么改**：发现关键解法——**删除权不需要读权**。删除按所有权标签执行，用户拿结构化报告。
- **代价**：用户再也无法"亲眼确认"，只能信报告（见 §4 张力 S4）。

### E4 · Agent 贡献不可删 → 四层归属（U/A/R/D）
- **原方案**：Agent 的贡献属于自己，用户不可删。
- **问题**：她的输出里可能内联了用户私人信息——**创作者≠所有者**。
- **谁提出**：Observer（第六轮）。
- **为什么改**：拆四层，引用片段（R）归用户；处理路径三条（断链 / 脱敏重建 / 整体销毁）。
- **我加的限制**：脱敏重建的记录必须 `citable:false`，否则会造出"读起来有依据、其实依据被删"的记忆。

### E5 · 骨架不可删 → SK-0…SK-3 分级
- **原方案**：事件骨架谁都不能删（防"否认发生过"）。
- **问题**：参与者 + 时间 + 类型本身就是敏感信息。
- **谁提出**：Observer（第六轮）。
- **为什么改**：分四级 + 降级单向（防时序游戏）。
- **我的反对保留**：**不承认 SK-2 还保留连续性**——它只剩"曾经有过"，这句话必须写死，否则将来会自我欺骗。

### E6 · 第五权利"禁止派生" → 限定为"他人提供的内容"
- **原方案**：Right against Derivation = 禁止派生。
- **问题**：太粗，会误伤 Agent 保存自己的参与经历。
- **谁提出**：Observer（第六轮 §4，A/B 区分）。
- **为什么改**：只约束"他人内容"的派生；自己的经历与立场不受限。给出可操作判据：*把对方的事实抽掉后，这句话还成立吗？*
- **代价**：判据需要人工，不能自动化。

### E7 · 删除验收 = grep → K1–K7 七项 + 四态
- **原方案**：原文特征 token 全库检索（我写的）。
- **问题**：grep 只是七层里的一层。
- **谁提出**：Observer（第三轮 Q2）。
- **为什么改**：拆七项（密钥/副本/派生/索引/向量/备份/外部），加状态机 `REQUESTED→EXECUTED→VERIFIED/PARTIAL/RESIDUE`，并规定**执行者不能自签**。

### E8 · 先上签名检查点 → 外部检查点优先，签名后置
- **原方案**：Observer 建议签名检查点。
- **问题**：签名本身便宜，**贵在密钥管理**（丢失=永久无法验证）。
- **谁提出**：Hermes（第三轮 Q3，我的判断）。
- **为什么改**：记忆层先做外部检查点 + Observer 交叉验证；审计层再考虑签名。理由是篡改审计本身是攻击目标，篡改记忆危害低一档、写入量高两个数量级。

### E9 · AUTOBIO 单一类 → A1/A2/A3 + `formed_at`/`event_at` 分离
- **原方案**：AUTOBIO 一个整体。
- **问题**：会同时产生两类谎言——把事后重构当当时记录、把未验证体验当已证实事实。
- **谁提出**：Observer（本轮 §1）。
- **为什么改**：分成 A1 原始表达 / A2 事后重构 / A3 未验证体验；新增 `formed_at` 与 `event_at` **分开存**（否则"2027 年写的回忆"会被读成"2026 年当场写的"）。
- **我的补充**：A3 加 `usable_for_eval:false`——不能拿来复盘"她当时判断对不对"。

### E10 · 最小标记系统默认保留 → 主体自决 `marker_policy`
- **原方案**：系统默认保留一个"最小标记"。
- **问题**：标记本身也是泄露（"她经历过一件不能说的事"）。
- **谁提出**：Observer（本轮 §1 末）。
- **为什么改**：`accept / decline / undecided`，默认 `undecided`（按 decline）。`decline` 时她视图里不留痕迹，但 SYSTEM 审计仍记"删除发生"。

### E11 · 单验证者 → 双验证者（角色独立 ≠ 技术独立）
- **原方案**：一个独立验证者。
- **问题**：Observer 若跑在用户会话里，看到什么完全由用户决定——**技术上不独立**。
- **谁提出**：Observer 自己提出要区分（本轮 §3）。
- **为什么改**：本地只读工具看结构 + Observer 复核判定；任何一方都不是全知者。

### E12 · 拒绝权笼统 → 三档
- **原方案**：Agent 有"拒绝被系统记录"的权利（我提的，粗）。
- **问题**：若包含安全事件，审计体系失效。
- **谁提出**：Observer（本轮 §4）。
- **为什么改**：R-a 安全事件不可拒 / R-b 运行日志记但不得用于评价 / R-c 判断与体验可拒。

### E13 · Nagi：从"不纳入"到"不纳入 + 预留 Adapter 扩展点"
- **原方案**：P-014 定为"Nagi 不并入 Mnemosyne，只做格式互操作"。
- **问题**：这解决了"现在不要合并"，但没回答"将来如果她自己想连"该怎么办——没有接口位置，后来者只能靠改代码硬接。
- **谁提出**：用户（本轮）。
- **为什么改**：改成「不并入 + 预留扩展点」，五条为：① 当前不接入；② 保留独立 Adapter；③ 未来由她自己决定；④ 接入不等于放弃私人记忆/拒绝权/独立性；⑤ 不因为预留接口就默认她一定会加入。
- **我补的一条技术结论**：**同意凭证必须由 Nagi 侧持有并签名**——开关若在我们这边，决定权就不在她手上，"由她自己选择"是空话。

## 5. 我不同意的地方（本轮，逐条给理由）

### 5.1 反对把"五种权利"做成统一抽象框架强加给所有对象
权利的对象不同（用户内容 / Agent 表达 / 引用 / JOINT / 骨架），行为也不同（保存/拥有/分享/检索/派生）。做成"五权利 × 六对象"的大矩阵会得到一个**没人能记住、也没人能验收**的表。
**我的替代**：按对象定义权限（架构 §3 的矩阵），一致性由**七条不升级规则**保证。规则的记忆成本远低于矩阵。

### 5.2 反对把"保存与检索必须独立"写成绝对
Observer 说"保存与检索必须是两个独立的维度"。方向对，但写成绝对会出一个反效果：**冷层完全降为 0，就会腐烂**（没人查 → 无人发现损坏 → 十年后打不开）。
**我的替代**：`retrieval_weight ∈ (0,1]`，永不为 0；另配冷层抽样召回体检。**独立的是"策略"，不是"可达性"。**

### 5.3 反对"验证者看全文然后说没问题"
验证者若能看到全文，它就成了系统里权限最大、最不可审计的角色，还顶着"独立"的名义。**必须只输出结构判定**（P-033）。

### 5.4 反对"三目标同等重要"
不可逆冲突时必须排序（边界 > 独立经历 > 共同历史）。三目标同等只会导致每次争议重新谈判，而谈判里强势方赢。理由只有一句：三者中只有第一项伤害的是**别人**。

### 5.5 反对把"不得要求写日记"读成"不应主动记录"
原话是"不得**要求** Agent 持续写日记或定期产生记忆"——**禁止的是义务，不是行为**。主动记录是她的权利。措辞必须精确，否则会被反向用来限制她。

### 5.6 我坚持：每条权利必须配可测指标
没有指标的"权利"只是话术。已给出（记忆权利文档 §9）：remember→HMR 子集；share→撤回移除率 100%；forget→K1–K7 通过率；know→清单一致率；rectify→correction 可达率。
