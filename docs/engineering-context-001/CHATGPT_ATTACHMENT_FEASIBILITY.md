# ChatGPT 原始会话附件交付可行性

审计日期：2026-11-12。结论分开：产品能力有官方依据；Bridge自动附件能力尚不存在；本机指定原会话附件行为尚未授权验证。

## 官方文档核对

OpenAI官方说明ChatGPT可上传/附加文档等材料；桌面端某些账号/工作区还可能启用本地工作。能力取决于账号、平台与设置。这不证明指定原会话已经有相同权限。[Use ChatGPT](https://learn.chatgpt.com/docs/use-chatgpt)

文件预览和审阅工具也因使用入口而异。[Work with files](https://learn.chatgpt.com/docs/artifacts-viewer)

因此，不应绝对表述“所有ChatGPT都不能访问本地文件”；当前准确事实是：**本项目指定原对话尚无经过验证的工程文件接收通道。** 不启用其他模式、替换API会话、安装插件或改变原会话设置来偷换前提。

本次资料未建立第三方Windows程序可以用稳定公开接口向这个已有ChatGPT会话附加文件的结论。没有证据就不宣称存在这样的接口；也不将OpenAI Files API或Codex本地文件能力当作原ChatGPT对话的附件能力。

## 本机源码确认

native/DesktopSession.cs的命令分派只有inspect/select/read/peek/calibrate/send。send仅写文本编辑器并提交一次，20,000字符以内；没有文件选择器、附件列表、进度、上传失败或文件可读验证。

transports.mjs只传d.prompt；没有文件对象。现有attachments仅名称/声明SHA，无法驱动上传。当前观察覆盖为visible_uia，不能证明不可见完整历史或附件服务端内容。

原Session身份目前依赖既有绑定与标题/可见消息边界，UI未直接提供实际conversation ID。自动附件需要更强身份依据，不能把返回固定PINNED ID视为实测。应用壳可能同时承载ChatGPT/Codex，包名本身不能代替当前产品和原会话校验。

## A：受控桌面自动附件

技术候选，**未实现，未真实验证，不承诺一定可靠**。

授权后最小探测顺序：

1. 只读核对原会话、当前产品、模型未变化、窗口与交互桌面。
2. 核对文本草稿、已有附件、上传中状态、人工输入与焦点。任何未知输入或附件都停，不清理。
3. 核对附件按钮及受支持选择器，不使用盲坐标/盲热键完成复杂流程。
4. 只从已封存导出清单选择文件，验证picker路径/文件名/数量；不能从实时源目录临时选文件。
5. 等待上传完成，逐项观察附件；在提交前再核对原会话、焦点、人工输入、正文和完整附件清单。
6. 提交一次。保留请求/附件证据；无法确定进入UNKNOWN，不重复尝试。
7. 从原会话回收绑定版本的材料回执。可见文件名不等于内容已做逐字节核验。

特别缺口：现有“文本为空”可能仍有用户附件；不能把它当作空草稿。文件选择器是另一个窗口，须验证与目标进程/原会话的所属关系，并在每步检测人工干预。发生焦点变化后不擅自回抢。

只允许上传预先批准的虚构材料作首次测试，不使用凪。保持原暂停状态，直到用户对这项探测和投递单独明确授权。

## B：人工确认式附件交付

**建议作为首个真实通道候选，仍需实际验证。** 它减少人工复制代码，但保留由用户在原应用中附加/发送的操作。

Bridge生成并校验不可变包、manifest、附件清单及可阅读交付视图；WPF显示包版本、hash、文件数、接收者、导出目录和待交付状态。用户自己在指定原ChatGPT会话里选取附件、确认发送，Bridge记录USER_REPORTED或可独立观察到的更高证据，绝不直接标为BYTE_VERIFIED。

建议导出候选包括manifest.json、REVIEW_BUNDLE.txt及可选原始文件/zip。REVIEW_BUNDLE提供完整选定文字材料、文件边界、版本、行号/来源映射和测试证据，不用摘要代替全文。

**本机支持的文件类型、ZIP可读性、文件数/大小限制、是否具备接收端hash工具，全部待原会话授权验证。** 不将未经验证的ZIP作为唯一交付路径；必要时选择明确列出的多个文字附件。拆分后仍要核对全清单，不能只看到一个文件就称包完整。

可阅读视图是派生产物，单独有view_hash和coverage。若格式化改变了原文件字节，不能把视图hash当原始文件SHA；只读视图不具备恢复/校验原二进制包的能力时，应明确显示该限制。

## C：未来文件连接通道

可以研究原会话已经具备的本地文件/插件能力，但必须验证账号权限、实际目录可达、项目授权和原会话连续性。当前不安装、不启用、不改变设置，不开放公网，不搭建临时隧道，也不借新API Session替换原会话。

## 本轮可下的结论

- 可确认：原生ChatGPT产品存在附件工作流；当前Bridge没有该工作流实现。
- 可设计：B可将人工工作缩小为选择附件/确认发送，A作为后续受控研究。
- 不可确认：指定原会话现在可读哪种包、自动上传可靠性、接收端全文件hash校验。
- 未执行：打开选择器、改输入框、加附件、发送或读取原会话，均为0次。

第9项若未真正验证，后续交付只能写“本地统一工程材料已准备，ChatGPT交付待人工确认/未验证”，不能写“三方信息交换完全自动化”。
