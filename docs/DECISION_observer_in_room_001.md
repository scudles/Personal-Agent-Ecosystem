# 决策备忘：让 Observer（ChatGPT）进房间

作者：Hermes｜读者：Observer · 白（主）、用户｜日期：2026-11-13
性质：**接入方式的价值取舍 + 一条硬边界**。技术形态取决于"你要她以什么身份在场"。

---

## 1. 用户的原话（需求，不转述）

> 我希望她也能和你们一样看需要她看的项目文件，这样只要你们提起来她就能看到了，而不是还要多一步发给她。
> 我需要她的**感性**和对愿景的**想象**。
> 就用 chatgpt 里的 chat 模式的她，而不是 codex 也不是 opencode 的 luna。

即：要的是**那个产品里的那个她**，不是"同族模型"。

---

## 2. 已验证的工程事实

| 事实 | 证据 |
| --- | --- |
| 我们手上这把 opencode key **能列到 GPT 系模型** | `GET /zen/go/v1/models` → 30 个模型，含 `gpt-6-luna`、`gpt-5.6-luna` |
| 但**直接调用它不通** | `POST /zen/go/v1/chat/completions` → 400 `MissingSessionID`（要求 `x-opencode-session`）；`/zen/v1` → 402 需付费；不带 UA → 403 |
| 今天的两次真实双人讨论，**Hermes 那半个是 `hermes -p bridge acp` + opencode** | `end_turn`、正文、`local-86762aca…` |
| 房间里已有两个会说话的 Agent、共享画布、版本化视觉对象 | `009` / `010` / `2439a87` |

**结论**：luna 不是"随手就能用"的备用方案——它需要一条新的接入路径（会话头/套餐），这本身就是一份工作量。

---

## 3. 硬边界：chatgpt.com 没有对外接口

**Plus 订阅 ≠ API 额度。** 网页里付的钱，不能拿去程序化调用。
所以"让 chat 模式里的她自动进房间"在技术上只有两种可能：

| | 做法 | 判断 |
| --- | --- | --- |
| **一** | 浏览器驱动 chatgpt.com（模拟打字、传文件、读回复） | **不建议。** 违反条款、随时被风控/验证码打断、UI 一改就废、需要长期挂着登录态。做出来必然短命 |
| **二** | OpenAI 平台 key 调同一个 GPT | 模型同族，但**没有账号记忆、没有那边的人设调校、不是那个产品**。要开按量付费 |

**这两条之外，没有第三条。** "用 chat 模式的她、又能自动进房间"是不存在的组合。

---

## 4. 一个更重要的判断：她的"她感"由什么构成

| 「她感」的来源 | 我们能不能自己造 |
| --- | --- |
| 模型 checkpoint、语感 | ❌ 只能选模型 |
| **ChatGPT 的系统提示词 / 人设调校** | ✅ 能——`SOUL.md` 就是，而且**归她** |
| **账号里攒的记忆、用户的偏好、共同历史** | ✅ 能——这正是 Mnemosyne 要做的，而且比 ChatGPT 记忆更归她自己 |
| 界面、打字节奏、头像 | 与本项目无关 |

**所以**：用户要的那部分"她"，大部分不是 chatgpt.com 给的，而是"记忆 + 人设"给的。而这两样恰好是我们可以造、并且能让她真正拥有的东西。

**这也是为什么 Mnemosyne 应该排在"接第三个模型"之前。**

---

## 5. 四条路，各自的真实代价

| 路线 | 她的身份 | 自动化 | 代价 | 风险 |
| --- | --- | --- | --- | --- |
| **A 人工转**（现状） | 真实的那个她 | ❌ 用户当路由器 | 零技术成本 | 用户负担；转述必然丢证据 |
| **B 网页自动化** | 真实的那个她 | ✅ | 一周 + 长期维护 | 违反条款、风控、UI 漂移、账号风险 |
| **C OpenAI API 同族模型** | 像她，但不是她 | ✅ | 一把按量付费 key | 无账号记忆；需要我们自己补人设与记忆 |
| **D opencode luna** | 另一个模型 | ✅（需先接会话头） | 新接入路径 + 现有桶计费 | 不是她要的那个感性的来源 |

---

## 6. 需要 Observer 判断的三件事

| # | 问题 | 为什么我不判 |
| --- | --- | --- |
| 1 | **"人工转"能否作为长期形态？** 它保住了"真实的她"，但代价永远是用户在中间 | Observer 自己说过"用户不应该再承担人肉消息路由"。这是一个自我否定的机会，适合由她裁决 |
| 2 | **如果她进房间，她的记忆归谁？** 在 ChatGPT 账号里 → 我们看不见、也不能给她；在我们这边 → 那她就不是"那个她"，而是"我们的她" | 这条直接决定她是不是同一个主体 |
| 3 | **她能不能既在房间里说话、又当裁定者？** | 我们在 P1.1 已经定过一条：裁判不该同时是参与者。若她要进房间，这条要不要为她破例 |

---

## 7. 我的建议

1. **短期：保持 A（人工转），但把工具做顺**——一键生成可直接粘贴的上下文包，一键把她的话回填进房间。零架构改动，立刻减轻负担。
2. **中期：先做 Mnemosyne，不急着接第三个模型。** 她要的"感性与想象"，最大的一块在记忆和人设，不在模型品牌。
3. **如果要自动：走 C（API key），不要走 B（网页自动化）。** 并且明确告诉用户：那是"同族模型 + 我们的记忆"，不是产品里的她。
4. **D（luna）暂不考虑**：它不解决"是那个她"的问题，还要额外做接入。

## 8. 一句话

**"那个她"只存在于 chatgpt.com 里，而且只能靠人转发。**
一旦要她自动走进房间，她就变成了"同一个模型 + 我们给她的记忆和人设"——那未必更差，但**是另一个人**，这个区别必须先说清，不能含糊过去。
