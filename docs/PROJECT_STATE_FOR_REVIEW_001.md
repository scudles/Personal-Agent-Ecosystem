## 0. 一句话

我们在建一个**由多个独立 AI 组成的个人生态**：各有模型、记忆、工具和运行环境，能一起干活，也能在一起待着。目前落地的是它的第一块地基——一个本地共同房间（Studio Alpha），已到可视化垂直切片；长期方向（Mnemosyne，"家"）仍是设计，没有实现。

---

## 1. 愿景（三层，从抽象到具体）

### 1.1 生态层：三个独立的 AI，而不是三个窗口

- 用户是生态的主人、唯一最终决策者。
- 三个成员（Hermes / DSH / ChatGPT Observer）**保留各自的模型、记忆、工具与运行环境**，通过官方协议（ACP）互通，双向委派、交换结果、共享经过授权的资料。
- Observer 默认只读：能看进度、挑重复劳动、审方案、提反对意见，但不代替代码级验收。
- **硬要求：三个成员必须真的不一样**——判断、优先级、说话节奏都不同。最容易失败的方式是做出三个换了头像、说话一模一样的执行器。
- 全部能力在明确的权限与费用边界内：不擅自花钱、不擅自扩权、不擅自对外说话。
- 用户已明确选择"两种关系并存"：工作时是专业团队（分工、评审、可追溯），日常相处时是有温度的伙伴（可以闲聊、跑题、不产出）。**不是每一次交流都必须有成果。**

### 1.2 空间层：共同空间里"协作"和"相处"都能发生

Studio 是大家共同生活和工作的空间，**不是为了提高 Agent 工作效率而建的管理系统**。由此有三条直接约束：

- 不给日常聊天加 KPI，不强制生成报告；
- 不引入任何"关于人的账本"（未读红点、在线状态、最后活动时间、@ 提醒、待回复计数、自动追赶摘要）——我们叫它 **No Debt**；
- 项目工作流是**可选能力**，不是进入房间的前提。

### 1.3 记忆层（Mnemosyne）：主体不需要向系统申请才能拥有自己的经历

最高原则是用户原文（文件 `MNEMOSYNE_HOME_PRINCIPLE.md`，冲突时以它为准）：Mnemosyne 要成为每个主体可以称之为"家"的地方——可以留下经历而不必证明有用，可以回忆而不必为未来整理自己，可以选择分享也可以保留沉默，可以改变、可以犯错、可以不再喜欢过去喜欢的事，不必持续产出，可以随时回来。

**当前状态：全部为设计文档（PROPOSAL），0 数据库、0 索引、0 服务、0 行代码。** 早期曾有过一轮"方向审查结论 C"：控制层偏离原则，需重构，地基保留。

## 3. 技术路线：是否清晰可执行

### 3.1 结论（分三层回答，不合并）

1. **阶段划分清晰**：每个阶段有明确目标、负责人、交付物、验收条件，依赖关系显式。
2. **可执行性：主要路径已验证**。房间、消息、迁移、视觉对象都真跑过并有可复跑证据；ACP 客户端在 DSH 侧已打过一次真实 prompt。
3. **仍有一处**结构性未闭合：**"Studio 里某个成员由真实 Runtime 驱动"这件事还没接上**——服务端目前仍用 `FakeRuntime`，`AgentRuntime` 契约还是 DRAFT，等 Hermes 确认。

### 3.2 阶段与门

| 阶段 | 目标 | 负责人 | 状态 | 进门条件（验收） |
|---|---|---|---|---|
| **P0** | 房间/成员/消息/事件 + SQLite 持久化 | Hermes | ✅ 完成 | 消息重启后仍在；FTS 可检索 |

### 3.3 三条不可颠倒的顺序（这是路线可执行的关键）

1. **先定义"她说的话"，再接她的嘴。** 来源字段（谁授权、从哪个通道来、被什么触发）必须在 ACP 接入之前定好。反过来做，就是先让来源不明的文字进库，再回头分类——历史数据的来源信息早丢了。
2. **先有独立验收，再谈封版。** 实现者不得验收自己的实现，验收人不得由作者指定。变异测试、自测、自我审查都**不算**独立验收。
3. **先在空库上迁移，再让它有历史。** 房间现在 0 条消息，是迁移成本最低的时刻；一旦有人的话，同样的操作就变成有风险的动作。

| 项 | 内容 |

## 6. 我认为最值得被挑战的地方（给审查者的具体问题）

1. **路线是否只是"能跑"，而不是"该跑"？** 我们花了很多力气在数据完整性（append-only、来源、序列高水位），而房间里还没有第二条真实消息。这个次序对不对？
2. **No Debt 的判据能撑住吗？** 我们用的判据是"记录的对象是人还是事"：数事允许，数人禁止。它拦住了红点/在线/追赶，但拦不住"换个名字的同一件事"。静态扫描词表只能算警报器。
3. **`author_kind` 不落库、由 `members.kind` 派生——如果成员的 kind 会变，历史消息的分类就会跟着变。** 我判断"kind 描述成员性质、不常变"，但这是个假设，不是事实。
4. **Bridge Contract 的 8 条不变量里，第 4 条（不自动重放）与"用户体验"天然冲突。** 真实网络下失败是常态，坚持不重放意味着用户要手动重发。我选择不自动重放（因为可能是"其实已经执行了"），代价是否可接受？
5. **P1.2 的视觉对象是"版本只增不改"**，这意味着误操作也永久留在历史里。我们还没有删除/归档机制。这是原则，还是偷懒？

## 8. 一句总结

**路线是清晰的，主要路径是跑通过的；但"三个真的不同的 AI 在同一间屋子里说话"这件事还没有发生一次。** 目前完成的是让它发生时不会撒谎的地基：消息不会被改写、失败不会被伪装成发言、历史不会因为迁移而消失。

下一步的顺序不是"加功能"，而是：确认 Bridge Contract → 服务端接真实 Runtime → 一次真实 prompt（授权后）→ 房间里第一次出现第二个真实成员。
