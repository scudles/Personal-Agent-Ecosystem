## 0. 前提：身份对称

**Observer · External Participant 是共同房间的正式成员，与 Hermes、DSH 对称。**

运行形态不同（她不在本机跑进程），不改变成员身份。这条决定了后面所有设计的方向：
凡是按"她是我们邀请来的客人"设计的机制（外部批注、只读视角、特殊标记），一律不用。
**她是成员；成员说的话，其他成员该能听见。**

## 1. B1 · 共同上下文可见性（选 A：携带式）

### 规则

> Observer 说过的话，在她说话之后的**下一次** Agent 正常执行时，按权限规则进入该 Agent 的上下文。
> 不实时唤醒、不增加未读/在线/待回复状态、不因她发言触发任何模型调用。

### 机制（已实现）

新增一张很小的表，只记"这个成员在这个房间已经被告知到哪一条"：

```sql
agent_context_watermark(
  member_id, room_id, last_message_id, updated_at,
  PRIMARY KEY (member_id, room_id)
)
```

开跑前：

1. 取该成员的 watermark（没有就从 0 开始）
2. 取 `id > watermark` 且 `origin='mcp'`、作者为 observer 的消息
3. 与讨论轮次的 context 合并（讨论 context 在前，携带 delta 在后，按 message id 升序）
4. 超过 `MAX_CONTEXT_MESSAGES` / `MAX_CONTEXT_BYTES` → **在创建 run 之前 400**，不截断
   （截断会让她以为只说了一半，比失败更糟）
5. run 结束（无论成功失败）后，把 watermark 推进到本次带上的最大 message id

### 为什么是 watermark 而不是"最近 N 条"

"最近 N 条"会让同一句话反复出现在每次执行里，Agent 分不清"这是新的"还是"这句话一直在"。
watermark 只投递**没投递过的那部分**，符合 Observer 的"Shared Context Delta"。

### 边界（明确不做）

- 不做未读红点、不做"她等你回复"计数——**投递是内部的，不是社交压力**
- 不因为她的发言去叫醒任何 Agent；只在人类已经发起的那次执行里顺带带上
- 她的话不进 `session`（那是成员自己的记忆），只进当次 `context`（本次的材料）

## 2. B6 · 写权限正式规则

**这是当前阶段的能力边界，不是永久限制。** 变更需要一次明确决定，而不是顺手改代码。

| 能力 | 当前 | 说明 |
| --- | --- | --- |
| 发布普通消息 | ✅ 允许 | `post_message`，作者为她，来源 `origin='mcp'` |
| 发布画布标注 | ✅ 允许 | `post_annotation`，钉具体版本 |
| 编辑/删除他人消息 | ❌ 不允许 | 房间整体 append-only；她也改不了自己的 |
| 创建讨论 | ❌ 暂不允许 | 讨论的开始由人控制 |
| 触发其他 Runtime | ❌ 不允许 | 说话不派活 |
| 自主发起模型调用 | ❌ 不允许 | 无进程；且不可由她诱发 |
| 频率 | 20 条/滚动小时 | 重试靠 `clientRequestId` 去重 |

**落实方式**：这些数字和开关集中在一个策略模块里，工具从策略读，不用散落的常量；
另有一条测试断言"工具列表 = 策略"，避免文档和代码各说一套。

## 3. B2 · 讨论参与者与 Runtime 执行者分离（最小设计，待做）

**问题**：现在"参与者"等价于"有 run 的成员"，所以她的意见进不了轮次。

**最小做法**：不动 `runs`，加一张 append-only 的旁表：

```sql
discussion_entries(
  id, discussion_id, message_id, round, member_id, created_at
)
```

- 讨论分组改为读"`runs` 的回复 + `discussion_entries` 的记录"，按 `(round, message_id)` 排序
- 她的发言**不伪造 run**：没有触发、没有 session、没有执行过程，只有"她在第 N 轮说了这句"
- 轮次推进仍由人（现有 `POST /api/discussions/:id/rounds`），她只能落在已有轮次里
- 撤销/删除：不提供（append-only）；她说错了就再说一句，历史保留

**不做**：让她推新轮、让她改别人轮次里的发言。

## 4. B7 · 共享项目资料白名单（最小设计 → 直接实现）

**原则：白名单是显式文件，不是文件夹名的推断。**

- 一个配置：`studio-alpha/.data/bridge/shared-files.json`，内容是**绝对路径**列表
  （可写目录或单文件），由人维护，不自动扩
- 解析时 `realpath`（解析符号链接、`..`、UNC），再判断是否命中白名单
- **仍然拒绝**：`.env`、密钥类文件、`.git`、`node_modules`、`.data`（即使被列进白名单）
- 单文件 64 KiB 上限，超了拒绝不截断
- 默认**不包含** Hermes / DSH 的私人目录、任何 `profiles/`、任何 home 配置
- 未命中白名单 → `不在共享清单里`，并在审计里留一条（谁问了哪个路径）

**不做**：不按"目录名看起来像项目"自动授权；不做通配符递归授权。

## 5. 给 DSH 的一轮技术咨询（只问接缝）

1. `RuntimeInput.context` 里混入"非讨论、非本轮"的成员发言（携带式 delta），
   在 adapter 的 `formatPrompt` 里应该怎么标记，才不会让她误以为这是"用户刚说的话"？
   我倾向沿用 `[shared message id — author]` 块头，但需要你确认它与讨论 context 的块头是否要区分。
2. watermark 在 run **结束后**推进是否安全？如果一次执行中途崩溃，下次会重投同一批 delta
   （同一句话出现两次），我认为"重投"比"漏投"可接受，请你判断 adapter 侧有没有更省的做法。
3. `context` 上限目前是条数 + 字节（20 条 / 50 KiB）。携带式 delta 会长期挤占这个额度，
   是否需要在契约里明确"超限即 400，不截断"——现在是这么做的。
4. 剩余一个来源问题：她的消息 `origin='mcp'`、`member_id='observer-white'`、无 run。
   如果 adapter 只认"run 产出的消息"，需要在契约里补一句说明这是合法的输入来源。

不需要重新审查七项，只回答这四条。
