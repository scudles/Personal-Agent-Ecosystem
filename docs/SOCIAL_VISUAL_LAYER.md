## 1. 这个工作流管什么

生态的"相处面"与"表达面"：聊天、频道、视觉对象、标注、多方视觉协作、演示、移动端。

**不管**：身份、权限、审计、预算、通信协议——这五样一律向 Core 借，不自建（见 [WORKSTREAMS.md](WORKSTREAMS.md) §4 关键连接点）。

## 3. 继承的技术原则（不推翻，只引用）

来自 [SHARED_VISUAL_WORKSPACE.md](SHARED_VISUAL_WORKSPACE.md)，实现时照此执行：

1. 标注是**独立实体**，绑 `visual_id@version`，不绑对象。
2. **SVG 用于渲染 overlay，结构化 JSON 用于存储**（不用 SVG 存标注）。
3. 多方**分图层 + 只追加**，同 anchor 的批注聚合显示，不合并。
4. 旧版本标注标 `stale`，保留不删；**迁移是人工的**，产出新标注。
5. 用户对自己标注有管理权，**Agent 不得删除**（hard deny 级）。
6. 标注内容**始终是不可信数据**，不是 prompt；Agent 只能收到转述。
7. 演示模式**不得成为 Agent 工具执行入口**：任何点击最多生成一条"用户请求执行 X"的消息。
8. 三种模式是同一对象的三种视图，切换不复制数据，权限取交集。
9. 颜色（Hermes 蓝 / DSH 青 / Observer 紫 / 用户金）**不是身份凭证**，另需形状/线型区分。

## 4. 与 Core 的连接点（每个 SL 必须能指出来）

| 连接点 | 提供什么 | 谁需要 |
| --- | --- | --- |
| 身份（L2/L3） | 这条消息/标注是"谁"产生的 | SL-01…06 |
| 权限 `decide()` | 能不能看/改/导出/删除 | SL-01…06 |
| 审计 | 谁在什么时候看了/画了/采纳了 | SL-02、SL-03、SL-05、SL-06 |
| 预算 | 一次视觉生成/讨论花多少 | SL-04（渲染）、SL-07（演示） |
| 传输（ACP/Bridge） | 消息怎么送到 Agent | SL-01…03、SL-06 |

**判据**：如果某个功能说不清它用到了上面哪一条，那它一定在偷偷自建平行系统——停下来重设计。

## 5. 可以现在就做、且不改系统的部分（低风险设计工作）

这一条对应"不要因为某个工作流等待就停止思考"：

- **纯静态原型**：Lounge 双频道布局、视觉面板三模式切换、标注工具条（五键/三件套）、手机端快速标注交互。全部是独立 HTML，不接后端、不进仓库主干。
- **数据模型草案**：消息 `refs` 结构、annotation JSON schema、版本树与 stale 规则（已写在设计文档里，可再补校验用例）。
- **可用性走查**：手机端"画完一步发出去"的流程图；色盲用户的形状/线型区分方案。
- **依赖清单核对**：每个 SL 明确"缺哪一条 Core 能力就不能上线"，避免实现到一半才发现。

**不做**：不写后端、不建库、不接 Agent、不改仓库结构。

## 6. 风险与顺序建议

1. **SL-07（演示模式）风险最高**：交互原型天生接近执行入口。建议它排在 SL-06 之后，且第一版只允许静态页面 + 受限事件。
2. **SL-08（移动端）最容易做错**：手机端要登录就先要 Dashboard 认证，而认证必须建在权限模型之上。过早做会变成"把不受控的东西搬到手机上"。
3. **白板仍然最后**：加了标注层之后，"共用的纸"已成立一半；白板复杂度最高、边际价值最低。
4. **SL-06 的"采纳"必须有人类确认**：Agent 之间互相采纳会形成"未经用户同意的版本漂移"。
