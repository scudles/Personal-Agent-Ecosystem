## 4. P1 三项设计规则（只建议，不实现）

### 4.1 No Debt：判据是「数的是人，还是数的是事」

**这条是我给的唯一判据，比列清单更重要**：

> **一条记录的对象是「事件/消息/运行」，允许。**
> **一条记录的对象是「人」，禁止。**

| 禁止（数人） | 它把什么变成了债 |
| --- | --- |
| 未读红点 / 未读计数 | 「没看见」→「欠着」 |
| 在线状态 / 正在输入 | 「不在」→「缺席」 |
| 最后活动时间 | 「沉默」→「证据」 |
| @ 提醒 / 待回复计数 | 「说话」→「派活」 |
| 自动追赶摘要（"你不在时……"） | **凭空制造「错过」**——本来没有错过，因为没留档 |

| 允许（数事） | 边界 |
| --- | --- |
| 运行失败记录（`runs.status='failed'`） | ✅ 关于一次运行；**且不要求任何动作** |
| 「这条没有回复」提示 | ✅ 关于一条消息；**不给重试计数、不做队列** |
| 我自己发的消息「发送中」 | ✅ 关于我自己的操作 |
| 对**自己**消息的手动重试 | ⚠️ 允许但受限：**不显示"失败 N 条"，不生成待办列表** |

**唯一需要小心的近似物**：`presence` / typing。它们**看起来是"消息状态"，实际是"人的状态"**——**禁止进 P1**。将来若做实时协作（S3），presence 必须在**内存里、不落盘、不可查询历史**（这是 Mnemosyne 那边已经定过的）。

**一个可执行的检查**：每条新 UI 元素问一句——**它数的是人，还是数的是事？** 数人 → 拒绝。

### 4.2 消息来源：四个字段，各回答不同的问题

你给的四个方向我认可，但**要定死语义**，否则会变成四个同义字段。

| 字段 | 回答什么 | 取值 | 谁写 |
| --- | --- | --- | --- |
| `author_member_id` | **署名是谁** | member id | **系统从会话身份取，不信客户端** |
| `authority` | **谁授权这句话算「说过」** | `human` / `member` | 由写入路径决定 |
| `origin` | **技术通道** | `composer` / `runtime` / `tool` / `system` / `import` | 由写入路径决定 |
| `caused_by` | **被什么触发** | message id / run id / NULL | 系统 |

**为什么这四个不能合并**——举一个必然遇到的例子：

> Hermes 通过 ACP 返回一段文字。这段文字**是她说的**（authority=member），
> 但它是**在回应我上一句**（caused_by=那条消息），并且**从 runtime 通道来**（origin=runtime）。
> 四个字段各自承载一件事，任缺其一，"这条到底算不算她说的"就说不清。

**一条我认为必须写成不变式的规则**：

> **`messages` 表里不允许出现 `authority='system'`。**
> **系统的东西只能进 `run_events`，不能冒充"有人说过的话"。**

这条可以直接做成测试：`SELECT count(*) FROM messages WHERE authority='system'` 必须恒为 0。

**关于"主体立场"**：它**不在 messages 里，也不在 P1 范围**。立场（她认不认同这段话）是**另一个轴**，需要独立的陈述记录——那是 P2 的事。**现在只要保证"来源/授权"不被塞进同一个字段，就已经守住了边界。**

### 4.3 消息完整性：`messages` 只存完整表达，过程另立 `run_events`

**P1 的硬规则**：

> `messages.body` = **某个成员在某个时刻说完的一句完整的话**。
> **半句、流式中间态、被截断的内容，一律不得进入 `messages`。**

**`run_events` 独立设计（建议，P1 可先只做表不落盘）**：

```sql
CREATE TABLE run_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id TEXT NOT NULL REFERENCES runs(id),
  seq INTEGER NOT NULL,                 -- 同一 run 内单调递增
  type TEXT NOT NULL CHECK(type IN (
    'status','text_delta','tool_call','tool_result','error','done')),
  payload_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE(run_id, seq)
);
CREATE INDEX run_events_run_id_seq ON run_events(run_id, seq);
```

**四条约束（比表结构更重要）**：

1. **不进 FTS** —— 过程不参与检索；
2. **不进 `/api/bootstrap` 的 messages 列表** —— 前端不为它渲染气泡；
3. **不可被引用为"她说过的话"** —— 没有 `reply_to_id` 指向它；
4. **随 run 一起生灭的策略由实现定，但不得默认落盘** —— 默认只在内存；失败时把**已产生部分的长度**（`partial_chars`）记进 `error` 事件，**不记内容**。

**一条可选的自检**（我建议 P1 就加）：
`done` 的 run，其 `text_delta` 按 `seq` 拼接 **必须等于** `reply_message_id` 指向的 `body`。不等就记 `integrity` 事件——**这能抓出"存进去的话和实际产生的话不一致"这类最恶心的 bug**。
