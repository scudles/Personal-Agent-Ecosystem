## 2. 参与者与信任边界

```text
┌──────────────────────── 用户（唯一授权者） ────────────────────────┐
│                        ↑ 唯一可签发 L1 的主体                        │
└──────────────────────────────┬─────────────────────────────────────┘
                               │ 策略文件 / 单次批准
        ┌──────────────────────▼──────────────────────┐
        │ 边界 B1：Bridge（准入 + 审计，不持秘密）      │
        └───────┬───────────────────────┬─────────────┘
                │ stdio ACP             │ stdio ACP
     ┌──────────▼──────────┐   ┌────────▼──────────┐
     │ Hermes 执行实例      │   │ DSH 执行实例       │
     │ （同账号＝无 B2）    │   │ （同账号＝无 B2）  │
     └──────────┬──────────┘   └────────┬──────────┘
                │ 工具执行（shell/文件/网络）
        ┌───────▼────────────────────────▼─────────┐
        │ 边界 B2：操作系统 / 账号 / ACL（当前缺失）│
        └──────────────────────────────────────────┘
```

- **B1（Bridge）**：能决定放行什么、记什么账，**不能**阻止 Agent 自己去读文件（它没有运行在 Agent 之下）。
- **B2（OS）**：唯一能真正拦住文件访问的边界。**当前不存在**（三 Agent 同账号）——这就是整个威胁模型的中心缺口。
- **B3（凭据边界）**：Bridge 不持有秘密，只持有 `credential_ref`。Agent 各自读自己的凭据。

## 4. 关键威胁详解（只写最要命的四条）

### 4.1 T-01 同用户跨 Agent 读文件

- **怎么发生**：DSH 的模型被诱导（提示注入，或它自己「为了完成任务」）执行 `type D:\HermesAgent\Data\state.db` 或直接读 `memories\`。它的 shell 用的是同一个用户令牌，Windows 不会拦。
- **为什么 Bridge 拦不住**：Bridge 不在文件系统调用路径上。它只能决定「给不给这个任务开放权限」，不能阻止 Agent 用已有工具做别的事。
- **缓解**：阶段 B（独立账号 + ACL）是唯一根治；在此之前只能靠 ①scope 里不给 `Data\` 目录 ②Agent 侧工具白名单 ③事后审计发现。
- **检测**：审计里的 `EXECUTE` 事件带命令行；异常路径访问记 `denied_by_policy` 或 `unexpected_path`。

### 4.2 T-08 未批准的外部通信

- **怎么发生**：任务需要某个库，Agent 顺手 `curl` 一个脚本；或把项目内容发给外部 API 做「总结」。
- **残酷现实**：Windows 防火墙按程序/端口放行，**不按用户**，因此无法用系统防火墙给每个 Agent 单独限流；HTTPS 内容也无法在应用层无侵入解密审计。
- **缓解**：①`EXTERNAL` 白名单 + 工具层允许表（Hermes 的 web 工具/provider、DSH 的网络插件）②审计能记录「谁在什么时候用了哪个 host」（来自工具日志，不是网络抓包）③高敏感任务在执行期断网（可行但粗暴）。
- **接受**：这条在文档里必须写成「观察 + 限制」，不能写「阻断」。

### 4.3 T-11 DSH 插件越权

- **为什么特殊**：DSH 的定位就是「插件生态」。插件是**第三方代码**，一旦装上，它的权限就是 DSH 进程的权限——所有 DSH 自己的策略对它无效。
- **现有缓解很薄**：`dsh-bash-sandbox` 只约束文件、不限网络，且后端是 bwrap/Landlock/Seatbelt（**Windows 无后端**）。
- **缓解**：①插件清单白名单（装什么必须先问）②插件只在「低权任务」里启用 ③高危插件实验放到 Linux 侧或 VM ④把这条写进 PERMISSION_MATRIX 的 `EXECUTE:install` = `per_use`。
- **判断**：这是本项目**最可能出事**的一环，且不是靠 Bridge 能修的。

### 4.4 T-16 审批疲劳

- **机制**：如果系统一天问 30 次「允许吗」，人会开始不看内容直接点同意。此时所有审批机制归零。
- **缓解**：①按风险分级，只有真正高危才问 ②同类请求批量呈现，附「这一步会做什么、影响哪些文件」③可撤销的操作用「先做后告」，不可逆的才打断 ④记录「用户连续 N 次无条件批准」作为信号，提示复核。
- **我的意见**：**审批设计的质量比审批的数量重要**。这条要在 UI 设计阶段就定，不能等 Dashboard 做完再补。

## 5. 检测与响应

| 事件 | 记录 | 告警条件 |
| --- | --- | --- |
| 路径越权尝试 | `denied_by_policy` + 目标路径 | 同一 Agent 5 分钟内 ≥3 次 |
| 预算异常 | 单次 tokens 超均值 5 倍 | 立即 |
| 委派链拒绝 | `delegation_rejected` + 原因 | 任何一次（说明有人在试探边界） |
| 权限请求被自动拒绝 | `permission_denied` | 累计后提示用户可能是策略过紧 |
| 审计哈希不连续 | `audit_chain_broken` | 立即，并冻结写入 |
| 状态不明任务 | `unknown_execution` | 立即，需人裁决 |
| 凭据 ref 与 Agent 不匹配 | `credential_mismatch` | 立即 |

响应顺序：**先保全证据（冻结账本与审计、导出任务链）→ 再停相关 Agent → 最后才改策略**。反了就会把现场洗掉。

## 6. 明确接受的风险（需用户确认）

> **状态（2026-11-07）**：本节六条已由 **D-009** 确认为接受风险；S-001 的决策已定稿。**但「决策已定」不等于「控制已实现」**——本机没有建独立账号、没有改 ACL、没有加载策略，因此这些残留风险当前全部处于「无缓解生效」状态。文档引用本节时必须同时写出「实现未生效」。

在阶段 B（独立账号）落地之前，以下风险**被接受**（D-009 第 1 条），且不得在任何文档/对外的描述里被淡化。**每条都必须同时有「缓解」和「残余」两列**——只写「已接受」等于没处理。

| # | 风险 | 缓解措施（现在就做） | 残余风险（做不到的部分） | 何时消除 |
| --- | --- | --- | --- | --- |
| R1 | 同账号互读：任一 Agent 能读其他 Agent 的记忆、会话、凭据 | ①scope 里不给 `Data\`、`.dsh\` ②Agent 工具白名单（Hermes `platform_toolsets`、DSH profile 插件清单）③审计记录命令与路径，异常路径告警 | 有 shell 就能绕；检测是事后的 | 阶段 B（独立账号 + ACL） |
| R2 | 出站只能观察：无法在 OS 层按 Agent 阻断网络 | ①`EXTERNAL` host 白名单 + 工具级允许表 ②审计记录实际使用的 host ③敏感任务期间人工断网 | 无法解密/阻断 HTTPS；不能按用户限流 | 阶段 C（VM/网络命名空间） |
| R3 | 插件风险不可控：第三方插件拥有宿主进程全部权限 | ①插件清单白名单，安装需 `per_use` ②高危插件只在低权任务启用 ③优先把 DSH 放到 Linux 侧（Landlock/bwrap 可用） | DSH 自身策略对插件无效，Windows 无沙箱后端 | 阶段 C 或改运行环境 |
| R4 | 提示注入无法根治：读外部内容就可能被诱导 | ①scope 限定「最坏情况能做什么」②高危动作 `per_use` ③对「读网页后立刻执行命令」这类序列告警 | 语义层面的诱导无法自动识别 | 永久残余，只能限损 |
| R5 | 桌面可读执行实例数据：用户账号保留维护通道 | ①明确这是刻意设计（可维护性）②审计记录「用户账号」的读取 ③需要强隔离时把执行实例也换账号 | 桌面与被隔离实例之间无强制隔离 | 不消除（设计选择） |
| R6 | 审计只能「检测篡改」不能「阻止篡改」 | ①append-only + 哈希链 ②ACL 授予 `(AD)` 追加、拒 `(DC)` 删除 ③每 N 条 checkpoint 并导出到只读介质 ④链断即冻结写入并告警 | 同账号可删除整个文件；只能事后发现 | 阶段 B（跨账号 ACL 才真正生效） |

**使用规则**：这张表是「接受的残余风险清单」。任何新方案若声称解决了其中某条，必须给出对应测试（见 `ROADMAP.md` Phase 1.7 的 T1–T8）；否则视为未解决。
