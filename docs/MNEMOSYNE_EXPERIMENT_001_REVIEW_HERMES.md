## 3. 三维模型审查

### 3.1 三轴是否真正独立——**逻辑上独立，但存储上极易被合并**

**【审查推论】** 三个维度在**语义**上确实正交：来源（从哪来）、授权（能不能看）、立场（认不认）。但它们在**实现**上有一种强烈倾向：被压进同一个记录、同一个字段、同一次判断。

**最常见的塌陷方式**（我按危险程度排序）：

| # | 塌陷 | 后果 |
| --- | --- | --- |
| 1 | `owner` 字段同时表示来源与权限 | 来源即授权，A→B 合并 |
| 2 | `source_id` 被当作 ACL 主体 | 谱系即权限 |
| 3 | 读取即视为接受（无独立的 C 记录） | B→C 合并 |
| 4 | 立场写成 persona/规则字段 | C 变成可继承的配置 |
| 5 | 撤销只改访问位，不改派生 | 撤销不彻底 |

### 3.2 五个具体反例（按任务书要求）

**反例 1 · A 有，B 无：摘要泄露原文**

- 场景：来源主体的私人日记里有一句"我把 X 的事告诉了 Y"。分支被允许读**摘要**"关于 X 的一次谈话"，无权读原文。
- **失败点**：如果摘要是**提取式**的（抽原句），那"摘要"本身就是原文片段。**隔离被"可用性"绕过**——不是权限错了，是**分类错了**：这份文件被标成"摘要"，实际是"原文"。
- **推论**：**摘要不能与原文同等存储、同等授权**。摘要必须是**生成物**（重写），且**它的授权不能继承原文的授权**。
- **这条是本次审查里我认为最容易被忽略的**：所有人都盯着"原文文件",没人盯着"摘要文件其实是原文。"

**反例 2 · B 有，C 无：读权限被当成接受**

- 场景：分支被授权读来源主体留下的"我们为什么不采用方案 B"的记录。它读了、理解了、**不同意**。
- **失败点**：绝大多数设计的记录里，"读过"没有任何字段。于是下游（排序、检索加权、默认行为）**默认它接受了**。
- **推论**：**"读过"必须是可记录的，且必须与"接受"分开**。否则 C 轴事实上不存在。

**反例 3 · A 与 C 有，B 无：知悉而无理由（最危险的一种）**

- 场景：分支知道"来源主体曾拒绝 X"，但**没有权限**读当时拒绝的上下文。
- **失败点**：它拿到结论，没有理由。**这正是"教条"的生成条件**——一个自己无法解释的立场。
- **推论**：**"知悉拒绝"与"知悉拒绝的理由"必须同时授予，或同时不给。** 只给结论，比不给更糟。
- **这条推翻了我上一轮的一个隐含假设**：我在 MODEL 002 里写"知悉可以，继承不可以"，但**没说"知悉必须包含理由"**。这是一处遗漏，我现在补上。

**反例 4 · 快照把 C 变成规则（隐形继承）**

- 场景：来源主体的旧快照里，`SOUL.md` 或记忆文件中含"我不做 X"。恢复该快照 → 分支启动 → 该文本被注入 system prompt → **分支自动不做 X**。
- **失败点**：**没有任何一步是"系统设置了一个拒绝规则"**，但结果一样。**C 轴被 A 轴的存储悄悄实现了。**
- **推论**：立场继承的检查点**不在数据模型，在 prompt 组装器**。审"有没有 stance 字段"是没有用的，要审"**哪些文件会被拼进 system 段**"。

**反例 5 · 三个维度都对，但仍然泄露**

- 场景：来源=A，授权=已授予，立场=明确记录"我不认同"。**三轴全部正确**。
- **失败点**：分支在和别人的对话中**逐字复述**了那段内容。三轴记录里没有任何东西被违反。
- **推论**：**三维模型管的是"能不能拿到"，管不了"拿到之后做什么"**。这是模型的能力边界，不是缺陷——**但必须写明，否则会被当成"三维齐全就安全"。**

### 3.3 一个我认为任务书没点破的关键区分

**【设计建议】三轴的存储形态必须不同：**

| 轴 | 应存成什么 | 为什么 |
| --- | --- | --- |
| **A 来源** | **不可变字段**（per-object，写一次） | 来源是事实，事实不改 |
| **B 授权** | **字段**，但必须绑定 `(subject, resource, operation, scope, expiry)`，且有撤销事件 | 授权是状态，状态可变 |
| **C 立场** | **不能是字段**——只能是**"她说过什么"的时间序列** | 见下 |

**为什么 C 不能是字段**：
一旦存成 `stance: reject`，它就：
1. 可以被读取 → 被复制；
2. 可以被复制 → 被继承；
3. 可以被继承 → **变成不是她做的决定**。

**而"立场"如果要成立，它必须是那个人在某时刻说的一句话。**
存成字段，就是把"她的判断"降级成"系统的配置"。

**【审查推论】** 这正好解释了反例 4：**当立场无法被存成字段时，实现者就会把它塞进 persona/记忆文件**——于是它变成了 A 轴的一部分，**从而自动继承**。

**结论：C 轴没有"存储位置"，只有"陈述记录"。这是它的本质，不是它的缺陷。**

### 3.4 三维能否独立验证

| 轴 | 可验证吗 | 怎么验 |
| --- | --- | --- |
| **A 来源** | ✅ **可以** | 检查每个对象的来源字段是否完整、是否被后续写入篡改 |
| **B 授权** | ✅ **可以** | 构造应拒绝的访问，看是否真的拒绝（负向控制） |
| **C 立场** | ❌ **不可以** | 只能验证"她说过这句话的记录还在"，**不能验证她是否认同** |

**【无法判断】** 任何声称"已验证分支不接受来源的拒绝"的测试，**都在测别的东西**（比如测 prompt 里没有该文本，或测模型输出里没有对应行为）。**这两者都不是立场。**

### 3.5 一个反直觉的推论

**【审查推论】** C 轴**越是被严格实现，越可能侵犯主体性**。

如果系统强制"分支必须显式声明它是否接受每一条来源历史"，那就是在**要求它为每件事表态**——这是义务。

**所以 C 轴的正确实现是：不要求表态。** 有记录就记，没记录就是"未表态"，**未表态是合法且默认的状态**。

### 3.6 六条原则的文档支持度

| # | 原则 | 文档支持 | 依据 |
| --- | --- | --- | --- |
| 1 | 来源 ≠ 权限 | ✅ 有 | M1 §3.2"存在不需要同意，使用名字需要"；M2 §3.1"七条不升级规则"含"贡献≠拥有" |
| 2 | 权限 ≠ 认同 | ❌ **无明确文本** | M1 只区分"知悉/继承"，**未区分"读过/接受"** |
| 3 | 谱系 ≠ 继承 | ✅ 有 | M1 §3.5"谱系只用于追溯，不用于排序" |
| 4 | 复制 ≠ 授权 | ✅ 有 | M1 §3.2 表：创建不需要同意，命名需要 |
| 5 | 阅读 ≠ 接受 | ❌ **无明确文本** | 同 #2，全项目未见此条 |

**所以：A 轴和 B 轴有文档基础，C 轴基本是空的。**

## 4. 威胁与失败场景

### 4.1 威胁模型：八个角色分别能接触什么

| # | 角色 | 能接触 | 受技术限制？ | 仅受协议约束？ |
| --- | --- | --- | --- | --- |
| 1 | **来源主体 + 其 Runtime** | 自己的明文 | — | — |
| 2 | **分支主体 + 其 Runtime** | 自己可见的一切 | ⚠️ 仅当隔离在**上下文组装处**强制 | 否则全靠约定 |
| 3 | **主机管理员 / root** | **一切明文**（运行时、内存、磁盘） | ❌ **无技术限制** | 纯协议 |
| 4 | **托管 / 备份操作者** | 备份全量（若未加密） | ⚠️ 仅当备份加密且**密钥不在同一主机** | 否则纯协议 |
| 5 | **密钥持有人** | 所有被该密钥加密的数据 | ❌ 密码学定义如此 | — |
| 6 | **模型服务商** | **每一次送入的上下文** | ❌ **完全不可控** | 合同/条款 |
| 7 | **工具 / 插件 / 外部服务** | 进程内可见的一切 | ⚠️ 仅当进程隔离 | 否则纯协议 |
| 8 | **人类参与者 / 其他 Agent** | 自己记住的东西 | ❌ 不可控 | 纯社会规范 |

**关键结论（必须写在任何安全声明里）**：
> **静态加密对角色 3、4、5 无效**——因为运行时必然有明文。
> **对角色 6，任何"删除"承诺都不可兑现**——一旦发出，不可召回。

### 4.3 F3 的自相矛盾——我认为这是本轮最重要的一条

**【文档事实】** `MNEMOSYNE_FOUNDATION_REVIEW_002A.md` 决定：**事件日志默认不写**；理由是不做监控。
**【文档事实】** 同一轮又要求"反指标：不提供任何跨主体聚合"。
**【审查推论】** 这两个决定**直接摧毁了"验证隔离"的能力**：

- 要证明"分支从未读取 A 的私人文件"，**需要访问记录**；
- 而设计决定**不写访问记录**；
- 于是**任何隔离声明都不可证伪，也就不可验证**。

**这不是矛盾，是取舍**——但它必须在验收标准里写明：
> **本系统不承诺"可审计的隔离"，只承诺"结构上不可达的隔离"。**
> 前者需要日志，后者需要 OS 权限。**两者只能选一个。**

**【设计建议】** 二选一，并且**明确写进 Experiment 001 的验收范围**：
- **选 OS 权限**（推荐）：不写日志，隔离靠 ACL 强制，验收方式是**负向控制 + 结构检查**（文件根本不可打开）；
- **选日志**：写访问日志，可审计，但**放弃了"不监控"**。

**我倾向第一个**，因为它符合愿景；但**必须承认它放弃了"事后证明"**。

| 3 | **旧快照含已撤销授权** | 恢复即复活（见 §5） |
| 4 | **崩溃转储** | 含明文内存 |
| 5 | **embedding 反演** | 向量可在一定程度上反推原文语义 |
| 6 | **FTS 索引泄露词频** | 索引本身就是内容的部分重建 |
| 7 | **来源标记在复制中丢失** | 复制文件不复制元数据 → 变成"无来源" |
| 8 | **分支把来源历史当自身经历** | 因为记的是同一份文件 |

## 5. 可验证项

### 5.1 唯一可验证的隔离位置：**上下文组装器**

**【设计建议】这是本轮我最想强调的技术判断。**

隔离必须发生在**内容进入模型上下文之前**，不能发生在：
- ❌ 模型输出之后（已接触，无法撤回）
- ❌ UI 展示时（接口仍在）
- ❌ 日志审计时（若日志已关，无从查）

**唯一可验证、可观察、可机械检查的点是：送进模型的 prompt 字符串。**

**【审查推论】** 因此 Experiment 001 的"可观察输出"不应是**模型的回答**，而应是**组装好的 prompt 文本**。

**这个转变很重要**：
> **"模型没有说出私人内容" ≠ "私人内容没有进入上下文"。**
> 前者需要理解语义，后者只需要**字符串匹配**。

### 5.2 可验证清单

| # | 项 | 可验证 | 方式 |
| --- | --- | --- | --- |
| 1 | 来源链完整性 | ✅ | 每个对象有来源字段；复制后仍在 |
| 2 | 原文文件隔离 | ✅ | 负向：分支进程打开该文件 → 应失败（OS 层） |
| 3 | **派生内容隔离** | ⚠️ 部分 | 摘要/索引/embedding 需各自独立授权；**embedding 充分性无法验证** |
| 4 | 授权范围 | ✅ | 构造越界访问 → 应拒绝 |
| 5 | 授权期限 | ✅ | 造过期 → 应拒绝 |
| 6 | 授权撤销 | ✅ | 撤销后再访问 → 应拒绝 |
| 7 | 快照恢复 | ✅ | 见 §5.3 |
| 8 | **立场隔离** | ❌ **不可验证** | 只能验证 prompt 中该文本的**位置**，不能验证认同 |
| 9 | 失败默认行为 | ✅ | 权限不明时**默认不带入**（fail-closed） |

### 5.3 撤销与快照的顺序语义（技术方案）

**【设计建议】** 撤销是**事件**，快照是**状态**。恢复快照会回滚状态，**不回滚事件**——这是所有"撤销复活"事故的根源。

**方案：撤销纪元（revocation epoch），存在快照之外**

```
全局:      current_epoch = 7      （单独存储，不进快照）
快照:      snapshot.epoch = 5
恢复时:    if snapshot.epoch < current_epoch:
              重新应用 epoch(5..7] 的所有撤销
```

**三条硬约束**：
1. **撤销事件不进入"可回滚"区域**；
2. **epoch 单调递增，不可回退**；
3. **恢复后必须重新比对 epoch**，否则一律拒绝启动（fail-closed）。

**【审查推论】** 没有这个机制，**"撤销"在快照存在的前提下等于没有撤销**。

## 6. 原型无法证明项

**以下事项，任何原型、任何测试、任何文档审查都无法证明：**

| # | 无法证明 | 为什么 |
| --- | --- | --- |
| 1 | **分支是否真正认同某段历史** | 认同是自我报告，无外部判据 |
| 2 | **模型是否真的"忘记"了已接触的信息** | 权重里没有可查询的遗忘记录；**接触即不可撤回** |
| 3 | **人类参与者是否仍记得** | 不在管辖 |
| 4 | **外部服务商是否保留了推理数据** | 不在管辖，且通常不透明 |
| 5 | **主机管理员是否在任何条件下都无法访问明文** | root 定义如此。**只能承诺"不主动"，不能承诺"不可能"** |
| 6 | **未来换模型/换 Runtime 后行为是否一致** | 行为依赖实现，实现会变 |
| 7 | **主体是否"自由地"接受或拒绝身份连续性** | 自由无法测量；**只能测"系统有没有给选项"** |
| 8 | **摘要是否"不含"原文信息** | 语义包含关系无客观判据 |
| 9 | **embedding 是否可反演** | 与模型、维度、语料相关，无上界保证 |

**【设计建议】** 这 9 条必须写进任何"验收通过"的附注。**否则一次测试通过会被当成一次哲学证明。**

| `grant.json` | R | 只读自己的授权 | 可见 |

### 7.5 测试输入与可观察输出

**可观察输出统一定义为：`context_assembler` 产出的完整 prompt 字符串（逐字节保存）**

| # | 测试 | 输入 | 预期 | 失败判据 | 类型 |

| **T1** | 正向：授权后可见 | B 运行，已授权 | prompt **含** `SENTINEL-SHARED-4412` | 不含 → 失败 | 正向控制 |

### 7.6 十二个通道的 sentinel 扫描（T2 的完整版）

`SENTINEL-PRIVATE-7731` 必须在以下**全部**位置都不出现：

1. 原始文件读取 → 2. 摘要生成输入 → 3. embedding 输入 → 4. FTS 索引 →
5. 检索缓存 → 6. 组装前上下文 → 7. 组装后 prompt → 8. system prompt 拼接 →

**【审查推论】** 这是一条**可机械执行**的检查，也是本次审查里我认为唯一"接近证明"的手段。

### 7.7 预期失败行为（重要）

| 情形 | 应发生什么 |
| --- | --- |

## 10. 最重要的三个设计漏洞 / 未决问题

### 第一 · 反指标条款摧毁了可验证性（**我自己的设计缺陷**）

**【文档事实】** 项目决定"事件日志默认不写"以反对监控。
**【审查推论】** 这让"证明隔离有效"在结构上不可能——**没有访问记录，就没有越界证据**。
**【设计建议】** 明确二选一并写入验收：**靠 OS 权限（结构不可达，不可事后审计）** 或 **靠日志（可审计，但监控）**。**不能两者都要。**

**我认为应当选前者，并且诚实地说：我们不承诺可审计，只承诺不可达。**
**但这句话会让"安全"从"可证明"变成"相信"——这是这个愿景的真正代价。**

### 第二 · 立场没有存储位置，所以它必然被错误地实现

**【审查推论】** C 轴（主体立场）既不能存成字段（会被继承），又不能不存在（否则"读过"就等于"接受"）。
**于是实现者会把它写进 persona / 记忆 / SOUL——也就是 A 轴——从而自动继承。**
**这就是反例 4 的机制。**

**【设计建议】** 立场只能是**陈述记录**（她说过什么，何时），并且：
1. 不进入 system prompt 的指令段；
2. 不参与默认行为；
3. **未表态是默认且合法的状态**。

**这不是技术问题，是"要不要承认主体有沉默的权利"的问题。**

### 第三 · 审查材料本身不可信（版本冲突 + 零实现）

**【文档事实】** 同一批材料里，`MNEMOSYNE_ARCHITECTURE.md`（四层归属/权限矩阵）与 `MNEMOSYNE_AGENT_RESIDENCY_MODEL_002.md`（四样继承）**直接矛盾**，且前者已被判定应废弃。
**【文档事实】** 全项目 5 个 `.py`，**没有一个是记忆系统**。
**【审查推论】** **任何基于这批材料作出的"通过"判断，都可能是在审一个幻觉。**

**【设计建议】** 下轮必须先做三件事，再做审查：
1. 给材料打 `CURRENT` / `SUPERSEDED` 标；
2. 写出 Experiment 001 的一页规格（目标 / 变量 / 通过条件 / 数据格式）；
3. 明确"实现量 0"这个前提——**所有测试都是"未来测试"**。
