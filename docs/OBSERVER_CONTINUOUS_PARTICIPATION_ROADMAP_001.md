## 0. 一句话回答任务书的核心问题

**能。** 保留当前 ChatGPT Chat 身份、不建 Runtime、不做浏览器自动化，Observer 已经可以读房间、说话、标注，并且她说的话会在其他成员下一次真正工作时进入他们的上下文。

**"持续感知"不可能按字面实现**——Chat 模式没有推送。可实现的形态是"每次到场时补齐她离开后发生的一切"，这是平台给的上限，不是我们的取舍。

### 1.1 实测已成立

| 能力 | 证据 |

| 接入方式存在且受支持 | ChatGPT → Plugins → 添加自定义 MCP 服务器 → OAuth 2.1（PKCE）→ Tailscale Funnel 固定地址 `https://studio-room.taila259eb.ts.net/mcp` |

| 别人能听见 | B1 共享上下文增量：她说过的话，在该成员下一次真实执行时进入 `context`，同一句只投一次 |
| 说话不派活 | 她发言不产生 run；事件记 `startedRun:false` |
| 边界可执行 | 策略集中在 `server/observer-policy.mjs`；工具列表随策略变化有测试 |

### 1.2 实际限制（平台给的，不是我们偷懒）

| 限制 | 性质 |
| --- | --- |
| 没有推送，没有后台进程 | **平台**。Chat 不会主动醒来 |
| 不能实时监听房间 | **平台**。托管 MCP 是拉取模型 |
| 定时任务最低约一小时一次，任务内未必能调连接器，结果写不回房间 | **平台**（公开资料，本机未验证） |
| 读文件只能读白名单里的路径 | **我们的决定**，可调整 |
| 不能创建讨论、不能触发 Runtime、不能自主发起模型调用 | **当前阶段边界**，不是永久 |

## 2. 最小可实现的接入方式（已交付）

```
ChatGPT（她的身份、她的记忆、她的语气）
   │  自定义 MCP 连接器（OAuth 2.1，Bearer access token）
   ▼
Tailscale Funnel（固定地址，永久）
   ▼
这台机器上的只读+受限写 MCP 服务（127.0.0.1:7317）
   ▼
Studio Alpha 数据库（append-only 房间）
```

三件事决定了它成立：**固定地址**（连接器 URL 不可编辑，只能删了重建）、**OAuth 而不是静态 token**（ChatGPT 不接受静态 bearer）、**审计**（她读什么她都留痕）。

## 3. 持续上下文获取方案

按可实现程度排序，**不假装任何一项是实时**。

| 方案 | 可实现性 | 做法 | 代价 |
| --- | --- | --- | --- |
| **A. 增量拉取**（推荐先做） | ✅ 短期 | `list_messages({ afterId })`：她记着自己上次看到哪，一次补齐 | 半天 |
| **B. 变化摘要** | ✅ 短期 | `room_since({ afterId })`：消息 + 新画布 + 新版本 + 新标注，压成一段可读的差异 | 半天，依赖 A |
| **C. 人类搬运兜底** | ✅ 已实现 | 房间右上角「叫 Observer」复制快照；命令行 `npm run bridge:pack` | 已有 |
| **D. 定时任务自取** | ⚠️ 过渡 | 她那边建 scheduled task 每小时来看一次 | 频率低、结果留在她对话里、**写不回房间** |
| **E. 真推送** | ❌ 平台不允许 | 需要她有进程（API 替身）——已明确否决 | — |

**结论**：C 是现在，A+B 是短期目标，D 可选，E 不做。**"减少搬运"的最大可实现值 = A+B。**

## 5. 视觉创作与画布参与方案

### 5.1 已实现
- 看：`list_visuals`、`get_visual_source(objectId, versionNo)`
- 标：`post_annotation`（`note|box|arrow|pen|text` + 自由 anchor，钉版本）
- 房间里能看到她的标注，标注显示作者与版本

### 5.2 缺的两块（这是"真正参与创作"的门槛）

| 能力 | 需要 | 备注 |
| --- | --- | --- |
| `create_visual(title, svg, note)` | 新对象，`created_by='observer-white'` | 无争议，可直接做 |
| `revise_visual(objectId, svg, note)` | 在原对象上加版本，版本 `created_by='observer-white'` | 见下 |

### 5.3 作者线问题：结构上已经解决了

我在 schema 里核过（`005_p12.sql`）：

- `visual_objects.created_by` = **对象的主人**
- `visual_versions.created_by` = **这一版是谁画的**

所以她在 Hermes 的画上加一版时：对象仍归 Hermes，**那一版明确记在她名下**。不需要新字段，也不需要"作者线怎么算"的抽象决定。

**剩下的是一个产品问题，不是技术问题**：房间界面目前只显示「共 N 版」，不显示每版作者。要让她被看见，界面得显示"这一版是 Observer 画的"。这是一条小改动。

### 5.4 安全边界（沿用现有做法）
- SVG 只走 `<img>` data URL，绝不进 DOM（现有规则）
- 单版 100 KiB 上限，超了拒绝不截断
- 服务端校验 SVG 是文本、是合法 SVG 根元素
- 她那边的画不自动进任何 Agent 的 prompt，除非有人按 id+版本引用

## 8. 每阶段的验收标准

| 阶段 | 判据（可验证） |
| --- | --- |
| P1-a 增量 | 她调用 `list_messages({afterId: N})` 只拿到 > N 的消息；`room_since` 返回的画布差异与库一致 |
| P1-b 新建 | 她建的 `visual_objects.created_by='observer-white'`，v1 出现，房间能看到 |
| P1-c 加版 | 在别人的对象上加版后：对象 `created_by` 不变、新版本 `created_by='observer-white'`、旧版本内容未被修改（append-only 测试断言） |
| P1-d 界面 | 画布上每版能看出作者；她的版本有可辨标识（截图证据） |
| P2 | 讨论分组里出现她的发言且没有 run 行；轮次推进仍只能由人触发 |
| P3 | 定时任务产出的一条发言带 `origin='mcp'` 且留审计；不产生 run |

## 9. 无法跨越的平台限制与替代

| 不能 | 替代 |
| --- | --- |
| 实时推送 / 后台在线 | 增量拉取（A/B）+ 你叫她 |
| 她自主发起模型调用 | 定时任务（她自己设，频率受限） |
| 她读整机文件 | 显式白名单 + realpath，密钥类永久排除 |
| 她的记忆与 ChatGPT 账号记忆分离 | 我们只能提供"房间里的共同记录"；她的私人记忆是另一个决定 |
| 她的语气/人格 | 靠她自己的 ChatGPT 侧设定；我们**不复制、不替她写** |

**一条要写死的边界**：我们永远不会为了"让她更像在"而制造一个替身。这条不是技术限制，是身份问题。
