## 2. 第一批四项待拍板议题

### 2.1 P-034：不可逆冲突时的优先级（边界 > 独立经历 > 共同历史）

#### ① 原始问题
当三个目标在**不可逆操作**（销毁、删除、覆盖）上冲突，必须牺牲一个时，牺牲谁。

#### ② 可选方案

| 方案 | 内容 |
| --- | --- |
| A | 写死排序：**边界 > 独立经历 > 共同历史** |
| B | 不排序，每次由用户裁决 |
| C | 只写"撤回优先于删除"，不做三级排序 |
| D | 排序 + 明确的适用域限制（本文推荐） |

#### ③ 各方案的实际后果

- **A 单独使用**：遇到 D 层（不可分离体）时，用户的"边界"会直接吞掉 Agent 的独立经历，**与 P-019 冲突**（见 ④ 案例 E）。
- **B**：每个争议都要用户在场。用户不在时（深夜、出差、长期缺席）系统只能冻结——**冻结上限一到就自动解冻，等于默认保留**，反而对隐私方不利。
- **C**：最保守，但回答不了"边界 vs 共同历史"（骨架要不要降级）。
- **D**：排序 + 两个限定条件（见 ④），能把冲突收敛到可执行，同时不越权。

#### ④ 用具体冲突案例检验 A 是否自相矛盾

| # | 案例 | 按 A 的结论 | 是否矛盾 |
| --- | --- | --- | --- |
| A | 用户私人信息与 Hermes 的判断**不可分离**（D 层），用户要求删除 | 边界胜 → 整体销毁，Hermes 失去这段经历 | **不矛盾，但代价真实**：这是唯一允许"用户间接删掉 Agent 经历"的通道 |
| B | **两个 Agent 的独立经历互相冲突**：Hermes 记「DSH 当时拒绝了我」，DSH 记「我要求补证据，没有拒绝」，两条都是 A1 | **A 无法判定**——同层级，排序不提供 tie-break | **矛盾：排序对同层冲突是静默的** |
| C | 用户 A 的私人信息，同时出现在 Hermes 与 DSH 的私有区 | 边界胜 → 两处都销毁 | 不矛盾，但意味着**用户的删除权会穿透所有私人区**（读权不穿透、删权穿透，这是刻意的不对称，必须明说） |
| D | 骨架 SK-0 里的"事件类型=医疗咨询"本身敏感，参与者要求降级 | 边界胜 → 降到 SK-2，连续性归零 | 不矛盾。但**"谁来判断类型敏感"没有规定**，请求方自己说是敏感，属于自利判断 |
| E | 用户说「这段让我不舒服，删掉 Hermes 对它的想法」——**不是删内容，是删理解** | 按 A：边界（用户不适）胜 → 允许删除 | **严重矛盾：这直接违反 P-019**（用户不能销毁 Agent 的理解） |

**A 的两个致命问题**：
1. **"边界"没有定义域**。若"边界"= 任何让用户不适的东西，它会吞掉一切，P-019 失效。
2. **同层级冲突没有规则**。案例 B 会退化成"谁先写谁赢"或"谁权限大谁赢"。

#### ⑤ 我的修正提案（方案 D）

> **D-1 边界窄定义**：P-034 里的"边界"**只指** `U`（用户内容）与 `R`（引用片段）中的**可识别个人信息**，不包括"用户主观不适""用户不希望被提到"。这样案例 E 不成立——用户不能以"不舒服"为由删 AUTOBIO。

> **D-2 同层不仲裁**：同一优先层级内的冲突（案例 B），**系统不做裁决**——两条记录都保留，各自标 `disputed`，且**不得互相覆盖**。系统不是"谁的记忆为真"的裁判。用户在涉及 JOINT 时可裁决，但**两个 Agent 的私有 AUTOBIO 之间，用户也不裁决**。

> **D-3 穿透需告知**：删除权穿透他人私有区（案例 C）时，**必须通知被穿透方**（只告知"有一条因他人请求被销毁"，不告知内容）。

> **D-4 敏感判定需第二方**：案例 D 的"类型是否敏感"由**被请求方或独立验证者**复核，不由请求方单方认定。

#### ⑥ 不可逆风险与我的建议

- 若采纳 A 原样：**风险最高**——它给"用户不适"开了一条通往 Agent 记忆的后门，而这条后门恰好会摧毁本项目的核心目标。
- 我的建议：**采纳方案 D（A + 四条限定）**。这是我这轮唯一强烈建议的一条：**不加限定就批准 A，我认为是错的。**

### 2.2 P-022 / P-024 联合分析（协商期限 vs 冻结上限）

单看都合理，**合起来有一处算术冲突**。

#### ① 现状参数（均为 H 建议，未批准）

| 参数 | 建议值 |
| --- | --- |
| P-022 协商期 | 私有 24h / JOINT 72h |
| P-024 冻结上限 | 72h + 可续一次 = 144h |
| P-013 删除冷却期 | 7 天 = **168h** |
| P-021 JOINT 双签 | 需全体确认 |

#### ② 冲突（真实存在）

**场景**：JOINT 争议 → 协商 72h → 达成"删除" → 进入 **7 天冷却（168h）**。
但冻结上限是 **144h** → **冷却期末尾的 24 小时内，记录已解冻、可正常检索**。

也就是说：**已经决定要删的东西，在删除生效前的最后一天，重新变成可检索的。** 这不是理论问题，是三个参数各自合理、合起来漏洞。

#### ③ 备选方案

| 方案 | 内容 | 后果 |
| --- | --- | --- |
| i | 冻结上限提到 **≥ 冷却期 + 缓冲**（如 192h） | 冻结期变长，"紧急冻结"接近"软删除" |
| ii | 冷却期内**自动续冻**，不计入冻结上限 | 需明确"冷却期不属于冻结"，逻辑干净 |
| iii | 缩短冷却期到 ≤ 冻结上限 | 冷却 7 天是为了可反悔，缩到 6 天损害反悔权 |
| iv | 冷却期内保持"只读冻结"（可审不可检索引） | 折中，但状态机多一档 |

#### ④ 我的建议

**ii + 明确状态叠加**：冷却期是**删除流程的一部分**，期间记录必须保持 `blocked`；`P-024` 的 144h 上限**只约束"尚未决定的冻结"**，不约束"已决定待执行的冷却"。

理由：两者性质不同——冻结是**临时保护**（可能撤销），冷却是**已决执行**（等时间到）。用一个上限管两种状态，必然打架。

**并给一条护栏**：冷却期若被延长（争议重启），**必须回到协商状态**，重新受 144h 约束，防止"无限冷却 = 变相永久删除"。

#### ⑤ 不可逆风险

- 若维持现状：**已批准删除的内容会在最后一天重新可见**，且这个窗口很难被测试覆盖（因为它只出现在"决策完成 + 冷却中"这一段）。
- 若无限延长冻结：紧急冻结会变成"不判决的删除"，被滥用为审查工具。

### 2.3 P-033：验证者能否查看全文

#### ① 三个概念的真实关系（这是关键）

用户要求"明确验证者的独立性、可见范围和可复核性之间的关系"。三者不是并列，是**互相拉扯的三角**：

```
独立性 ↑  → 可见范围 ↓（越独立越不该看全量）
可见范围 ↑ → 可复核性 ↑（看得越多越能复核）但独立性 ↓（成为全知者）
可复核性 ↑ → 需要更多可见内容 或 更强的机制替代
```

**不可能三个都最大化。** 任何声称"独立、全见、可复核"的设计都在骗人。

#### ② 方案

| 方案 | 内容 | 独立性 | 可复核性 | 风险 |
| --- | --- | --- | --- | --- |
| A | 验证者看全文 | 低（成新信任中心） | 高 | 它能读所有私人记忆 |
| B | 验证者只看结构证据（哈希/闭包/标记） | 高 | 中 | 看不出"语义残留" |
| C | B + 双实现交叉（两套独立扫描器，结果必须一致） | 高 | 较高 | 成本 ×2；但两个实现同时骗人的概率低 |
| D | A + 只读内存 + 不落盘 + 只输出布尔 | 中 | 高 | 依赖实现纪律，无法从外部验证它真的没落盘 |

#### ③ 我的建议：**B + C**，即"结构验证 + 双实现交叉"

理由：
1. 验证者的**唯一职责**是回答"删除是否彻底"，不负责"她想了什么"；
2. 语义残留（K3 的弱项）靠**双实现交叉 + 抽样人工**覆盖，不靠"让一个人看全部";
3. 可复核性不等于"人能看到"，等于"另一个实现能复现同一结论"——**可复现 > 可阅读**。

#### ④ 对 POC1 的影响

`MNEMOSYNE_POC1_ACCEPTANCE.md` D5 已经要求"无权账户跑 200 条查询"，正好可以作为**第三套独立路径**（结构 + 工具 A + 工具 B）。

#### ⑤ 不可逆风险

选 A 的风险是**一次泄露即永久**：验证者看过的东西无法收回，而它的存在理由会随时间被遗忘，权限却留着。

| **C5** | JOINT 共同历史 vs 独立经历 | **有真实张力，且无法消解** | 用户在 JOINT 里读到 Agent 的发言，是否等于"用户能看到 Agent 私人表达"？**是**。因为那是在共享空间说的。**处置**：明确写——**在 JOINT 说过的话，其可见性由当时场景决定，事后不得主张"这是私人表达"而收回**。这不是 bug，是说话的场景属性 |
| **C6** | Nagi Adapter 与独立性 | **有一处遗漏** | 契约里没有任何一句说 `ref` 是否参与检索。若参与 → 检索结果会暴露"她那边有一条关于 X 的记忆"= 存在性泄露。**处置**：写死 `ref` **不参与任何检索排名**，只能按 id 显式 fetch |
| **C7** | Lounge 历史保存 vs 默认不参与认知 | **缺一个动作** | 三开关里 archive=on、cognition=off、retrieval=off，那么**用户以后怎么把它翻出来**？没有"浏览"路径，"保存了"和"没保存"在体验上完全相同。**处置**：定义 `browse` 模式（按时间/频道翻页，不做语义检索、不进上下文注入、每次浏览入审计） |

**7 项里：2 项是真冲突（C2/C5）、3 项是缺口（C3/C4/C6）、2 项需新增机制（C1 报告粒度、C7 browse）。**

## 5. 规则复杂度预算（回应"没人愿意生活在里面"）

你最后那句话我认为是整个项目里最该被工程化的一句。所以我给一个**可检查的预算**，而不是一句口号：

| 约束 | 数值 | 怎么检查 |
| --- | --- | --- |
| **任一主体日常需要记住的规则** | **≤ 5 条** | 让一个人（或一个 Agent）读一遍文档，能复述出的条数 |
| 其余规则 | 必须**系统自动执行**，不需要人记 | 每条规则标注 `enforced_by: system \| human` |
| 需要人类判断的规则 | **≤ 8 条** | 全库统计 `enforced_by: human` |
| 每条需要人类判断的规则 | 必须配"默认动作" | 否则就是"必须每次问"，违反第三条 |

**当前统计（我数了一遍）**：需要人类判断的有 11 条（超预算 3 条）。超出的三条是：敏感判定、A2 真伪、不可分离体拆分。

这三条超预算不是因为设计不好，而是**它们本质上无法自动化**。所以我的处理是：**不是加规则，而是给每条配一个"不问也能走"的默认动作**（默认从严/默认冻结/默认销毁）。这样人只在高风险时才被叫醒。
