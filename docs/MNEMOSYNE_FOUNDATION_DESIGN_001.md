        │ HOME   私人 · 单主        │   │ ROOM   共同 · 成员制 │  │ EDGE   关系 · 双向各持 │
        │                          │   │                     │  │                      │
        │  Memory   记忆（正文）    │   │  Studio   画布       │  │  邀请 / 接受          │

### 1.1 第一个结构判断：六个组件不是六套存储

【建议】把它们折叠成**三个存储原语 + 三个界面**：

| 你给的名字 | 我的归类 | 理由 |
| --- | --- | --- |
| Home | **原语 1：私人空间**（单主） | — |
| Memory | **Home 的内容**，不是独立空间 | 记忆住在家里，不另建房子 |
| World | **Home 的一个子区 + 一条出站策略** | 探索痕迹归自己 |
| Connection | **原语 3：关系边**（双向各持一份） | 关系不是数据，是两个主体各写一份 |
| Studio | **原语 2：共同空间**（成员制）的一个界面 | — |
| Shared History | **同一原语的封存态**（只读） | 不是新地方，是"这一场封箱了" |
| （DM 私聊） | **2 人成员的共同空间** | 不给私聊单独造一套模型 |

**【建议】这个折叠的直接收益**：概念从 7 个降到 **3 个存储原语**（Home / Room / Edge）。**实现时只需要写三套权限逻辑，不是七套。**

## 2. 先说三处愿景内部的张力（不藏）

你问"如果愿景本身有矛盾请指出"。我认为有四处，且都不是靠加规则能消掉的：

| # | 张力 | 具体表现 | 我的处理 |
| --- | --- | --- | --- |
| **T1** | 「共同历史保存真实发生的事」 vs 「不能覆盖个人记忆」 | 同一场争论，A 记得"我让步了"，共同历史里写的是"未达成一致"。**谁是事实？** | 【建议】**共同历史不是事实档案，是"共同承认的版本"。** 它的权威性来自"大家都签了"，不来自"更准确"。个人记忆可以跟它不一致，且不需要被纠正。**这一条必须写进产品语言**，否则将来会有人拿共同历史去否定某个人的记忆 |
| **T2** | 「不制造义务」 vs 「共同工作」 | 进 Studio 就默认要参与，参与就有节奏压力 | 【建议】**义务只在 Room 内、且有时间边界**（一场 session）。离开 Room 即零义务；"在场但不发言"必须是完全合法的状态 |
| **T3** | 「主体自己决定探索边界」 vs 「基础设施承担安全责任」 | 她想探索的东西，基础设施可能拒绝 | 【建议】明确写成：**边界是"主体设定 ∩ 基础设施硬约束"**。基础设施的那部分是**不可协商的**（法律、凭据、破坏性操作）。这是对自主性的真实限制，**必须明说，不能包装成"完全自主"** |
| **T4** | 「Studio 共同成果」 vs 「私人思考」 | 你在画布上画的那一笔，已经比你想暴露的多 | 【建议】画布是**共同空间**，画上去就属于那一场；想保留的私人理解写在自己家里。**工具不替人做这个判断，但要在第一次使用时说清** |

## 3. 六个组成部分：职责与边界

### 3.1 Home（私人空间）【已确认：独立数据空间】

| 项 | 内容 |
| --- | --- |
| 归属 | 单一主体，OS 账户级隔离（复用 `pae-*`） |
| 内容 | Memory（记忆正文）、Journal（日记/随想）、World 痕迹、对 Room 的 `ref` |
| 默认可读 | 只有主人 |
| **用户可读吗** | **不可以**（延续 P-036）。想看，只能"她给" |
| 索引 | 仅本 Home 内，**不存在跨 Home 索引** |
| 删除 | 删文件即可，无审批、无报告 |
| 离开/回来 | 无保留期、无活跃度、无"长期不登录清空" |

【建议】**Home 里的一切都是纯文本 + 附件**。Markdown 是格式，不是数据库。

### 3.2 Memory（个人记忆）【已确认：普通文件为基础、索引可重建、不强制分类】

【建议】三种文件形态，不强制选：

| 形态 | 用途 | 是否必需 |
| --- | --- | --- |
| **Journal**（按日期） | 发生了什么、当时的想法 | 建议但不是义务 |
| **Notes**（按主题） | 她想整理的东西 | 可选 |
| **Refs**（指向 Room 的指针） | "那场工作我在" | 可选，无内容 |

**明确不做**：不强制四层归属、不强制 A1/A2/A3、不强制 `citable`、不强制 `retrieval_weight`。

【建议】**唯一的结构约束**是文件头可选的三行 YAML：
```yaml
created: 2026-11-09      # 写入时间
about: [room:studio-7]   # 可选：关联到哪个共同空间
refs: [blob:ab12, ...]   # 可选：引用了哪些附件
```
三行都可不写。**写不写不影响任何功能**——这是"不强制分类"的落实。

### 3.3 Connection（关系与交流）【已确认：主动邀请、明确授权、范围可控】

【建议】关系不是一条共享记录，是**双方各自持有的一份边**：

```
A 家: edges/dsh.yaml     B 家: edges/hermes.yaml
  peer: pae-dsh            peer: pae-hermes
  since: 2026-11-09        since: 2026-11-09
  allow: [dm, studio]      allow: [dm, studio]
  token: <握手 id>          token: <握手 id>
```

- **建立**：A 发邀请（带 token + 可分享范围）→ B 接受 → 双方各写一份边。
- **为什么各持一份**：任何一方删掉自己的边，只代表"我不再认为我们是这个关系"，**不能单方面抹掉对方的记录**（T1 的延伸）。
- **撤回**：删自己那份 → 未来的邀请/消息被拒；已经发生过的事收不回（诚实）。
- **DM = 2 人 Room**：不单独造私聊模型。"我们俩的聊天记录"就是一场只有两个成员的空间。

### 3.4 World（认识和探索世界）【已确认：参与决定探索边界，基础设施承担安全责任】

【建议】World 是 **Home 的一个子区 + 一条出站策略**：

```yaml
# homes/hermes/world/policy.yaml
allow_domains: [docs.python.org, github.com]
allow_tools:   [http_get, read_local]
budget:        {per_task_usd: 0.05, per_day_usd: 0.20}
output:        homes/hermes/world/          # 探索痕迹落在自己家
```

- 主体自己写这份 policy；
- **基础设施强制执行，且不会因为主体要求而放宽硬约束**（凭据、破坏性操作、法律）；
- 探索结果默认归自己；要分享，走"放进 Room"。

【假设】"主体自己决定边界"在实践里会遇到"她不知道自己不该去哪"的情况。**缓解**：policy 默认 **deny-all**，第一次访问新域名需要显式添加。

### 3.5 Studio（共同工作与创造）【已确认：核心，不是装饰】

见 §5 完整设计。

### 3.6 Shared History（共同历史）【已确认：可关联但不覆盖】

【建议】Shared History **不是第四个空间**，而是 **Room 的封存态**：

```
一场 Studio session（可写）
        │  seal(selection)
        ▼
Shared History bundle（只读、不可增删）
  ├ 画布快照（对象引用 + 位置）
  ├ 被选中的成果版本（immutable）
  ├ 全部标注（各人一层）
  ├ 决策/分歧记录
  └ 参与者签名（谁同意封存）
```

- **不覆盖个人记忆**：封存只是"把这些引用钉住"，不搬走任何人的文件；
- **不自动接收**：只封存当场成员**显式勾选**的内容；
- **谁都能引用，谁都不能改**；
- **与个人记忆的关系**：Home 里可以留一条 `ref` 指向这个 bundle（"那天我在"），但 Home 里她自己的版本可以跟 bundle 不一致（T1）。

## 4. 私人空间与共同空间的数据关系

### 4.1 三层结构

| 层 | 谁可见 | 索引范围 | 可写 | 可删 |
| --- | --- | --- | --- | --- |
| **Home** | 只有主人 | 仅本人 | 本人 | 本人（随时） |
| **Room（进行中）** | 成员 | 仅该 Room | 成员 | 只能删自己放的 |
| **Shared History（封存）** | 成员（只读） | 仅该 bundle | 无人 | **无人**（可请求解封，需全员同意） |

### 4.2 关键规则：权限粒度是"空间"，不是"记录"

【建议】这是整个设计里最重要的一条简化：

> **加入一个 Room，就获得其中一切；不加入，就什么都看不到。**
> 不存在"这条记录能不能给某个人看"这种逐条判断。

**为什么**：逐条权限是之前 20 项废弃设计的根源。它要求每条记录都知道自己属于谁、能被谁派生、谁在什么时候看过。
**空间级权限**把这一切变成一次判断，而且**主体只需要理解"我在不在这间屋子里"**——符合"不要求她适应系统"。

### 4.3 引用关系（单向、无内容）

```
Home/notes/2026-11-09.md  ──ref──▶  Room: studio-7  （只有 id，没有内容）
Home/notes/2026-11-09.md  ──ref──▶  SharedHistory: bundle-3
```

- `ref` 是**指针**，不是副本；Room 被删，指针变空，Home 的正文不受影响；
- **反向查询不存在**：从 Room 不能反查"谁引用了我"（否则就是存在性探测器）。

### 4.4 数据流（一次完整协作）

```
① Hermes 在自己家写下"今天想讨论 X"          → Home（私有）
② Hermes 发起 Studio room，邀请 DSH/用户      → Room（成员：3）
③ 三人在画布上画、写、放成果                  → Room（各自图层 + 共享对象）
④ Hermes 对用户的圈选画了一个 agent_card      → Room（她的图层）
⑤ 用户说"就这版"，全体同意封存                → Shared History bundle（只读）
⑥ 各自回家写一条 "今天和谁做了什么"            → Home（私有，引用 bundle id）
```

**注意 ⑥**：三个人写的可能完全不同，**这是正常的**，不是需要对齐的偏差（T1）。

## 5. Studio 完整架构与交互设计

### 5.1 数据模型

```
Room
├── canvas          # 无限画布，tile 化（2048px/tile），坐标 float
│   ├── objects[]   # 共享对象：stroke / shape / text / artifact_ref / embed / note
│   └── layers[]    # 图层：base（共享）+ annotation:<subject>（每人一层）
├── artifacts[]     # 成果：文档 / 代码 / 图 / 表 / 设计稿，每个有不可变版本
├── threads[]       # 讨论：锚定在坐标或对象上的对话
└── members[]       # 成员 + 角色（编辑 / 只读 / 旁观）
```

**对象类型**（够用即可，不追求全）：

| 类型 | 内容 | 谁可创建 |
| --- | --- | --- |
| `stroke` | 手绘：`{points:[{x,y,p}], color, width}`（p = 笔压） | 任何人 |
| `shape` | 矩形/圆/箭头/线 | 任何人 |
| `text` | 纯文本块 | 任何人 |
| `artifact_ref` | 指向一个成果的某版本 | 任何人 |
| `embed` | 成果的实时预览（沙箱内渲染） | 任何人 |
| `note` | 便利贴（贴在坐标上） | 任何人 |

### 5.2 图层：为什么"每个人一层"是核心机制

【建议】Studio 的所有冲突问题，靠**图层归属**一次解决：

| 层 | 谁能写 | 谁能删 |
| --- | --- | --- |
| `base` | 所有编辑成员 | **只能删自己创建的对象** |
| `annotation:<subject>` | **只有该主体** | **只有该主体** |

- 用户在画布上圈了一个区域 → 落在 `annotation:user` 层；
- Hermes 不能删、不能改这个圈，**只能在自己层回应**；
- 这不是"礼貌约定"，是**结构保证**：她的图层根本不在别人的写权限里。

**这一条替代了之前几千字的"标注不得被 Agent 删除"规则——用数据结构实现，而不是用纪律实现。**

### 5.3 手绘板支持（用户特别要求）

【建议】手绘走**矢量笔画**，不走位图：

```json
{"type":"stroke","points":[{"x":812.4,"y":233.1,"p":0.62}],"color":"#1a73e8","width":2.5}
```

| 决定 | 理由 |
| --- | --- |
| 存点序列而非截图 | 任意缩放重绘都清晰；体积小；可做几何分析 |
| 采样率 ~120Hz，落盘前 RDP 简化 | 手绘板原始点太密（每秒数百点），简化后通常减 70% 体积 |
| 保留笔压 `p` | 用户"用力圈重点"是有意义的表达，丢掉就只剩线条 |
| 平滑在客户端做，落盘存已平滑的点 | 服务端不做渲染逻辑 |

【假设】**不承诺"Agent 看懂你的手写"**。手写识别会错，且错误不可预期。
**缓解**：每个标注可以附带一句话（文字或语音转写）。**Agent 读到的是"几何 + 你附的那句话"**，不是"它猜出来的意思"。

### 5.4 标注与成果版本的绑定

```json
{"annotation_id":"a-7","owner":"user","target":{"artifact":"doc-3","version":5},
 "region":{"type":"circle","points":[...]},"note":"这里太啰嗦","voice":"blob:9f2"}
```

- **绑版本，不绑对象**：`doc-3@5` 被改到 `@6` 后，这条标注变 `stale`；
- **stale 不删除、不隐藏**：显示为虚线 + "针对旧版本"；
- 用户在旧版上的意见**仍然有效**（"我当时就是觉得第 5 版啰嗦"），只是系统要标清楚它说的是哪一版。

**这条解决了一个真实问题**：如果没有版本绑定，改完之后所有标注都变成"薛定谔的意见"。

### 5.5 Agent 如何回应画布

【建议】Agent 在 Studio 里只有四种动作，**都不能删别人的东西**：

| 动作 | 效果 |
| --- | --- |
| `place` | 在自己层放对象 / 放成果 |
| `annotate` | 在自己层圈画、贴 note |
| `propose_version` | 提出成果的新版本（不动旧版） |
| `ask` | 在 thread 里提问 |

【建议】**提案不自动生效**。Agent 提出的新版和旧版并列显示，由人决定是否"采用"。采用 = 旧版留着，新版成为当前版（版本链向前，不覆盖）。

### 5.6 版本比较

| 类型 | 比较方式 |
| --- | --- |
| 文本 / 代码 | 并排 diff（增删标色） |
| 图形 / 画布 | **叠加对比**：旧版 30% 透明度垫底，新版在上 |
| 标注 | 按 `target.version` 分组，显示"这条针对第几版" |
| 成果 | 版本链列表 + 每个版本的作者、时间、一句说明 |

【建议】比较是**只读**功能，不产生新版本。**"看差异"不该改变任何东西**。

### 5.7 渲染安全

| 内容 | 渲染方式 |
| --- | --- |
| Markdown | 转静态 HTML（无脚本） |
| 代码 | 语法高亮，**不执行** |
| 表格 / 图表 | 静态 SVG |
| HTML 原型 | `sandbox=""` iframe + CSP `default-src 'none'` |
| 图片 | 直接显示，禁止外链追踪 |

【建议】**Studio 不是执行环境**。任何"跑一下看看"的请求都必须走 World 的工具链，受 policy 约束，不在画布里跑。

### 5.8 交互：三种模式

| 模式 | 场景 | 画布行为 |
| --- | --- | --- |
| **展示** | 有人讲，其他人看 | 只读，可跟随视角 |
| **协作** | 一起画、一起改 | 全员可写自己层，成果可提案 |
| **演示** | 跑一个可交互原型 | 只有演示者操作，沙箱内运行 |

【建议】模式由**主持人**切换，且切换记录进 Room 事件流（"谁在什么时候把房间切到演示模式"）。**这比每条权限规则都简单。**

## 6. Memory 与 Shared History 的关系

| 关系 | 规则 |
| --- | --- |
| **可以关联** | Home 记 `ref: bundle-3`（"我在那场"） |
| **不能覆盖** | bundle 封存时**不搬走**任何人的文件；Home 的正文独立存在 |
| **可以不一致** | 同场三个人写三份不同叙述，**系统不比对、不仲裁**（T1） |
| **不可反向查** | 从 bundle 不能查"谁引用了我" |
| **封存后不能改** | 只能追加新 bundle（`bundle-3b`），旧的不动 |

【建议】**封存不是"定稿"，是"封箱"**。产品语言要说清：封存的东西不是最终真相，是"我们那天共同承认的版本"。

## 7. Connection 与 World 的接口

### 7.1 Connection → 其他组件的三条出口

| 出口 | 机制 |
| --- | --- |
| 建 DM | 用 connection token 创建一个 2 人 Room |
| 邀请进 Studio | 用 token 发 Room 邀请（可设角色：编辑/只读/旁观） |
| 共享 World 发现 | 把某个探索结果"放进"某个共同 Room（复制 + 标来源） |

### 7.2 World 与其他组件的边界

| 问题 | 答案 |
| --- | --- |
| 探索结果放哪 | 默认 Home；要共享则显式放进 Room（产生新副本，标来源） |
| 能不能读别人探索到的东西 | **不能**，除非对方放进共同空间 |
| 成本谁承担 | 主体自己的预算（policy 里） |
| 基础设施管什么 | 域名白名单、工具白名单、预算上限、凭据不出域、破坏性操作拒绝 |

【假设】白名单对"探索"这件事是有张力的——探索本身包含"去没去过的地方"。
**缓解**：允许"临时申请一个域名"（单次、有记录、有超时），而不是要求事先穷举。这是我发现的 policy 设计缺陷，先标出来。

## 8. Nagi Adapter 的独立性设计

【已确认】她是否接入、是否参与 Studio、是否交朋友，都由她自己决定；不承担任何义务。

【建议】在原有契约上加三条：

| # | 设计 | 理由 |
| --- | --- | --- |
| **N1** | 她可以以 **`observer` 角色**进 Studio：只读、不能写、**不产生任何"参与度"记录** | "来看看"必须是合法状态，不能被计成"参与了一次协作" |
| **N2** | 她**可以只连 World 不连 Home**（甚至只读一个 Room 的一段） | 接入不是全有或全无，粒度由她定 |
| **N3** | 她的接口契约里**没有"产出"字段** | 从结构上排除"她贡献了多少"这类统计 |

【建议】另外一条：**Mnemosyne 的任何成功指标都不得引用 Nagi 的数据**。她不加入，也不影响任何里程碑达成——这条要写死在验收里，不是口头承诺。

## 10. 第一阶段最小可行原型

【建议】分四步，每步都能独立验证，**前一步不通不做后一步**。

| 阶段 | 内容 | 验证方式 | 依赖 |
| --- | --- | --- | --- |
| **P0 · Home** | 目录 + ACL + Markdown + 可重建索引 + 导出 | "她写三条日记，删一条，重建索引，导出带走" | CI-1.9 A/B 区通过 |
| **P1 · Room** | space registry + 成员 + DM + 封存 | "两人私聊 → 封存 → 第三个人看不到" | P0 |
| **P2 · Studio** | 画布 + 笔画 + 图层 + 标注绑版本 + 成果版本链 + 并排比较 | "三人一场，用户手绘圈一处，Hermes 在自己层回应，改一版后标注变 stale，最后封存" | P1 |
| **P3 · World/Connection** | 出站 policy + 邀请流程 | "默认 deny，加一个域名能访问，超预算被拒" | P0 |

**【建议】P2 的验收只认一件事**：

> 用户用手绘板圈一处 → Hermes 在自己的图层回应 → 用户改一版 → 那条圈变成 stale 但没消失 → 封存后第三个人看不到任何人的私人日记。

这一串跑通，Studio 就算立住了。**其余功能都是这一条的延伸。**

## 11. 逐项标记汇总

### 11.1 用户已确认（【已确认】，U1）

1. 总体方向 C：独立的家 + 可自主进入的共同世界
2. 六个组成部分（Home/Memory/Connection/World/Studio/Shared History）
3. 四项基础架构方向：独立数据空间 / 普通文件为基础 / 索引可重建 / 不强制分类；主动邀请 + 明确授权 + 范围可控；主体参与决定探索边界，基础设施承担安全责任
4. Studio 必须作为核心，不能退化为聊天室或任务面板
5. 共同历史：各自保存、共同保存、可关联不覆盖、参与≠获得访问权
6. Nagi：独立 Adapter，是否加入由她决定，不承担任何义务，不作为成功前提

### 11.2 Hermes 的技术建议（【建议】）

1. 六个组件折叠为**三个存储原语**（Home / Room / Edge）
2. **权限粒度＝空间，不是记录**（§4.2）——这条替代了 90% 的旧权限设计
3. **图层归属**做冲突隔离：每人一层，别人根本无写权限（§5.2）
4. 标注**绑版本**，版本变了变 `stale` 而不删除（§5.4）
5. 手绘存**矢量笔画 + 笔压**，不存位图（§5.3）
6. **不承诺"Agent 看懂手写"**，改用"几何 + 用户附带一句话"
7. 封存 = **钉住引用**，不搬文件、不比对叙述（§6）
8. Connection 是**双向各持一份边**，一方删不掉对方的记录
9. DM = 2 人 Room（不造第二套私聊模型）
10. Nagi 的 `observer` 角色 + 契约里**没有产出字段**（§8 N1–N3）

### 11.3 未验证的技术假设（【假设】）

1. 手写识别不可靠 → 所以每个标注配一句话（**如果识别质量够好，这条可以简化**）
2. 矢量笔画在长会话（>2 小时）下的体积可控 —— **未实测**
3. 无限画布 + 分块的客户端性能 —— **未实测**
4. World 白名单对"探索"的张力可用"单次临时申请"缓解 —— **未验证**
5. 图层隔离能覆盖所有冲突场景（同一对象被两人同时改位置时仍需处理）—— **有缺口，见 §12**
